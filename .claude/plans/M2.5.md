# Plan: M2.5 `Option` and `Result`

ADRs: 0044, 0045, 0046
Base: 863bd339660d8e5c80f97d402e8dca9e500da13f
Program on QEMU: a number parser returning `Result`
(`tests/e2e/number_parser.ers`, step 6).
Out of scope:
- `Option` and `Result` as comptime functions in `core`, paths such as
  `Option(u32)::Some`, and `!` as a type argument (M6);
- placing `Option` and `Result` in a module (M2.6);
- converting error types in `?`, and `?` on anything but `Option` and
  `Result` (not scheduled);
- a `PanicReason` for "enum value is no variant" (M2.6).

Before step 1: the `docs(adr)` commit that accepts ADR 0044 to 0046 also
sets the status lines of the ADRs they amend, in the files as
`Accepted; amended by NNNN (what changed)` and in the index
(`docs/adr/README.md`) in its style, `Accepted, amended by NNNN`:
- ADR 0035: amended by 0044 (a variant may be named `.V`);
- ADR 0037: amended by 0044 (`.V` patterns);
- ADR 0039: amended by 0044 (`.V(args)` builds a variant);
- ADR 0040: amended by 0044 (`.V` patterns, and the enums a `match`
  needs).

## 1. feat: variants named by the expected type in expressions
- Status: done
- Implements: ADR 0044, "`.V` in expressions", "`E::V` stays" and the
  diagnostic code.
- Changes:
  - `src/syntax/{ast,parser}.rs`: in `primary`, a `.` followed by a
    name, and optionally arguments parsed as a call's (trailing comma
    allowed), is one node, a variant named by the expected type. The
    postfix `.` after an expression stays a field access.
  - `src/hir/{mod,lower}.rs`: an unresolved `ExprKind` holding the name,
    its span, and the arguments if written with parentheses (so that
    `.V()` stays apart from `.V` for the count check, as for
    `ExprKind::Variant`), visited by `Expr::walk`.
  - `src/ty.rs`: the node is resolved against the normalized expected
    type: an enum gives `(EnumId, variant index)`, recorded in `Tables`
    for MIR building; then it is checked as `ExprKind::Variant` is
    (payload count, each argument against its payload type, not a
    place). It takes its expected type exactly where an integer literal
    does, siblings included (`if`/`match` branches, `break`s, array
    elements through `array()`'s pending list, binary operands):
    `needs_expected_type` returns true for it. No expected type is
    `ty::untyped-variant`, with the `E::V` help when exactly one
    *declared* enum has a variant of that name, and the "write the
    type" help for `.None`, `.Some`, `.Ok`, `.Err`; a non-enum expected
    type is `ty::mismatched-types` ("found variant `.V`"); an unknown
    name `ty::unknown-variant`; `Error` reports nothing. When the `.V`
    is in error, its arguments are checked against `Error`. The `as`
    operand rule of ADR 0017 does not apply to it: `.Run as u8` is
    `ty::untyped-variant`.
  - `src/mir/build.rs`: the node is built from the resolution in
    `Tables`, exactly as `ExprKind::Variant`.
- Tests:
  - ui (parser) `parse_context_variants.ers`: `.V`, `.V(a, b,)`,
    nested `.Some(.Run)`-like arguments with a declared enum, a
    statement starting with `while` followed by `.V` on the next line
    (a new tail expression), `x.V` still a field access.
  - ui (typeck) `typeck_context_variants.ers`: `.V` accepted at every
    position ADR 0044 lists (`let`, constant, static, assignment,
    argument, payload value, struct field, array element and repeat,
    `return`, function tail, block tail, `if` branches, `match` arm
    bodies, `break` value, `comptime` operand, both sides of `==`), for
    an enum without payloads and one with payloads, and with types from
    siblings: `if c { m } else { .Off }`, a later `match` arm, a later
    `break`, `[m, .Off]`.
  - ui (typeck) `typeck_context_variant_errors.ers`: `ty::untyped-variant`
    as a scrutinee, in `.Run as u8`, in `.A == .B` and as an expression
    statement, with the `E::V` help (one enum has the name), without
    it (two enums have it), for `.None` (the "write the type"
    help), and for `.None` with a declared enum having `None` (both
    helps); `let x: u32 = .Run;`, `a[.Run]`, `if .Run {}`
    (`ty::mismatched-types`); `.Run < m` (`ty::invalid-operand`); an
    unknown name (`ty::unknown-variant`); `.Write(3)`, `.Nop()`,
    `.Write` (`ty::wrong-payload-count`); a literal out of range in a
    payload; `let x: u32 = .Write(3, 4);` and `.Bogus(1)`, one error
    each; an erroneous expected type reporting nothing more.
  - MIR snapshot `mir_context_variants.ers`: two functions, one with
    `.V`, one with `E::V`, whose MIR is the same.
- Decisions (taken while implementing, commit 26bf271):
  - The resolution of a `.V` expression is recorded in
    `Tables::variants`, keyed by `ExprId`; MIR building reads it and
    builds the node exactly as `ExprKind::Variant`. Known values
    (`src/mir/build/known.rs`, not named above) treat it as `Variant`
    too, without which `.V` and `E::V` would not give the same MIR.
  - `Diagnostic` holds a single help, so when both helps of
    `ty::untyped-variant` apply (`.None` with a declared enum that has a
    `None`), they are joined into one text: "name its enum:
    `Slot::None`; or, for the variant of `Option`, write its type where
    the value is expected, as in `let x: Option(u32) = .None;`".
  - When neither help applies (no declared enum has the name, or two
    do), `ty::untyped-variant` gives a generic help, "name the enum, as
    in `E::Off`, or give the value a type first". ADR 0044 only says the
    `E::V` help is absent then.
  - `cast` asks `takes_literal_type`, which leaves out `.V`, so ADR
    0017's rule for literal operands does not reach it: `.Run as u8` and
    `(-.Run) as u8` are `ty::untyped-variant`.
  - `.Off == .Run` is reported once, at the first operand.
  - Diagnostics keep naming variants of declared enums `E::V` even when
    the program wrote `.V` (e.g. "`Msg::Write` carries 2 values"), as
    ADR 0044 says.
  - An array made only of `.V`s with no expected type, such as
    `[.Off, .Run][0] == m`, reports `ty::untyped-literal` as an array of
    literals does, with a help whose example is an integer array.
    Consistent with "exactly where a literal takes its type"; the
    wording was left as is.
  - `.None` with both helps has its own test file,
    `typeck_context_variant_none.ers`: declaring an enum with a `None`
    changes the help of every `.None` in the program, so it cannot sit
    beside the case with only the "write the type" help.

## 3. feat: the types `Option(T)` and `Result(T, E)`
- Status: done
- Implements: ADR 0045, all sections except the run-time tests (step 4).
- Changes:
  - `src/syntax/{ast,parser}.rs`: a type written as a name followed by
    type arguments in parentheses, comma-separated, trailing comma
    allowed; `Name()` parses (a count error).
  - `src/hir/{mod,lower}.rs`: `hir::Ty` gets a built-in application
    (`Option` or `Result`, arguments leaked like pointee types), which
    `is_normal` reports as not normal. Lowering checks the count
    (`resolve::type-argument-count`, also for arguments after any other
    type name, and for `Option`/`Result` without arguments); an item
    any item (struct, enum, function, constant, static) named
    `Option` or `Result` is `resolve::duplicate-type`, and so, from now
    on, is any item named `bool` or an integer type: ADR 0029 asks this
    of every item named like a built-in type, but the check covered
    only structs and enums, so `fn usize() {}` and `const u8: u16 = 1;`
    were accepted. One check now serves every built-in type name.
    `Option::V` as a
    path (expression or
    pattern) is `resolve::not-an-enum` with the `.V` help. The parser's
    `parser::unexpected-token` for `::` after a call gets the same help
    when the callee is named `Option` or `Result` (only reached when
    its arguments parse as expressions). A `!` argument is
    recorded as a `NeverPosition` for `ty::never-in-memory`, and `[T]`
    as an `UnsizedPosition` for `ty::unsized`, as for payload types;
    the whole type then counts as erroneous.
  - `src/query.rs`: `normalize` normalizes the arguments and interns
    each distinct application as an enum with payloads: an `EnumId`
    after the declared enums, `int: u8`, `payloads: true`, a display
    name with computed lengths (`Result([u8; 4], ParseError)`), and the
    variants `None = 0`, `Some(T) = 1` or `Ok(T) = 0`, `Err(E) = 1`,
    whose discriminants are known without evaluation. An application
    with an erroneous argument normalizes to `Error`. Every lookup of an
    enum's definition (`hir.enum_` in `query.rs`, `ty.rs`,
    `ty/usefulness.rs`, `hir/mod.rs` and `mir/`) goes through one
    accessor that also covers these enums; `enums_needed` gets the
    payload types of a nested position the same way. Their layout and
    `mir_enum` reuse the enum-with-payloads code. Size errors have no
    declaration to point at: `ty::too-large` for an instance whose
    arguments all have layouts is reported at each place it is written
    (as for an array type); one whose argument failed reports nothing
    more (the `inner_failed` rule of `enum_layout`). A containment
    cycle through one is labelled at the first declared struct or enum
    of the cycle, counted from where it was found, the instance shown
    in the path. `--emit=typeck` and `--emit=mir` list
    instances after the declared enums, sorted by display name, so
    that dumps do not depend on the schedule (ADR 0028).
  - `src/ty/usefulness.rs` and witness printing: variants of these
    enums are printed `.V`.
  - Codegen and the evaluator: nothing new is expected; they see enums
    with payloads.
- Tests:
  - ui (parser) `parse_option_result.ers`: the types in every position
    a type is written, nested, behind pointers, in array types, with a
    trailing comma.
  - ui (resolve) `resolve_option_result_errors.ers`: every
    `resolve::type-argument-count` case of ADR 0045, `struct Option {}`
    and `enum Result: u8 { A = 0 }`, `fn Option() {}` and
    `const Result: u32 = 0;`, `fn usize() {}`, `const u8: u16 = 1;`
    and `static bool: u8 = 0;` (all `resolve::duplicate-type`),
    `Option::None` in an expression
    and a pattern, `Option(u32)::None`, an unknown argument type
    reported once.
  - ui (typeck) `typeck_option_result.ers`: accepted uses (fields,
    elements, parameters, returns, constants, statics, `.V` building,
    matches over both, nested `Option(Option(u8))`, `Option([u8; 4])`
    where `Option([u8; 2 + 2])` is expected), and a `comptime` block
    asserting `size_of`/`align_of` of every row of ADR 0045's table.
  - ui (typeck) `typeck_option_result_errors.ers`: `Option(!)`,
    `Result(u32, !)` in a function nothing calls (once each),
    `Option([u8])`, `struct Node { next: Option(Node) }`,
    `struct A { x: [u8; size_of(Option(Node))] }` before that `Node`
    (labelled at `Node`), `Option([u8; 0x7FFF_FFFF])` written twice
    (two errors), `Option(Big)` with `Big` too large (one error), a
    parameter `Option(Node)` beside the cycle (nothing more), `==`,
    `as`, `.f`, a volatile read of
    an `Option(u8)`, `Option(u32)` against `Option(u16)`, and witnesses
    `.None`, `.Some(_)`, `.Err(_)` and `.Some(Mode::Run)`.
  - MIR snapshot `mir_option_result.ers`: an `Option(u32)` built and
    matched, and its enum listed.
  - Layout against clang: `tests/layout/structs.ers` and `structs.h`
    get a struct with fields `Option(u8)`, `Option(u32)`,
    `Option(u64)`, `Option(())` and `Result(u32, Mode)`, its C twin
    using one union per field type.
- Decisions (taken while implementing, commit c5802ab):
  - `enums_needed` moved from `Hir` (`hir/mod.rs`) to `Queries`
    (`query.rs`): it needs the accessor `enum_def` and `normalize` for
    payload positions such as an `Option(Mode)` payload, and `hir`
    cannot reach `Queries`. `Hir::enum_` was removed so that no lookup
    bypasses `enum_def`.
  - Built-in enums have no declaration: `EnumDef.name_span`,
    `VariantDef.span` and `PayloadDef.span` became `Option<Span>`, and
    `VariantDef.value` became `VariantValue::{Comptime(FnId), Known(u64)}`.
    `EnumDef::variant_path` prints `E::V` for a declared enum and `.V`
    for a built-in one; witnesses and payload-count messages use it.
  - `ty::too-large` for an instance: reporting it only where layouts
    are computed missed pointees (`*const Option([u8; 0x7FFF_FFFF])`)
    and return types, leaving a function without a layout and with no
    diagnostic, and `into_mir` would then panic. Instead lowering
    records every written application with its span in
    `Hir::applications`, and a pass in `check_all`
    (`report_too_large_applications`) reports each too-large one at each
    place it is written, unless an argument failed. Every other position
    treats a too-large instance as already reported.
  - Containment cycles are rotated to start at the first declared
    struct or enum. The instance appears in the path without a label of
    its own; `ty::cycle` now accepts items without a span (`start_at`).
    Known gap: in `const N: usize = size_of(Option(S)); struct S { a:
    [u8; N] }` the `Option(S)` step is shown nowhere, although the
    comment at `start_at` says it is (left open, see below).
  - `offset_of` normalizes its type before matching it, so
    `offset_of(Option(u8), f)` gets the payload help.
  - `Option(u32)::None` is a parse error and the pipeline stops before
    resolution, so its test is `parse_option_result_errors.ers`, not the
    resolve file. The parser remembers where a call to `Option` or
    `Result` ends to give the `.V` help; the help text
    (`builtin_variant_help`) lives in the parser and lowering reuses it.
    The parser cannot depend on HIR, so its list of the names and
    variants of `Option`/`Result` repeats `BuiltinEnum`'s; keep both in
    sync.
  - Wording: `resolve::not-an-enum` says "`Option` is not an enum",
    labelled "an enum only with its type arguments, as in `Option(T)`",
    with the help "the variants of `Option` have no path: write `.None`
    where an `Option(T)` is expected, and that type gives it its enum".
    A type that takes no arguments written with empty parentheses
    (`u32()`) says "`u32` takes no type arguments, and is written
    without parentheses" (changed after review: it said "but none were
    given").
  - `Option(())`: the compiler places the zero-size payload at offset 1
    (the dumps show `Some(() at 1)`), where ADR 0045's table says
    "none"; the layout is the same, and `docs/reference.md` says "1, of
    size 0".
  - `tests/c_layout.rs` splits fields outside parentheses and maps an
    instance to its C union name (`Option(u8)` → `OptionU8`,
    `Result(u32, Mode)` → `ResultU32Mode`, `Option(())` →
    `OptionUnit`), so instances can be checked against C.

## 5. feat: the `?` operator
- Status: done
- Implements: ADR 0046, all sections.
- Changes:
  - `src/syntax/{token,lexer}.rs`: the `?` token.
  - `src/syntax/{ast,parser}.rs`: postfix `?` in the postfix loop, next
    to indexing and field access.
  - `src/hir/{mod,lower}.rs`: an `ExprKind` for `e?`;
    `resolve::return-in-comptime` when in compile-time code, with a
    message naming `?`.
  - `src/ty.rs`: the operand is checked without an expected type;
    `ty::try-operand` unless it is an `Option` or `Result` instance
    (`!` gives `!`, `Error` gives `Error`, silently); the function's
    return type checked as in ADR 0046 (`ty::try-return`, with the
    "never converted" help for a different `E`; `E` compared for
    identity, with no ADR 0024/0031 conversion; nothing when the return
    type or `E` is erroneous); the type is the `Some`/`Ok` payload
    type.
  - `src/mir/build.rs`: the operand into a temporary, a switch on its
    tag: the value case copies the payload into the result; the failure
    case builds `.None` or `.Err(x)` in the return place and returns;
    the default calls the panic function with the "enum value is no
    variant" cause, as a `match` without a catch-all does.
- Tests:
  - ui (parser) `parse_try.ers`: `f()?`, `a[i]?`, `s.f?`, `f()?.x`,
    `f()??`, `-f()?`, `*p?`, `match r { ... }?` at the start of a
    statement (rejected) and in parentheses, `x as T?` (rejected).
  - ui (resolve) `resolve_try_errors.ers`: `?` in a `comptime`
    expression, a `comptime` block, a constant's initializer and an
    array length.
  - ui (typeck) `typeck_try.ers` and `typeck_try_errors.ers`: the cases
    of ADR 0046's ui (typeck) list.
  - MIR snapshot `mir_try.ers` and LLVM IR snapshot `codegen_try.ers`:
    on an option and a result, the tag switch, the early return and the
    panic default, no range metadata on the tag load.
  - ui (eval) `eval_try.ers`: a function using `?` evaluated in a
    `comptime` block in both outcomes; `eval_try_no_variant.ers`: a tag
    that is no variant reaching `?` (`eval::panic` with the cause).
  - e2e `try_operator.ers`: an error propagated through three calls;
    `f(a()?, b())` not calling `b` when `a` fails, observed through a
    counter; `?` on options. e2e `try_no_variant.ers`: a tag that is no
    variant reaching `?` panics (exit code 1).
  - Differential (`comptime_differential.ers`): functions using `?` on
    options and results, at compile time and at run time.
- Decisions (taken while implementing, commit 50de243):
  - An operand whose type is erroneous through its layout, such as an
    `Option(Node)` with `Node` in a containment cycle, gives `e?` the
    type `{error}` and reports nothing, as `match` does for such a
    scrutinee. ADR 0046 only speaks of "an erroneous operand".
  - MIR: the operand goes into a temporary unless it already is one
    (the rule `match_` uses; an unnamed temporary or constant-data local
    is never written again). The failure case writes the `Err` payload
    and the tag directly into the return place, then returns.
  - Two helpers: `Queries::builtin_enum` tells whether an enum is an
    `Option` or `Result` instance, and `BuiltinEnum::try_variants` gives
    the indices of the value and failure variants. The indices are
    written out and must match the order of `BuiltinEnum::variants()`.
  - Wording: `resolve::return-in-comptime` for `?` says "`?` cannot
    leave code that runs at compile time"; the three `ty::try-return`
    messages, with the help "errors are never converted (ADR 0008)" for
    a different `E`, and the `ty::try-operand` message are in the
    snapshots `typeck_try_errors` and `resolve_try_errors`. For a
    function returning `()`, `ty::try-return` is labelled at the
    function's name.
  - The parser test is split into `parse_try.ers` (accepted, AST dump)
    and `parse_try_errors.ers` (rejected), since errors replace the AST
    dump. A lexer unit test for `?` was added.

## 6. test(e2e): a number parser returning `Result`
- Status: done
- Implements: the M2.5 milestone program.
- Changes: `tests/e2e/number_parser.ers`.
- Tests: the program declares `enum ParseError: u8 { Empty = 0,
  BadDigit(u8) = 1, Overflow = 2 }`; `digit(c: u8) -> Result(u32,
  ParseError)`; `checked_mul10` and `checked_add` returning
  `Option(u32)`, combined with `?` in a function returning
  `Option(u32)`; `parse(s: *const [u8]) -> Result(u32, ParseError)`
  using `?` on `digit` and turning a `.None` into `.Err(.Overflow)`

  `b"42"`, `b"4294967295"`, `b"4294967296"`, `b""`, `b"12a"`) and
  prints each result or error, the bad byte included; a `comptime`
  block asserts the same results for the same inputs. Run at both
  optimization levels (by the e2e harness).
- Decisions (taken while implementing, commit c83205b):
  - The six inputs above overflow only in `checked_add` (429496729 × 10
    still fits), so the early return of `?` on `checked_mul10` was never
    taken: an off-by-one in its bound went unnoticed. A seventh input,
    `b"4294967300"`, was added (after review). Its prefix 429496730 is
    the one value that catches that off-by-one; `b"9999999999"` or
    `b"42949672950"` would not, being above both bounds.
  - The loop runs to `len(&raw const INPUTS)`, not a written count.

## 7. docs: document `Option`, `Result`, `.V` and `?`, and mark M2.5 done

## Follow-up: compiler panic on a type with a failed array length

Found by the final review of M2.5; it predates M2.5.

A function evaluated at compile time taking `*const Broken`, with
`struct Broken { x: [u8; N] }` and `N` failing to evaluate, made the
compiler panic in `mir_ty`. `struct_layout` and `enum_layout` lay out a
field whose length failed as `{error}` (size 0), so the struct kept a
layout, and `lacks_layout` looked only at an array's element, never its
length; `needs_missing_layout` then let MIR building reach it. Every
shape reaching such a struct (by value, behind pointers, arrays,
slices, fields, payloads, `Option`; at compile time and at run time)
panicked.

- Decisions (taken while fixing, commit a47eb48):
  - The fix is in `lacks_layout` (the array arm also checks the
    length), not in the layouts. A failed length is treated as a field
    of type `!` already is (ADR 0034): the struct keeps its size-0
    field layout and `lacks_layout` finds the error through the fields.
    Taking the layout away would take it from every containing type and
    change what `layout_of` and `size_of` give.
  - The arm calls `array_len` (cached) rather than `normalize` on the
    whole type: same result, but `normalize` leaks a box for every type
    not already normalized, and HIR field types never are.
  - The element is checked before the length, stopping at the first
    error, as `normalize` does. `check_all` still evaluates and reports
    every length, so no diagnostic is lost.
  - Nothing new is reported: a body using such a type is silently not
    lowered, and the program shows one error, at the length. A constant
    such as `size_of(*const Broken)` or `size_of(Broken)` now silently
    gets no value (before, it came from the size-0 layout), as a
    pointer to a struct without a layout already did.
  - Type checking follows through `is_erroneous`, deliberately: an enum
    reaching a failed length is erroneous (ADR 0034/0039, as for a `!`
    payload), so a `match` on it is not checked for coverage, its
    payload patterns are not checked, and `?` with such an operand or
    return type checks nothing more.
  - Two tests: `mir_failed_length_inside.ers` (lowering, where the panic
    was) and `typeck_failed_length_inside.ers` (type checking staying
    silent; it reports four more errors without the fix).
