# Plan: M4.4 External interrupts

ADRs: 0089, 0090, 0091, 0092
Base: 22b91133bdd46c2c0c3115b5b9261fe301f8b357
Program on QEMU: a UART driven by its interrupt on both targets: the CMSDK UART0's
transmit line on `mps2-an385`, at `Interrupt::Uart0Tx` (step 6); the 16550 through
the PLIC on `virt`, dispatched from `Vector::MachineExternal` (step 6).
Out of scope:
- checking the rule for shared statics, and reading a vector's kind: M4.5;
- priorities and nesting (ADR 0078): not scheduled;
- reception on thumbv7m end to end (ADR 0092): the CMSDK UART has no loopback, and
  a byte through QEMU's standard input did not reach it on Windows; left until a
  program needs it;
- a PLIC or dispatch in `core`: never, by ADR 0091; a board's module may have one.

Before step 1: the `docs(adr)` commit that accepts these ADRs also sets the status
lines of the ADRs they amend, in their files and in the index
(`docs/adr/README.md`):
- 0057: adds `0090 (the origin of the code's region also suits the table of the
  program's list)`; index adds `0090`;
- 0070: adds `amended by 0092 (`svd::missing-element` covers an `interrupt`; two more
  kept modules)`; index adds `amended by 0092`;
- 0071: `Accepted; amended by 0092 (the generated file ends with the list)`; index
  `Accepted, amended by 0092`;
- 0072: adds `amended by 0092 (`interrupt` is read)`; index adds `amended by 0092`;
- 0074: adds `0090 (`code_align` is the minimum; a program with a list may need
  more)`; index adds `0090`;
- 0083: adds `0090 (`_start` is further from the origin with a list)`; index adds
  `0090`;
- 0084: `Accepted; amended by 0089 (the path after `at` may name a variant of the
  chip's list; the meaning of `resolve::not-a-vector`)`; index `Accepted, amended by
  0089`;
- 0085: `Accepted; amended by 0090 (the table's length with a list; default handlers
  for lines, and for words with no variant, on thumbv7m)`; index `Accepted, amended by
  0090`.
The same commit holds the roadmap's edit written while planning: M4.4's pending
decisions settled.

Order: the list exists (1) before a handler can name it (2), and a handler can name
it before the table gives it a word (3). The table's programs need `nvic_*` to raise
a line, so those end-to-end tests come with `nvic_*` (4), and step 3's tests are ui
and ELF. The generator (5) comes after the attribute it writes. The milestone (6)
needs all of them. Every existing test passes after every step.

In every step: if the count of `unreachable!` or `expect` for a file in
`tests/architecture.rs` rises, say why in `Decisions`, and only then raise it.
A program without `#[interrupts]` compiles to the same bytes as before steps 1 to 3 and
5; only step 4 changes the thumbv7m image, by adding `core`'s functions.

  - `find_handlers` takes all the enums and keys by `(EnumId, variant)`; the message of
    `resolve::duplicate-vector` is `EnumDef::variant_path`, which for `Vector` is the text it
    had (`core::arch::Vector::SysTick`), so its snapshots are unchanged.
  - `resolve::not-a-vector`: the title stays (`is not a variant of core::arch::Vector`), as
    do the labels; only the help gains ", or, where the chip's interrupts are vectors, with a
    variant of the enum that has `#[interrupts]` (ADR 0084, 0089)". The one existing snapshot
    with it, `interrupt_resolve_errors`, changed by that text alone (read).
  - `ty::interrupt-not-a-vector` is `Checker::interrupt_vector`, called by `fn_` before
    `interrupt_return`: it labels the path after `at` ("an interrupt of the chip, not a
    vector") and its help says the interrupt arrives at `Vector::MachineExternal`. A handler
    with that error and a wrong return type reports both (two mistakes), as
    `chip_interrupts_handlers.ers` shows.
  - `ty::interrupt-return`: `diverges` is looked up only if `is_core_vector`; the others fall
    through to the rule of a plain handler.
  - `mir::Handler` keeps `vector: String`, now the dump text (`vector_path`), and gains
    `word: u32`; `make_vector_table` finds a handler by `h.word == v.word`. The word is the
    target's own for a `Vector` variant and `first_word + value` for a list's, read from
    `Queries::discriminant`. `handlers()` is now `&mut self` for that. Nothing in codegen reads
    `vector`, so `keep_symbols` stayed as it was. The unit test of `mir` only got a `word`.
  - `PANICS` of `src/query.rs` 27 -> 28: one `unreachable!` in `handlers()`, when a handler has
    no word. No user input reaches it: `make_vector_table` runs only with no error reported,
    and a handler on a target where the chip's interrupts are no vectors is
    `ty::interrupt-not-a-vector`, a value of 496 or more is `ty::interrupt-number`, a failed

    skipped for a list that failed `ty::interrupts-enum` (a `u8` or `u64` list, or one with

    gets. Both are errors all the same: a handler at a list that fails `ty::interrupts-enum`
    is rejected because that is reported, and a handler at a further list's variant is
    rejected through `resolve::duplicate-interrupts`. The `value as u32` in `handlers()` is
    safe (no truncation, no `first_word + value` past the table) only because of these.
  - Tests: the shorthand and the integer are parse errors (`interrupt_parse_errors.ers`), so
    `chip_interrupts_handlers_resolve_errors_thumbv7m.ers` does not hold them (they would have

  - e2e: step 4, which raises lines.
- Decisions:
  - Two helpers in `src/query/hardware.rs`, where the other checks of the list are:
    `chip_lines` (the list's variants as `(value, name)`) and `chip_table_words` (`first_word`
    plus the largest value plus 1). Both are `None` without a list, on a target whose
    interrupts are no vectors, and when the list failed one of `check_chip_interrupts`'s
    rules (not `u32`, a payload, a value that failed or is 496 or more): the values are not
    the chip's numbers, and an error is reported already. `make_vector_table` and the
    alignment check use the same two, so the table and the check cannot disagree on the length.
    A list with no variant has no largest value: `chip_table_words` is `None` and the table
    stays 16 words (the ADR says `16 + m + 1` for a largest value `m`, and says nothing of an
    empty list).
  - `make_vector_table` loops over `chip_table_words().unwrap_or(table_words)` words. A word
    `>= first_word` is a line: the list's variant of value `word - first_word`, or a hole
    (`Some(None)` in the `line` of the match). A handler is found by `h.word == word`, not by
    the vector's word: the same for a `Vector` variant, and the only way for a list's. The arm
    `(Armv7m, _, None, None) => Reserved` holds for words below 16 only, since `line` is `Some`
    from the first line on. Names: a `Vector` keeps `__erebos_unhandled_<name>`, a line is
    `__erebos_unhandled_irq_<variant>` with the bare variant as message, a hole shares
    `__erebos_unhandled_other` with `unknown`, as riscv32 does for a cause with no variant.
    Without the parameter the one `__erebos_unhandled` serves all, unchanged.
  - `ty::misaligned-code`: the required alignment is `max(code_align, next_power_of_two(4 *
    words))`, used only when it is above `code_align` (that is, when the list is why), so a
    program with no list, and a list of 15 or less, produce the text they had; no existing
    snapshot changed. When the list is why, the label says "not a multiple of {required}" and
    the help is another text: it names the list, gives its words and bytes and the required
    number. A misaligned origin that is also not a multiple of 128 is reported once, with the
    larger number. The check is skipped when `chip_table_words` is `None`, which covers the ADR's
    "a value failed or is above the limit".
  - No test on riscv32 for the alignment: nothing changes there (`code_align` 4,
    `external_vectors` `None`), and the existing riscv32 snapshots of `interrupt_table*` are
    unchanged, which is the evidence for it.
  - `src/mir/mod.rs` and `src/link.rs`: comments only, as the plan says. `src/codegen/vectors.rs`
    needed nothing, nor did `keep_symbols`: the table is written from `Mir`, which has the words.
  - Tests, ui. `interrupt_table_chip_thumbv7m.ers` and `_noparam_` use one list in a module
    (`Uart = 0`, `SysTick = 1`, `other = 2`, `Timer = 4`): a handler at the first, one `#[export]`
    in a module at the last, a hole at 3, and no handler for `Vector::SysTick`, so that
    `__erebos_unhandled_SysTick` and `__erebos_unhandled_irq_SysTick`, and
    `__erebos_unhandled_other` (the hole) and `__erebos_unhandled_irq_other`, are in one dump.
    `chip_interrupts_no_handler_thumbv7m.ers` has a hole too (`Timer = 40`) and a panic
    function with the parameter, whose defaults would otherwise show.
  - Tests, alignment: one file per case, `chip_interrupts_aligned_{15,16,495}_thumbv7m.ers` and
    `chip_interrupts_misaligned_{16,495}_thumbv7m.ers`, named by the largest value, each with a
    list of two variants (`First = 0` and the largest) and the origin of the ADR's table
    (128, 256, 2048 accepted; 128 for 16 and 1024 for 495 rejected). They are `// emit:
    typeck`, so that an accepted case shows no error and the memory block in the dump.
    `chip_interrupts_misaligned_skipped_thumbv7m.ers` (a list ending at 496, at origin 0x400)
    shows that only `ty::interrupt-number` is reported then, which the ADR asks and the plan did
    not list.
  - Tests, ELF: `thumbv7m_vector_table_with_a_list` is a list of 0, 1, 2, 4 and 40 (57 words, so
    `_start` is at origin plus 228, not a power of two or a round number) at `0x0800_0000`, with a

  - What QEMU does, which shaped the programs: the CMSDK UART and the 16550 both send a byte
    on the write itself (the host character device takes it at once), so the transmit
    interrupt is raised right after the write and the handler runs again at the next
    instruction boundary with interrupts on. A queue therefore drains inside one trap (the
    tail-chain on thumbv7m, the `claim` loop on riscv32), and the entry function resumes only
    when it is empty. The programs do not rely on that: they wait in `critical` with
    `wait_for_interrupt` on the state they need (`BUSY`, `TAIL`, `HEAD`).
  - "Until the queue is empty" is, in both milestone programs, until the queue is empty and
    `BUSY` is false: `BUSY` is a byte in the transmitter whose interrupt has not been served. The
    ADR's wording would let the entry function exit as soon as the handler wrote the last byte;
    waiting for the interrupt that follows that byte is what shows the byte left. The exit
    checks that `SENT` is 21, the length of the message, with exit code 2 on a mismatch. What
    that catches differs by target. On thumbv7m `SENT` counts handler runs, one per byte, so a
    lost or extra interrupt gives exit code 2 (a lost final interrupt would instead leave
    `BUSY` true and hang, a harness timeout). On riscv32 `SENT` counts the writes to `THR`, so
    it catches a lost or extra byte; a doubled interrupt is harmless there (cause 2, `BUSY`
    false, `THRI` cleared again) and is not caught, and a lost final interrupt leaves `BUSY`
    true with the entry function in `wait_for_interrupt`, so the failure is a harness
    timeout, not exit code 2.
  - The message is `uart tx by interrupt\n` (21 bytes) in a ring of 16 slots, in both programs: it
    does not fit, so `send` takes the ring's room inside one `critical`, starts the
    transmitter, and waits with `wait_for_interrupt` for the handler to make room (the
    interrupt runs when the block ends, and `send` loops), and the indices pass the ring's end
    (`HEAD` reaches 21, the slot 5). The ring's `HEAD` and `TAIL` count bytes and the slot is
    the count modulo 16, so full is `HEAD - TAIL == 16` and empty `HEAD == TAIL`, with no
    spare slot. The statics are `usize`, `u8` arrays and a `bool`, written only in `critical` or
    in the handler (the rule for shared statics is M4.5's).

    the line is enabled (QEMU wants the divisor before the transmitter, as `board::putc` does),

    the first byte inside `critical`. The handler reads `IPSR` (`16 + 1`) and
