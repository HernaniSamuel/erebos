# Plan: M4.3 Handlers and vector tables

ADRs: 0084, 0085, 0086, 0087
Base: acd35faead583577daa36b91576a0c025449858a
Program on QEMU: a timer interrupt counting ticks shared with the entry
function, read in a `critical` block, with the entry function waiting in
`wait_for_interrupt` (SysTick on `mps2-an385`, step 5; the CLINT on `virt`,
step 6); a fault reaching the panic function on both targets (`udf` as
`HardFault`, step 5; an illegal instruction as `IllegalInstruction`, step 6).
Out of scope:
- the chip's interrupts, the length of the thumbv7m table beyond the system
  exceptions, `code_align`, and enabling interrupts in the NVIC and the PLIC:
  M4.4;
- checking the rule for shared statics, and M4.5's diagnostics: M4.5;
- priorities and nesting (ADR 0078); handlers with a frame, returning from
  faults: deferred ideas of the roadmap.

Before step 1: the `docs(adr)` commit that accepts these ADRs also sets the
status lines of the ADRs they amend, in their files and in the index
(`docs/adr/README.md`):
- 0022: adds `0087 (`#[align(N)]` on functions)`; index adds `0087`;
- 0030: adds `0085 (`_start` sets the trap vector on riscv32), 0086 (`_start`
  masks interrupts first)`; index adds `0085, 0086`;
- 0052: adds `0084 (the compiler knows `core::arch::Vector`), 0086 (and
  `__critical_enter` and `__critical_exit`)`; index adds `0084, 0086`;
- 0053: adds `0085 (`PanicReason::UnhandledVector`, with a `PanicInfo` that
  locates nothing)`; index adds `0085`;
- 0074: adds `0085 (the rest of the table; a fault reaches the panic function;
  the table is not in the dump of a program without handlers)`; index adds
  `0085`;
- 0079: adds `0084 (`#[naked]` does not apply to a handler)`; index adds `0084`;
- 0083: `Accepted; amended by 0085 (the table has 16 words, `_start` at origin
  plus 64 on thumbv7m; `_start` sets `mtvec`; the table is not in the dump of a
  program without handlers), 0086 (`_start` masks interrupts first)`; index
  `Accepted, amended by 0085, 0086`.
The same commit holds the roadmap's edits written while planning: the M4.3
pending decisions settled and the deferred idea of handlers with a frame.

Order: `#[align]` (1) comes before the trap entry that uses it (6). What
`critical` and the waits need of `core` (2) comes before `critical` (3), and
every test of `critical` that does not need a handler comes with it; the tests
that need a timer come with steps 5 and 6. Handlers are declared (4) before
the tables make them run (5, 6). thumbv7m comes first (5) because the table
already exists there. Every existing test passes after every step.

In every step: if the count of `unreachable!` or `expect` for a file in
`tests/architecture.rs` rises, say why in `Decisions`, and only then raise it.
The timer programs of steps 5 and 6 declare the registers they use (SysTick,
`ICSR`, the CLINT) themselves, as each names one target; the boards keep what
ADR 0077 lists.

## 1. feat: `#[align(N)]` on functions
- Status: done
- Implements: ADR 0087.
- Changes:
  - `src/hir/lower/item.rs`: function attributes take `align`, at most once,
    with `array_len` as structs do; `misplaced_attr`'s text for `align` names
    functions; `extern fn` rejects it.
  - `src/hir/mod.rs`: `FnDef` gains `align`.
  - `src/query.rs`: the value is checked with `checked_align`, natural
    alignment 1.
  - `src/mir/mod.rs`, `src/mir/build*`: `Body` gains `align: Option<u64>`, in
    the dump.
  - `src/codegen/mod.rs`: `set_alignment` on the LLVM function.
- Tests:
  - ui: per ADR 0087, in `align_fn.ers` (`// emit: llvm-ir`),
    `align_fn_thumbv7m.ers` and `align_fn_errors.ers`; existing snapshots of
    `resolve::misplaced-attribute` for `#[align]` show the new text.
  - ELF: `function_alignment` in `tests/elf.rs`, on both targets at both
    levels: an `#[export]` function and a naked function with `#[align(64)]`
    are multiples of 64 (minus the Thumb bit); on riscv32 two builds of a
    `#[align(4)]` naked `pad` holding only `c.ret`, then a naked `next`. In the
    control build `next` has no attribute and is at 2 mod 4, which fails if the
    functions change order; in the other, `next` has `#[align(4)]` and is at 0
    mod 4. Proves the attribute moves the symbol where a template's `.p2align`
    cannot.
  - e2e: `align_fn.ers`, both targets: calls an aligned function, exit 0.
- Decisions:
  - The HIR struct is `hir::Fn`, not `FnDef` as the plan says; it gains
    `align: Option<(ArrayLen, Span)>`, as `StaticDef` has. Every `Fn` built for
    a body run at compile time has `align: None`.
  - `fn_attrs` in `src/hir/lower/item.rs` reads `align` inline, as
    `static_attrs` does (argument through `array_len`, `resolve::attribute-argument`
    without one, `resolve::duplicate-attribute` for the second), and returns it
    as a third value. An `extern fn` goes through `no_attrs` as before, so it
    gets `resolve::misplaced-attribute` with no code of its own. The entry and
    the panic function take `#[align]`, as the ADR says.
  - The message of `resolve::misplaced-attribute` for `#[align]` now reads
    "applies only to structs, statics and functions with a body" (the plan and
    ADR call it the text and the help; there is no separate help for `align`).
    The help of `resolve::unknown-attribute` also lists `#[align(N)]` on
    functions (ADR 0087), since it listed every attribute and would be wrong
    otherwise; its snapshots change with it.
  - `Queries::fn_align(FnId)` in `src/query.rs` (cached in `fn_aligns`, as
    `static_align` is) calls `checked_align` with natural alignment 1 and
    subject "a function"; invalid values are reported once and leave the
    function without alignment, as a struct's invalid `#[align]` leaves its
    natural one. `check_all` calls it for every function, so an alignment on a
    function that is never built, or run only at compile time, is still
    checked (the ADR says the attribute has no effect there, "and no
    diagnostic" for the attribute itself being valid). Its value comes from a
    `Comptime::Value` body, which `check_all` already evaluates.
  - `mir::build::finish` sets `Body::align` from `fn_align`, except for bodies
    run at compile time (`comptime`) and `extern` ones, which are never
    emitted. `leave_out` clears it where it turns a body into a declaration.
  - The MIR dump writes `#[align(N)]` on the line before the function's header,
    as the source has it, and nothing when there is no attribute, so every
    existing MIR snapshot stays as it was; `#[align(1)]` is shown, since it was
    written. The typeck dump of functions is left as it is: it shows no
    attributes (`#[export]` is not shown either).
  - Codegen: `inkwell` has no `set_alignment` on `FunctionValue`, so it is set
    through `as_global_value()`, which calls `LLVMSetAlignment` and sets the
    function's `align` in the IR. The `expect("alignments are small")` is the
    one of the statics' alignments, and raises `PANICS` of
    `src/codegen/mod.rs` from 69 to 70: `checked_align` bounds the value by
    `MAX_ALIGN`, 2^31, so it fits `u32` whatever the program says.
  - ADR 0087's "above the limit" case has no test: on both targets `MAX_ALIGN`
    is 2^31, the largest power of two a `usize` holds, and a larger literal is
    `ty::mismatched-types` (too large for `usize`) before it is an alignment.
    The branch is the shared `checked_align`'s, tested for structs and
    statics.
  - ui tests: the plan's `align_fn.ers`, `align_fn_thumbv7m.ers` and
    `align_fn_errors.ers`, plus `align_fn_invalid.ers` (the values 3, 0, `1 / 0`
    and `true`, and a valid one on a function run at compile time), because
    resolution errors stop the pipeline before the typeck ones, so they cannot
    share a file with `extern fn`, the duplicate and `#[packed]`; and
    `align_fn_mir.ers` for the MIR dump. `align_fn.ers` has the entry and panic
    functions aligned, a constant expression, `align(1)`, an `#[export]` and a
    naked function; `-O` shows the attribute kept on all of them.
  - ELF tests: `function_alignment` (both targets, both levels: an
    `#[export]` and a naked function at 64, the Thumb bit masked) and
    `function_alignment_moves_the_symbol` (riscv32, control and aligned build,
    both levels). The naked `pad` is `ret`, which the assembler compresses to
    two bytes (there is no `c.ret` mnemonic), and the control asserts
    `next == pad + 2` as well as `next % 4 == 2`, so a change of order fails
    it. Both tests fail with the `set_alignment` call removed (checked).
  - e2e `align_fn.ers` runs on both targets (no `// targets:`), with aligned
    plain, exported and `align(1)` functions and an aligned panic function; the
    alignment itself is the ELF test's, since a program cannot read its own
    function's address.
  - `src/query.rs` and `src/mir/build.rs` were edited with CRLF line endings by
    mistake and put back to LF before the end, as `.gitattributes` has it.

    `_start`, and its comment's list of steps; `enable_interrupts`,

  - On thumbv7m a call of `interrupts_enabled` in a handler is tested in step 5,

  - `call_of` in `tests/e2e.rs` learned `pub fn name() -> type`: the call is

    0037), so `interrupts_enabled` is built at both levels on both targets;
    `portable_items_are_checked_against_the_files` covers the new form and what

    `interrupts_masked_restart_riscv32.ers` and

    (`board::SCRATCH`, volatile), as `startup_bss.ers` marks its first run,
    rather than in a `static mut`: `_start` zeroes `.bss` and copies `.data`
    again, so a static would read as at the first run. The first run enables
    interrupts, checks them enabled, jumps (`tail _start`; `movw`/`movt` and
    `bx` on thumbv7m); the second finds them masked.

- Status: done

  lowers" and "Syntax and types".
- Changes:
  - `src/syntax/token.rs`: the keyword `critical`. `src/svd/names.rs` renames
    it through the table of keywords (ADR 0071), with no code.
  - `src/syntax/ast.rs`, `src/syntax/parser.rs`: `ExprKind::Critical(Block)`,
    wherever a block expression is, with the statement rule of `loop` and
    `if`.
  - `src/hir/mod.rs`, `src/hir/lower/expr.rs`: `hir::ExprKind::Critical`.
    `src/hir/lower.rs`: `Hir` gains `critical_enter` and `critical_exit`,
    found as `reset` is (no visibility check).
  - `src/ty.rs`: the block's type, as a block.
  - `src/mir/mod.rs`: `Statement::CriticalEnter(Local)`,
    `Statement::CriticalExit(Local)`, in the dump and in `leave_out`, which
    keeps the two bodies as declarations when a kept body has one; `Mir` gains
    their ids.
  - `src/mir/build.rs`: a stack of the blocks being built; `LoopScope` records
    its depth; `break`, `continue`, `return` and `try_` emit exits, innermost
    first, after their value and before their jump.
  - `src/eval.rs`: both statements do nothing.
  - `src/codegen/mod.rs`: each is a call, storing or passing the local.
  - `rt/arch/riscv32.ers`, `rt/arch/armv7m.ers`: `__critical_enter`,
    `__critical_exit`, with ADR 0086's text.
- Tests:
  - ui: per ADR 0086, in `critical_parse.ers` (`// emit: ast`),
    `critical_types.ers`, `critical_mir.ers` (`// emit: mir`),
    `critical_codegen.ers`, `critical_codegen_thumbv7m.ers`, and `critical` as a
    name.
  - Compile time: `critical_comptime.ers` (`// emit: typeck`, or a program in
    e2e that prints the constants).
  - e2e: `critical_exits.ers`, both targets, both levels, through
    `interrupts_enabled`: each exit, nested blocks, a block entered masked, the
    block's value.
  - Generated programs: `Feature::Critical` in `tests/common/generator.rs`,
    wrapping a generated block; both oracles agree (ADR 0068).
- Decisions:
  - Parser: `critical` is parsed in `primary`, next to `loop`, and listed in
    `at_block_like` and `ExprKind::is_block_like`, so a statement that starts
    with it ends with its block (`critical { X } + 1` as a statement is
    `parser::unexpected-token`, as `if c {} - 1` is) and needs no `;`. It takes
    `self.block()`, which clears `no_struct`, so `while !critical { DONE } {}`
    parses with the block as the operand of `!`. The keyword is in
    `TokenKind::keyword`, which `src/svd/names.rs` already reads, so it renames
    `CRITICAL` to `critical_` with no change there; a line in its unit test
    `names_with_a_meaning_get_an_underscore` says so.
  - HIR: `ExprKind::Critical(Block)` is its own variant (not a flag on `Block`),
    so MIR building and the type checker see it; `Expr::walk` visits its block.
    `Hir::critical_enter` and `critical_exit` are found by `arch_fn` in
    `hir::lower`, the closure that now also finds `_start`: the three are looked
    up in `core::arch`'s namespace, private, with an `unreachable!` each that
    the file defines them (the count of `src/hir/lower.rs` is unchanged: the
    `_start` one became the closure's). The mock `core` of the unit test
    `crate_in_core_is_core` gained the two functions.
  - Type checking: `Critical` shares the arms of `Block` in `check` (the
    mismatch report on the block, the tail's type passed as expected) and in
    `expr_kind`, so its type is the block's and a statement without `;` must be
    `()` or `!`. The typeck dump labels it `critical`.
  - MIR: `Statement::CriticalEnter(Local)` and `CriticalExit(Local)` dump as
    `critical_enter _n` and `critical_exit _n`. `Mir::critical_enter` and
    `critical_exit` are `Option<BodyId>`, `Some` for a full program and `None`
    after `leave_out` unless a kept body has the matching statement, in which
    case the body stays as a declaration (the dump shows `extern fn
    core.arch.__critical_enter() -> u32;`). Each is kept on its own, so a body
    with only `critical { loop {} }` declares `__critical_enter` alone. A
    program without `critical` has neither in a dump, so no existing snapshot
    changed because of them.
  - MIR builder: `Builder::criticals` is the stack of the hidden `u32` locals,
    and `LoopScope::criticals` the stack's depth where the loop started. A
    `break` or `continue` leaves the blocks from that depth on; `return` and `?`
    leave all of them, in each case through `leave_criticals`, innermost first,
    after the value is stored (`_0 = ...`, the loop's result place) and before
    the jump. The `?` failure path emits its exits after it writes the return
    place. The panic call of a check emits none. The block's own value needs no
    temporary: a read of a static is already a temporary made inside the
    block, and a read of a local is no one else's; the value is read after
    `critical_exit` in `end()` of `critical_mir.ers` and is `_3`, assigned
    before it. An unreachable end has no exit because `push` emits nothing
    without a current block.
  - Evaluator: both statements are `Ok(())`; the hidden local is never read
    there. Checked with `critical_comptime.ers`, whose `comptime { assert(...) }`
    block fails when a value is wrong (tried with two values changed).
  - Codegen: each statement is the existing `FnCodegen::call` on the body from
    `Mir::critical_enter` or `critical_exit` (the local as the result, or as
    the one argument), through `critical_callee`. `critical_callee` has one
    `expect`, which raises `PANICS` of `src/codegen/mod.rs` from 70 to 71: a
    program is built from a `Mir` that either holds both bodies (a full
    build) or came from `leave_out`, which keeps the matching body whenever a
    kept body has the statement, so no input reaches it.
  - `core::arch`: `__critical_enter` and `__critical_exit` are in both files
    with the text of ADR 0086 and a comment on what each returns (8 or 0 on
    riscv32, `PRIMASK` on thumbv7m). Being `__`-named items of `core`, no
    program can name them. They are emitted in every program, as the other
    functions of `core` are; no ELF test changed.
  - ui tests: `critical_parse.ers` (statement, `let`, `while` condition,
    nested, operand, tail), `critical_parse_errors.ers` (a statement that
    starts with a `critical` block cannot go on with `+`; `critical;`),
    `critical_name.ers` (`fn`, field and `let` named `critical`),
    `critical_types.ers` (value, aggregate, `()`, `!`, in a loop, as a
    condition), `critical_types_errors.ers` (the four mismatches),
    `critical_mir.ers` (end, `break`/`continue` to the loop outside, `return`,
    `?`, a jump crossing two blocks, a `break` that crosses only the blocks
    inside its loop, a diverging block with a check in it),
    `critical_comptime.ers`, `critical_codegen.ers` and
    `critical_codegen_thumbv7m.ers` (`// opt: both`: the calls stay in order
    around the load at `-O`). `critical_parse.ers` could not have the plan's
    `critical { TICKS } + ...` as a statement, which is the rule, so that case
    is the error test's. The comptime test is `// emit: typeck` with its own
    `comptime { assert(...) }` on each result, rather than an e2e program that
    prints the constants.
  - Snapshots of `resolve_bit_struct`, `resolve_field_modes`, `resolve_memory`,
    `resolve_peripheral` and `resolve_register_arrays` changed with no change
    in what they show: the ids of `core`'s items shift by the two new
    functions (checked: only numbers differ). Accepted by moving the `.snap.new`
    over the `.snap` without its `assertion_line`.
  - e2e `critical_exits.ers` (no `// targets:`, so both targets at both
    levels): a numbered exit code for each check. It enters a block masked
    before `enable_interrupts`, then covers the end of a block with its value,

## 4. feat: `interrupt fn ... at` declares a handler
- Status: done
- Implements: ADR 0084.
- Changes:
  - `rt/arch/riscv32.ers`, `rt/arch/armv7m.ers`: `pub enum Vector: u32`, not in
    the `// portable:` list; a comment on what its value is.
  - `src/target.rs`: per target, the list of vectors: variant name, value, word
    in the table, kind, whether it must diverge.
  - `src/syntax/token.rs`, `src/syntax/ast.rs`, `src/syntax/parser.rs`: the
    keyword `interrupt`, `FnKind::Interrupt` with its path, `at` as a word after
    the signature.
  - `src/hir/lower/item.rs`, `src/hir/lower.rs`, `src/hir/lower/expr.rs`: the
    path resolved after `use`s are, `resolve::not-a-vector`,
    `resolve::duplicate-vector` (scanning functions by id),
    `resolve::call-interrupt`, `resolve::misplaced-attribute` for `#[naked]`;
    `Hir` gains the id of `core::arch::Vector` and `handlers`.
  - `src/query.rs`: handlers are roots, as the entry and the panic function.
  - `src/ty.rs`: `ty::interrupt-params`, `ty::interrupt-return`.
  - `src/mir/mod.rs`: `Mir` gains `handlers` (vector and body), in the dump;
    `src/codegen/asm.rs`: `keep_symbols` keeps them.
- Tests:
  - ui: per ADR 0084, each case its list names: `interrupt_parse.ers`,
    `interrupt_errors.ers`, `interrupt_errors_thumbv7m.ers`, one `// target:` file
    with a variant of the other target, `interrupt_mir.ers` and a handler's symbol
    in LLVM IR.
  - Unit: each file's `Vector` agrees with `src/target.rs`, in names, values and
    words.
  - The test of keywords in `erebos svd`, if it lists them.
- Decisions:
  - AST: `ast::FnKind::Interrupt(Path)` holds the path after `at`, as the plan
    says, so `FnKind` is no longer `Copy` or `Eq` (callers pass `&decl.kind`
    and `match`). A field `at` on `FnDecl` would have added `at: None` to
    every AST snapshot of the suite (25 files); the variant changes none.
  - Parser: `interrupt` is a keyword (`TokenKind::Interrupt`, listed in
    `item()` and `describe`); `fn_decl` takes it as a kind, then after the
    signature requires the word `at` and a `path()`. Without `at` the error is
    `parser::unexpected-token` "expected `at`" with a help showing the form.
    `at` after any other function (plain, `entry`, `panic`) is reported as
    "expected `{`" with a help that only an `interrupt fn` takes `at`; the ADR
    leaves the text to the parser, and the bare "found identifier" says nothing
    about why. `extern interrupt fn` is "expected `fn`, found `interrupt`",
    with no code of its own, as `extern entry fn` is. A shorthand (`.SysTick`)
    and an integer after `at` fail in `path()` as "expected identifier".
  - `recover_to_item` treats `interrupt` as the start of an item only when
    `fn` follows, unlike `entry` and `panic`: otherwise a field or a `let`
    named `interrupt` (an error already reported) made the recovery stop on
    it and report a second error ("expected `fn`, found `:`") at the same
    place. `interrupt_name.ers` shows one error for each name.
  - HIR: `FnKind::Interrupt(HandlerVector)` with the vector in the kind
    (`HandlerVector { variant, span }`: the index of the variant in
    `core::arch::Vector` and the span of the path), instead of a field on
    `hir::Fn`, which would have changed every HIR snapshot (`Fn` is shown by
    `Debug`, as `align` was in step 1). `Hir` gains `vector: EnumId` and
    `handlers: Vec<FnId>` (in id order), and `Hir::vector_name` gives the
    variant's name. Neither is in the `--emit=hir` dump struct: each
    function's kind shows its vector, and the dump's list of fields would
    otherwise grow by a line in every HIR snapshot.
  - Resolution is in `Lowerer::handler_vector` (`src/hir/lower/item.rs`), called
    by `fn_decl` right after the attributes, so its errors come before the
    ones of the signature and the body. It uses `lookup_path`, so `use`, `as`,
    `crate::`, `super::` and visibility work as for any path. A variant of
    `Vector` is the vector; a variant of another enum, or an item (struct,
    function, constant, static, enum, module, peripheral), is

  - ADR 0088 asked step 6 to confirm what a second trap does on riscv32. Run by
    hand (QEMU 11.1): a panic function that faults enters the trap entry again on
    the same stack and reaches the panic function again; when it always faults, the
    program recurses until the harness's timeout (killed after 5 s in the check, no
    exit). The ADR's text is right. `fault_in_panic_riscv32.ers`, not in the plan,
    tests the first half: the panic function records that it ran in a `static mut`,
    faults with `unimp`, and prints `second` when it is entered again. The endless
    case has no test: `// takes-exceptions: yes` requires `// expect-exit:`, and a
    program that must run for ever is the one thing the header cannot say.
  - ADR 0088's test of the harness on riscv32: the two tests of `tests/e2e.rs`
    (`a_program_that_takes_exceptions_passes_only_with_the_header` and
    `a_guest_error_fails_a_program_that_takes_exceptions`) now loop over a program
    for each target instead of being thumbv7m's. On riscv32 the first uses an `ecall`
    whose `EnvironmentCall` handler prints and exits (an exception's handler never
    returns, so there is no `svc` equivalent): with the header it passes, without it
    it fails showing `riscv_cpu_do_interrupt`. The second writes 0x1234 to the test
    finisher, which `virt` logs as a guest error (`sifive_test_write: write: addr=0x0
    val=0x1234`), found by trying: a write to unassigned memory is a trap there, not
    a log line. The programs have distinct file names per test (`exceptions_<target>`,
    `guest_error_<target>`): `run` names its ELF after the file, so two tests writing
    the same name collided when they ran in parallel (found by running the suite).
  - e2e programs, all `// takes-exceptions: yes`, `// targets:
    riscv32imac-unknown-none-elf`, both levels. The CLINT's registers are declared
    in each program (the plan says so): `MTIME` at 0x0200_BFF8, `MTIMECMP` at
    0x0200_4000 and 0x0200_4004, as two words, with the high word kept at 0 (the
    time stays below 2^32 for the life of a program), and `mie.MTIE` (0x80) written
    with `asm("csrs mie, ...")`, since `core::arch` has no item for `mie` (the PLIC
    and the chip's interrupts are M4.4). A handler that must run once more re-arms
    with `MTIMECMP = MTIME + PERIOD`; the pending interrupt compares the time with
    it, so moving it clears the interrupt. The programs that wait with `wfi` re-arm
    in the handler too (`handler_registers`, `handler_stack`): a tick that came
    before the `wfi` would otherwise leave it waiting for ever, and the ARM ones
    have a periodic SysTick. `interrupt_clint`, `handler_in_module`, `critical_spin`
    and the others disable `MTIE` inside the `critical` block that reads the final
    count, as step 5's stop SysTick there; `interrupt_clint` waits with
    `wait_for_interrupt` in the block and the interrupt then runs at the block's exit
    (QEMU's `wfi` returns for a pending, enabled interrupt with `MIE` clear, as the
    ISA allows; the QEMU log shows `epc` just after the block).
  - `interrupt_clint.ers` (5 ticks, `interrupts_enabled` false in the handler),
    `fault_unhandled_riscv32.ers` (`unimp`, prints `vector not handled:
    IllegalInstruction at :0:0`), `fault_unhandled_noparam_riscv32.ers`,
    `fault_handler_riscv32.ers` (declared `IllegalInstruction`, finds `mcause` 2),
    `ecall_handler_riscv32.ers` (declared `EnvironmentCall` with `a7` set before the
    `ecall`: finds `mcause` 11 and `a7` as the caller left it),
    `handler_in_module_riscv32.ers` (three ticks, handler in `timer.machine`),
    `vector_unhandled_timer.ers` (the panic function finds `MachineTimer`, `mcause`
    0x80000007 and `MIE` clear), `vector_unhandled_unknown.ers` (`mie.SSIE` and
    `mip.SSIP` set by the program, cause 1: message `unknown`, `mcause` 0x80000001),
    `handler_registers_riscv32.ers`, `handler_stack_riscv32.ers` (`sp` at 0 modulo 16
    in the handler, a `u64`), `handler_check_riscv32.ers` (division by a zero read
    from RAM: the panic function finds `DivisionByZero` and `mcause` 0x80000007),
    `critical_spin_riscv32.ers`, `critical_race_riscv32.ers`.
  - `handler_registers_riscv32.ers`: the interrupted code sets every register but
    `zero` and `sp` (`ra`, `gp`, `tp`, `t0` to `t6`, `s0` to `s11`, `a0` to `a7`) to
    a distinct value, in one `asm` that first saves `gp`, `tp` and `s0` to `s11` in
    a 64-byte frame it makes and restores them at the end (as the thumbv7m one
    saves `r4` to `r11`); it waits with `wfi` and checks. `t0` is checked first by
    subtracting its own value and then serves as the scratch for the others. A
    difference reaches `unimp`, hence the panic function, which exits 1. The handler
    keeps ten values live across an `asm` that overwrites `ra`, `t0` to `t6` and `a0`
    to `a7` with -1 (`clobber_abi("C")`), so the compiler puts them in `s` registers
    (the disassembly at `-O` shows the saves of `s0` to `s11`), and the entry's code
    finds the `s` registers restored too. Checked to fail: with the `lw a3` of the
    trap entry removed the program exits 1 at both levels.
  - `critical_race_riscv32.ers`: `PERIOD` is 50 (5 microseconds), not the 200 first
    tried. With 200 about 25 ticks ran during the loop but only a few percent of
    them landed between the load and the store, so a version without `critical` lost
    a count in about half of the runs and the test proved little (QEMU takes the
    interrupt at the start of the next translated block, and with no CSR access in
    the loop the two blocks of an iteration are not equal in time). With 50 the
    version without `critical` lost counts in 30 of 30 runs at `-O0` and 29 of 30 at
    `-O`, and the real one was exact in 50 of 50 at each level. Both reads of the
    final check are in one block, which also disables `MTIE` first.
  - `critical_fault_riscv32.ers`, not in the plan as its own file: the plan lists
    "a `critical` block around a fault, reaching the panic function masked". The
    program enables interrupts, faults inside `critical`, and the panic function
    prints `mie 0 mpie 0`; `MPIE` holds what `MIE` was when the trap came, so it is
    0 only because the block cleared it (the same program without the block prints
    `mpie 1`: checked). The block's exit never runs; the panic function does not
    return.
  - Timer programs run many times by hand against the compiled ELF with `-d
    guest_errors`, as the harness does: 40 runs at each level for each of the eight
    timer programs and for `vector_unhandled_unknown` and `critical_fault`, with no
    failure; the two loudest (`critical_race`, `interrupt_clint`) 15 runs at each
    level for six copies at once, 12 QEMU processes in parallel, with no failure.
  - A handler named like a register (`sp`, `ra`, `t0`, `a0`, `x5`) assembles in
    `.word` and runs (checked by hand at both levels, one of them being the handler
    that served the fault); `riscv32_trap_table` has one named `sp`.
  - ui tests: `interrupt_table.ers` (panic function with the parameter, `// opt:
    both`: a handler in a module, an `#[export]` one, `__erebos_unhandled_<variant>`
    with their information and `__erebos_unhandled_other` with `unknown`),
    `interrupt_table_noparam.ers` (the single `__erebos_unhandled`, no information),
    and, not in the plan, `interrupt_table_all.ers` (a handler at each of the twelve
    variants: no per-variant default, only `other`, which a table of riscv32 always
    has). `interrupt_codegen.ers` now shows the table, as its thumbv7m twin does.
    The riscv32 snapshots of programs without handlers did not change: they had no
    `module asm`. Five snapshots that show ids of `core` items changed by the new
    function (`resolve_bit_struct`, `resolve_field_modes`, `resolve_memory`,
    `resolve_peripheral`, `resolve_register_arrays`: numbers only, checked), accepted
    by moving the `.snap.new` over the `.snap` without its `assertion_line`.
  - ELF: `riscv32_trap_table` (new, in `tests/elf.rs`) builds three programs at both
    levels (with handlers, with none and the parameter, with none without it) and
    checks that `__erebos_trap_table` is an object of 132 bytes, 4-aligned, inside
    `.rodata`, and that each of the 33 words is the address of the expected function
    (handler, `__erebos_unhandled_<variant>`, `__erebos_unhandled_other`, or the shared
    one), and that `core.arch.__erebos_trap` is a function at a multiple of 4. The
    last assertion fails at `-O` when `#[align(4)]` is removed (checked: it lands at
    0x...7ea). `_start`'s tests (`startup_ranges`, `reset_entry_alone`,
    `the_entry_function_is_far_from_start`) pass unchanged.
  - No change to `PANICS` or `ONLY_IDS`: nothing new in `src/codegen/vectors.rs`
    can panic that did not already (the `expect`s of step 5).
  - The MIR dump does not show the table, as in step 5; the LLVM IR does.
