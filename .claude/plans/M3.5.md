# Plan: M3.5 Second target

ADRs: 0073, 0074, 0075, 0076, 0077
Base: 099f48c
Program on QEMU: the e2e programs on both targets: every portable
program of `tests/e2e/` built for `riscv32imac-unknown-none-elf` and run
on QEMU `virt`, and built for `thumbv7m-none-eabi` and run on QEMU
`mps2-an385`, each at `-O0` and `-O`, with the same output and exit
code (ADR 0077, step 7).
Out of scope:
- exception handlers, the rest of the vector table, interrupts: M4
  (ADR 0074);
- inline assembly, and with it `__aeabi_uldivmod`/`__aeabi_ldivmod` for
  C code on thumbv7m: M4 (ADR 0074, 0076);
- Cortex-M0 (`thumbv6m-none-eabi`), floating-point units, big-endian
  and 64-bit targets: not planned (ADR 0073, 0074);
- conditional compilation: not planned (ADR 0077);
- emitting LLVM's 64-bit division for constant divisors on thumbv7m: an
  optimization for later (ADR 0076);
- running the ESP32-C3's generated module, or generating ARM SVD files:
  the ESP32-C3 stays a riscv32 build test (ADR 0070).

Before step 1: the `docs(adr)` commit that accepts ADR 0073 to 0077
also sets the status lines of the ADRs they amend, in their files and
in the index (`docs/adr/README.md`):
- 0010: `Accepted; amended by 0073 (riscv32 is the first target, not
  the only one; the target is chosen per build), 0077 (test programs
  stop QEMU through their board module)`; index `Accepted, amended by
  0073, 0077`;
- 0012: `Accepted; amended by 0030 (...), 0057 (...), 0074 (on ARMv7-M
  the reset entry is two words of a vector table before `_start`)`,
  keeping the existing text; index `Accepted, amended by 0030, 0057,
  0074`;
- 0020: `Accepted; amended by 0052 (...), 0076 (where LLVM would call
  a 64-bit division function with a convention C cannot write, code
  generation calls `core`'s)`; index `Accepted, amended by 0052, 0076`;
- 0030: `Accepted; amended by 0034 (...), 0051 (...), 0057 (...), 0074
  (the unwind tables of ARM objects are discarded)`; index `Accepted,
  amended by 0034, 0051, 0057, 0074`.
The same commit holds the roadmap's edit written while planning: the
M3.5 pending decision settled by ADR 0073 to 0077.

Order: the target becomes a description (1) and a choice (2) while
riscv32 is the only one, so that no behavior changes; 64-bit division
moves out of LLVM's hands (3) and `core` gains the EABI's memory
functions (4), both tested on riscv32; the e2e programs move their
machine into a board module (5), still on riscv32. Then the ARM target
(6) arrives with its ABI, startup and linker script, checked by
snapshots and ELF inspection, and finally runs every portable program,
the generated programs and the layout tests on QEMU (7). Each step
leaves every existing test passing.

## 3. feat(codegen): 64-bit division calls `core`
- Status: done
- Implements: ADR 0076.
- Changes: `src/codegen/mod.rs`: in `rvalue`, `BinOp::Div` and
  `BinOp::Rem` on 64-bit integers, when the target's `div64` is false,
  build a call to `__udivdi3`, `__umoddi3`, `__divdi3` or `__moddi3`
  (the table of ADR 0076) with the C ABI's scalar passing, instead of
  `udiv`/`sdiv`/`urem`/`srem`; when it is true, as on riscv32, nothing
  changes. The callee is the module's function of that symbol,
  `core`'s; where a dump leaves `core` out (ADR 0052), the function is
  declared with the same signature. `rt/builtins.ers`: the comment of
  the division section says who calls them: LLVM where `div64` is true,
  code generation where it is false, and C code on riscv32.
- Tests:
  - the code path where `div64` is false cannot be reached from a
    target until step 6; a unit test in `src/codegen/mod.rs` lowers a
    body with the four 64-bit operations for a test description that
    copies riscv32's with `div64` false, and checks that the printed IR
    holds the four calls and no `udiv`/`sdiv`/`urem`/`srem` on `i64`.
    Step 6 adds the thumbv7m snapshot.
  - `tests/e2e/c_division64.ers` with a C file, `// targets:
    riscv32imac-unknown-none-elf` (ADR 0077's reason 2, a feature of
    the C side: clang calls libgcc's names): C code divides and takes
    the remainder of `u64` and `i64` values, which links only because
    `core` exports the four names (ADR 0076). The divisors are run-time
    values (parameters passed from Erebos), never constants, so that
    clang calls the four functions at `-O0` and at `-O2` alike; the
    test runs at both levels. Its header takes effect from step 5, when the
    harness learns to read it; until then every program runs on
    riscv32 only.
  - unchanged on riscv32: every snapshot, `tests/e2e/division64.ers`
    and the differential tests.
- Decisions:
  - The call is built by a new method `FnCodegen::divide64(op, signed,
    lhs, rhs)` in `src/codegen/mod.rs`, next to `compare`; `rvalue`'s
    `Div | Rem` arm takes it first when `int_of(lhs)` has 64 bits and
    `div64` is false, and otherwise keeps the old four builder calls. It
    does not go through `FnCodegen::call`, which needs a MIR callee id:
    the four functions are found by symbol, not by body id.
  - `Shared` and `FnCodegen` gain two fields, `module: &Module` and
    `div64: bool` (copied from `target.div64` in `lower`), instead of the
    whole `Target`, so that the code generation of a body reads only what
    it needs.
  - Finding the callee: `module.get_function(symbol)`, which is `core`'s
    when the module holds it (`#[export]` makes the symbol the name,
    ADR 0051); otherwise (a dump, `core` left out) the function is added
    with the signature `i64 (i64, i64)` and `nounwind`. It is not
    `null_pointer_is_valid` or `no-builtins`: those belong to bodies.
    `u64` and `i64` are `Direct`, so the type is the one `declare` gives
    `core`'s functions. Reserved names (ADR 0052) keep a program from
    defining a function of that symbol with another type.
  - Unit tests live in `src/codegen/mod.rs` as the plan says, and go
    through `driver::dump` and `driver::build` (the test module is outside
    the architecture table's reach), because `front_end` is private to the
    driver and building a `Mir` by hand would restate what the pipeline
    does. The test target is riscv32's description with `div64: false`
    (`Target { div64: false, ..RISCV32IMAC }`, leaked to get `'static`).
    Three tests, beyond the plan's one:
    `div64_false_calls_the_four_functions` (the dump has one call to each
    of the four and a `declare` of each, no `udiv`/`sdiv`/`urem`/`srem`
    on `i64`, and the 32-bit `udiv`/`srem` stay; at `-O0` and `-O`, where
    the calls become `tail call`);
    `div64_true_keeps_llvms_division` (riscv32: the four instructions, no
    `divdi3`/`moddi3` in the IR);
    `div64_false_links_with_core` (an object build and link, at both
    levels, with `core` in the module: it would fail if the call were
    declared instead of found, since LLVM would name the declaration
    `__udivdi3.1`). It writes to `$TMP/erebos-codegen-div64`, without a
    dependency on a temporary-directory crate.
  - `tests/e2e/c_division64.ers` repeats `division64.ers`'s values through
    four C functions (`c_udiv`, `c_urem`, `c_sdiv`, `c_srem`) that take
    both operands as parameters, so the divisor is a run-time value at
    every level and clang calls libgcc's names at `-O0` and `-O2`. The
    expected output is that of `division64.ers`. The `// targets:` header
    is there already and is ignored until step 5, as the plan says (the
    harness reads only the headers it knows).
  - `rt/builtins.ers`: the comment of the division section is rewritten as
    the plan says (LLVM and C code where `div64` is true, code generation
    where it is false). `docs/reference.md` (the paragraph on `core`'s
    support functions says "LLVM calls them") is left for step 8, which
    documents the targets.
  - `tests/architecture.rs`: `PANICS` for `src/codegen/mod.rs` goes from
    67 to 69. The two new panics are in `divide64` and have no user input
    behind them: an `expect("builder is positioned")` on `build_call`, and
    the `unreachable!` for a call that returns no basic value, which the
    function's own type (`i64`) rules out. Both follow `call`'s pattern.
    The symbol `match` has no `unreachable!`: like the old four-way
    `match`, its last arms take what is left.
  - One snapshot changed, `ui__ui@resolve_core.ers.snap`: its diagnostic
    quotes `rt/builtins.ers` at `__udivdi3`, so the longer comment moves
    the lines from 87-89 to 91-93. Nothing else in it differs (checked
    with `diff`); the new `assertion_line` metadata was dropped to keep
    the file's format. Every other snapshot is unchanged.

## 4. feat(rt): the EABI's memory functions
- Status: done
- Implements: ADR 0074, "Run-time functions".
- Changes: `rt/builtins.ers`: `__aeabi_memcpy`, `__aeabi_memcpy4`,
  `__aeabi_memcpy8`, `__aeabi_memmove` (and `4`, `8`),
  `__aeabi_memset(dest, n, c)` (and `4`, `8`) and `__aeabi_memclr(dest,
  n)` (and `4`, `8`), each `#[export]`, private, calling `memcpy`,
  `memmove` or `memset`, with a comment saying who calls them (LLVM on
  ARM EABI targets) and that the alignment promise is ignored.
- Tests: `tests/e2e/aeabi_memory.ers` with `aeabi_memory.c`
  (`// link-c:`): the C file declares the twelve functions and calls
  each on buffers with known contents, including overlapping moves in
  both directions, `n = 0`, and `__aeabi_memset`'s argument order (a
  value of `c` different from `n`); the program reports failures
  through the UART and the exit code. It runs on riscv32 now, and on
  both targets from step 7.
- Decisions:
  - The twelve functions are a new section of `rt/builtins.ers`, "ARM EABI
    memory functions", between the memory section and the 64-bit division
    one, with one comment for all (who calls them, that they exist on every
    target, that the alignment promise is ignored, that none returns a
    value). The file's header comment now names the ARM EABI beside libgcc
    and the C library. Each function is `#[export]` and private (not `pub`),
    as the plan says: programs reach `memcpy` and its two siblings by `core::`,
    not these. They have no return type (ADR 0074: none returns a value) and
    discard the result of `memcpy`, `memmove` or `memset`.
  - `__aeabi_memset*(dest, n, c)` calls `memset(dest, c, n)`: the swap of
    the two arguments is the only thing they do, and is commented. `c` is an
    `i32`, as ADR 0074's table says, and `memclr*` passes the constant `0`.
  - `tests/e2e/aeabi_memory.c` holds the checks, not the Erebos side: C is
    where the functions can be named and called with their own signatures
    (the Erebos functions are private). The C file numbers its checks and
    exposes `c_check_aeabi()` (the number of the first failed check, or 0)
    and `c_aeabi_checks()` (how many ran); `aeabi_memory.ers` prints `ok 64`
    or `fail N 64` and exits with the failed number, so a failure shows in
    the output and in the exit code, and a run that stopped early shows in
    the count. The Erebos side has no `__aeabi_*` calls of its own.
  - The checks go through one function pointer per kind (`copy_fn`, `set_fn`,
    `clr_fn`), so each of the twelve runs the same checks: copy (disjoint
    areas, guard bytes on both sides, then `n = 0`), move (overlapping, 24
    bytes shifted up and then down, bytes around them untouched, then
    `n = 0`), set (`n = 9` with `c = 0x15A`, so that the value differs from
    the length, and only its low byte `0x5A` is stored), clear (13 bytes,
    guards, `n = 0`). The plain forms use odd offsets (1, 3 and 5), the
    `4` and `8` forms offsets of 8 into 8-aligned buffers, which keeps the
    promise they make. The buffers are 512 bytes and the operations touch at
    most 64, so a swapped `n` and `c` (up to 346 bytes) fails a check
    instead of overrunning the buffer. Changing `__aeabi_memset` to swap
    them back was seen to fail at both levels (check 41); the ARM
    functions' shared body is not otherwise distinguished by the tests.
  - The program runs on riscv32 only, with no `// targets:` header: until
    step 5 the harness runs every program there, and it needs no header
    after, since nothing in it is specific to riscv32; the program is
    portable except for its UART and finisher addresses, which step 5 moves
    into `mod board;` like the other programs. Step 5 and 7 should check it
    like them.
  - Twelve functions added to `core` shift every item id after them: six
    UI snapshots changed, `resolve_core` (the diagnostic quotes
    `rt/builtins.ers` at `__udivdi3`, now at lines 163-165 instead of
    91-93) and five others (`resolve_bit_struct`, `resolve_field_modes`,
    `resolve_memory`, `resolve_peripheral`, `resolve_register_arrays`),
    whose resolved-item ids go up by 12. Checked with `diff`: nothing else
    in them differs. The `assertion_line` metadata was dropped as in step 3.
  - `tests/architecture.rs` is unchanged: no Rust code was touched.
