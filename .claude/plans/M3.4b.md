# Plan: M3.4b SVD

ADRs: 0070, 0071, 0072
Base: 78499a9
Program on QEMU: a peripheral generated from SVD, run on QEMU: the
devices of QEMU `virt` described in a hand-written SVD, generated with
`erebos svd`, configured and used by a program (`tests/e2e/svd_virt/`,
step 6).
Out of scope:
- interrupts (SVD's `interrupt`): M4 (ADR 0072);
- SVD's write effects without a neutral value, reset values of
  registers without fields, arrays of bit fields and arrays of
  peripherals: not added (ADR 0067); the generator declares what it can
  and warns (ADR 0072);
- carrying the GD32VF103's and the CH32V003's files: their license is
  unclear (ADR 0070); their constructs are in small hand-written files;
- running the ESP32-C3's module: the official QEMU has no machine for
  it; it is built into an executable with a small program, not run
  (ADR 0070);
- patching SVD files (as `svdtools` does) or options that change what
  the generator writes: none;
- the second target: M3.5.

Before step 1: the `docs(adr)` commit that accepts ADR 0070 to 0072 also
sets the status line of ADR 0063, in its file as `Accepted; amended by
0070 (the module svd, which uses syntax and which driver uses; the
external crate roxmltree)`, and in the index (`docs/adr/README.md`) as
`Accepted, amended by 0070`. The same commit holds the roadmap's edit
written while planning: the M3.4b pending decisions settled by ADR 0070
to 0072.

Order: warnings in `diag` (1) come first, since the reader reports
them; the reader (2) turns an SVD file into a model with spans and no
Erebos in it; the writer emits peripheral types, registers and
peripherals (3), then fields and enums (4), with the subcommand and the
test harness from step 3. The ESP32-C3 (5) and the program on QEMU (6)
need the whole generator. Every generated output a test makes is
compiled (type checked, and the ESP32-C3's and `virt`'s built into
executables), so a step whose writer emits invalid Erebos fails its own
tests.

## 1. feat(diag): warnings
- Status: done
- Implements: ADR 0070, "Diagnostics" (a `Diagnostic` gains a severity).
- Changes:
  - `src/diag.rs`: `Diagnostic` gains `severity: Severity` (`Error`,
    `Warning`); `Diagnostic::error` keeps its signature, and
    `Diagnostic::warning(code, message)` builds a warning.
    `Diagnostics::has_errors` counts errors only, while `len` and
    `is_empty` count both. `render` keeps miette's
    `GraphicalReportHandler`: the wrapper implementing
    `miette::Diagnostic` (`WithSource`) returns `Severity::Warning` from
    `severity()` for a warning, so that miette draws it with its warning
    glyph (and color, when colored). No layer of the compiler emits one.
- Tests: unit tests in `src/diag.rs`: a sink holding only warnings has
  no errors, one holding a warning and an error has, and `len` counts
  both; a warning renders, in the `unicode_nocolor` theme the ui
  snapshots use, with miette's warning glyph instead of the error's
  `×`, its code, labels and help.
- Decisions:
  - `Severity` is a new `pub enum` in `src/diag.rs` (`Error`, `Warning`,
    with `Clone, Copy, Debug, PartialEq, Eq`), separate from
    `miette::Severity`, which has an `Advice` the compiler has no use
    for; the `miette::Diagnostic` wrapper maps one to the other. The
    field is `pub`, as the others of `Diagnostic` are.
  - `Diagnostic::error` and `warning` both go through a private
    `Diagnostic::new(severity, ...)`, so no caller builds the struct by
    hand (none did before) and a field added later is set in one place.
  - `WithSource::severity()` returns `Some(Error)` for an error instead
    of leaving miette's default `None`: miette draws both the same, and
    the existing snapshots did not change, so one `match` states the
    mapping completely.
  - `has_errors` is `any(severity == Error)`; `len` and `is_empty` stay
    as they were and count both, as the plan says. No caller in the
    compiler changed: none emits a warning yet, so `has_errors` answers
    as before for every existing run.
  - The tests are two. `warnings_are_not_errors` covers the sink (only
    warnings: no errors, `len` 1; plus an error: errors, `len` 2; an
    error alone). `a_warning_renders_with_the_warning_glyph` renders
    with `render(.., color: false)`, which uses the `unicode_nocolor`
    theme the ui snapshots use, and checks the code, `⚠` on the message
    line, label, help and position, no `×`, then that an error of the
    same shape shows `×` and no `⚠`. They are assertions on substrings
    like the other `render` tests of the module, not a snapshot: no file
    in `tests/ui/` renders a warning until step 3.
  - In miette's layout the code (`test::example`) is on a line of its
    own, above the glyph and message, so the glyph is asserted next to
    the message, not next to the code.

## 2. feat(svd): read SVD files
- Status: done
- Implements: ADR 0070 ("Reading XML", "Where it lives", the errors of
  "Diagnostics"); the reading half of ADR 0072 ("Properties", the
  `derivedFrom`, `dim` and `dimIndex` rules of every element, "Values
  that are no SVD value").
- Changes:
  - `Cargo.toml`: `roxmltree = "0.21.2"` (0.21.0 is yanked); the commit body says why
    (ADR 0070: a read-only tree with node ranges for diagnostics, no
    dependencies of its own, MIT or Apache-2.0).
  - `src/lib.rs`: `pub mod svd;`.
  - `src/svd/mod.rs`, `src/svd/read.rs` (names are suggestions): a model
    of the device (name, version, license text), its peripherals,
    registers, clusters, fields and enumerated values, each with the
    span of its element in the SVD file (a file of the `SourceMap`), and
    `read(file: FileId, text: &str, diags: &mut Diagnostics) ->
    Option<Device>`. The reader:
    - parses numbers as SVD writes them (decimal, `0x`/`0X`, `#` for
      binary; `svd::invalid-number` otherwise), and enumerated values
      with don't-care bits (`#1x0`) as such, for ADR 0072 to leave out;
    - inherits `size`, `access`, `resetValue`, `resetMask` from device
      to peripheral to cluster to register;
    - resolves `derivedFrom` on peripherals, clusters, registers, fields
      and enumerated values, and `alternatePeripheral`, with ADR 0072's
      "`derivedFrom`" rules: where a name is looked up, what is copied,
      how children merge, and when a derived peripheral shares its
      base's type (`svd::unknown-reference`, `svd::derived-cycle`);
    - takes a field's bits from the first form it states (ADR 0072);
    - reads `dim`, `dimIncrement` and `dimIndex` (ranges `2-3` and
      `A-C`, lists `A,B,C`) into an array or a list per ADR 0072
      (`svd::invalid-dim`);
    - reads `access`, `readAction`, `modifiedWriteValues` and `usage`,
      a value SVD does not define becoming absent with the warning
      `svd::invalid-value` and a note the writer turns into a comment;
    - reports `svd::xml` (roxmltree's error, at its position; a file
      that is not UTF-8, without a span), `svd::not-svd` and
      `svd::missing-element`;
    - leaves out reset values where no level states one, and reads an
      absent `resetMask` as every bit (ADR 0072, "Properties").
    The model holds no Erebos names or syntax: those are the writer's.
  - `tests/architecture.rs`: `LAYERS` gains `("svd", &["syntax"])`
    (used from step 3), `EXTERNAL` gains `("roxmltree", "svd")`, and
    `PANICS` the new files if they hold any (each justified in
    `Decisions`).
- Tests: unit tests in the `svd` module, on SVD text written in the
  test: numbers in each syntax and the invalid ones; inheritance of each
  property, a register stating its own, no `resetValue` anywhere, no
  `resetMask`, and reset bits above the register's size; `derivedFrom`
  of each kind (peripheral, cluster, register, field, enumerated
  values), by name and by path, a derived peripheral with registers,
  with only a property of its own, and with neither, a derived register
  inheriting from its own parent and not its base's, children replaced
  in place and added after, an unknown name, an unknown
  `alternatePeripheral`, and a cycle; a field with two forms of bits;
  a file that is not UTF-8; `dim` as an array, as a list from
  `dimIndex` in each form and from `0..dim`, and each `svd::invalid-dim`
  case; an `access` of `write` and of `read/clear` read as absent with
  `svd::invalid-value`, and so a `readAction`, `modifiedWriteValues` and
  `usage` of no SVD value; each other error, with its span on the right
  element.
- Decisions:
  - **The dependency.** `roxmltree = "0.21.2"` in `Cargo.toml` (a normal
    dependency, used only in `src/svd/`). It is not free of dependencies as
    ADR 0070 says: 0.21.2 depends on `memchr` (MIT or Apache-2.0), which was
    already in `Cargo.lock` through `insta` (a dev-dependency) and is now
    also a runtime dependency of the crate. ADR 0070 got a dated note
    (2026-11-02) saying so, its status line and the index entry reading
    "corrected 2026-11-02" (review). Text for the commit body: "Adds
    `roxmltree` 0.21.2 (MIT or Apache-2.0) to read SVD's XML with node
    ranges for diagnostics (ADR 0070). It depends on `memchr` (MIT or
    Apache-2.0), already in Cargo.lock through the dev-dependency `insta`
    and now also a dependency of the crate; ADR 0070 is corrected."
  - **Files.** `src/svd/mod.rs` is the model (public types, `pub use
    read::{read, utf8}`); `read.rs` is the entry point, the `Reader` that
    counts and de-duplicates diagnostics, the phases, and every test of the
    reader (they run on SVD text through `read`, as the plan asks, so they
    live in one `tests` module, which the architecture test needs to be the
    last item of a file); `parse.rs` turns the XML into `raw.rs`'s arena;
    `derive.rs` resolves `derivedFrom`; `build.rs` inherits properties and
    reads `dim` into the model; `number.rs` holds the number and index
    syntaxes, with their own unit tests.
  - **Phases.** The reader runs parsing, `derivedFrom` resolution and the
    build in turn, each only if the one before reported no error: an element
    dropped for a missing `name`, or a number that could not be read, would
    otherwise bring `svd::unknown-reference` and `svd::missing-element`
    that follow from it. The cost is that a file with an invalid number and
    an invalid `dim` shows the first only. Tested by
    `a_parse_error_stops_before_the_errors_that_follow_from_it`.
  - **Model with the SVD's names.** Names are kept as the file writes them
    (`%s` and `[%s]` included, names trimmed); descriptions and the
    `licenseText` are kept as the XML gave them (entities decoded, nothing
    trimmed or collapsed), since collapsing and wrapping are the writer's
    (ADR 0072, "Comments"; ADR 0070). The reader does no `[%s]`/`%s`
    substitution: that is ADR 0071's step 1.
  - **What the model holds of each element.** `size`, `access`,
    `resetValue`, `resetMask` are inherited into the register
    (`Register.size`, `access`, `reset_value`, `reset_mask`); a register
    without any level stating a `size` is `svd::missing-element`. The reset
    value and mask are cut to the register's size (64 and above keep every
    bit). A field keeps its own `access`, `read_action` and
    `modified_write_values` (not inherited from the register: the writer
    compares them with the register's, ADR 0072). A register and a field
    keep the span of `writeConstraint` (and a register that of
    `protection`) as an `Option<Span>`: only their presence matters, and
    the warning's place. `Peripheral.alternate` is the index of the
    peripheral named; `Cluster.alternate_cluster` and the register's
    `alternate_group`/`alternate_register` are strings, not looked up
    (ADR 0072). An `EnumValue` keeps `value: Option<EnumNumber>`
    (`Value(u64)` or `DontCare(text)`) and `is_default`.
  - **Notes.** `notes: Vec<String>` on peripherals, clusters, registers,
    fields and sets hold the text of each `svd::invalid-value` read as
    absent at that element (the same text as the warning's message), for
    the writer's `// svd:` comment. A value on the device has no item: it
    is warned without a note. Notes belong to the element that states the
    value and are not copied by `derivedFrom` (a copy is built clean), so
    the comment shows once, at the base. An unreadable `isDefault` (not
    `true`, `false`, `1`, `0`) is `svd::invalid-value` too, read as
    `false`, with no note (an `enumeratedValue` is no item to comment).
  - **Derived elements keep the spans of the elements they are copied
    from**: a copied register's span is the base's, not the derived
    peripheral's. A mistake in a copy is therefore found at the base, and
    `Reader` reports an error once per (code, span, message), so a base
    with a missing `size` copied into three peripherals shows one error.
  - **A shared type has no items.** A peripheral that shares its base's type
    (`shares_type_with: Some(index)`, the end of the chain of peripherals
    that have a type of their own) has `items` empty in the model: the
    registers are the other peripheral's, and building them again would
    only repeat their errors. They are still copied in the reader, so
    paths into them (`B.REG`) resolve.
  - **`derivedFrom`, what the ADR left to the code.** A name with `.`
    searches each segment among the children of the previous element, by
    SVD name (the last segment takes the first child of the kind wanted,
    the others the first child of any kind); a
    set's sibling search is among the sets of every field of its register,
    first in file order. An element's own `name` is never copied. `dim`,
    `dimIncrement` and `dimIndex` derive as one block (a derived element
    stating `dim` replaces the base's whole). Children match by SVD `name`
    and only against the base's (two children of the derived element with
    one name do not replace each other); a child without a `name`
    (a set) replaces nothing. A set's values merge the same way (by value
    `name`, a nameless value is added). A derived set keeps
    `derived_from: Some(SetId)` of the original set, and a copy of an
    element made for another peripheral keeps pointing at the original set
    too. The ADR says a set with `derivedFrom` "is the enum written for the
    set it names" when the integer types agree, without saying what a
    derived set that adds values of its own is: the model holds both the
    merged `values` and `derived_from`, and step 4 decides.
  - **Cycles.** `svd::derived-cycle` is reported once, at the
    `derivedFrom` of the element where the cycle closes, with the chain of
    names as its label (`A -> B -> A`). A base is resolved whole (its
    subtree too) before a derived element copies it, so an element that
    derives from another's child while that other derives from it
    (`P2 derivedFrom P1` with `P1.R derivedFrom P2.Q`) is reported as a
    cycle although a finer order would resolve it; the user accepted this
    (review).
  - **A ceiling on copies (review).** `derivedFrom` copies the base's
    children, so a chain of derived clusters, each holding a copy of the
    one before, doubles the tree at every level: a few kilobytes of SVD
    would allocate without end. `MAX_CLONED` in `raw.rs` is 262 144 (2^18)
    elements copied in all; before a derived element copies its base's
    children, `merge_children` counts them (`Tree::size`) and, if the
    total of copies made so far plus these passes the ceiling, reports
    the error `svd::too-large` at the `derivedFrom` and fails the element
    (no panic, no abort; what derives from it is failed silently, as for a
    cycle). 2^18 elements are about a hundred megabytes in the worst case
    and some fifty times what the ESP32-C3, the STM32F407 and the
    GD32VF103 files copy (all three still read). `svd::invalid-dim` does
    not fit (nothing is repeated), and the other codes of ADR 0070 name
    other mistakes, so the code is new: `svd::too-large`, an error
    stated only here, as the user decided (it also reports the two limits
    of the next entry); step 7 lists it with the other `svd::` codes. Tested by a chain of 40 clusters (under 8 KB of SVD)
    and by a chain of 10 that is copied.
  - **Caps on recursion (review).** The walks over the tree recurse
    (the parser, `Tree::size`, `height`, `clone_deep`, `Resolver::subtree`
    and `children`, the build), and roxmltree has no nesting limit, so a
    file of a few kilobytes overflowed the 1 MB stack at about 400 nested
    `<cluster>`. Two limits in `raw.rs`, both reported as `svd::too-large`
    (the policy of the other limits: no new code, no ADR):
    - `MAX_DEPTH = 32`: no element stands deeper than 32 levels, the
      peripheral being 1 (the real files reach 6: peripheral, cluster,
      cluster, register, field, set). The parser refuses a cluster whose
      register, field and set would pass it (clusters nest to 28 levels)
      before it reads the cluster, so its recursion stops at the cap;
      the file's outermost too-deep cluster is the one error. `derivedFrom`
      can build depth too (`Ck` holding a copy of `C(k-1)`, ~700 levels
      under `MAX_CLONED`), so `merge_children` refuses when the derived
      element's depth plus the base's height (`Tree::height`) passes the
      cap, before it copies anything. Every tree the later walks see is
      therefore at most 32 deep.
    - `MAX_CHAIN = 32`: no more than 32 elements may wait on a
      `derivedFrom` at once (`Resolver::stack`): resolving an element
      resolves its base first, which recurses, and a file of 100 000
      peripherals each deriving from the next would otherwise overflow.
      The element that would be the 33rd fails with the error.
    The two together are bounded by a test, run on a 512 KB stack (half
    the main thread's on Windows): 32 registers, each at the bottom of 25
    nested clusters, deriving from the one before by a path, written last
    first. It also passes at 200 KB. Other tests: 28 nested clusters read
    and 29, 400 and 100 000 are refused; a linear chain of derived clusters
    reads to `C29` and is refused from `C30` to 3 000; a chain of 32
    derived peripherals reads and 33, 100 and 3 000 are refused (not
    larger: looking a sibling up is linear in the peripherals, so a chain
    of 100 000 takes quadratic time before it is refused, which a file of
    that size can already cost; not a stack problem).
  - **Empty names.** The reader accepts a `name` that is empty or only
    white space (`<name> </name>` reads as `""`): ADR 0071 makes it
    `svd::invalid-name` when its characters are replaced, which is step
    3's, so step 3 must test it (a peripheral, a register, a field and an
    enumerated value with an empty name).
  - **`alternatePeripheral`** is looked up after every `derivedFrom` is
    resolved (a derived peripheral copies its base's), by SVD name among
    the peripherals, first in the file; it may name the peripheral itself
    (the compiler rejects it later). `svd::unknown-reference` is at the
    `alternatePeripheral` element.
  - **`dim`.** Peripherals and fields are always a `Repeat::List` (arrays
    of them are not added, ADR 0072), even with `[%s]`. A register or
    cluster whose name has `[%s]` is a `Repeat::Array` when `dimIndex` is
    absent or exactly `0` to `dim - 1`; any other case is a list. The
    `svd::invalid-dim` cases are the ADR's plus `dim` 0, a `dimIndex` that
    goes down (`3-2`, `C-A`) and a list wider than 65 536 indices
    (`MAX_LIST` in `build.rs`, applied when a list or a `dimIndex` is
    expanded; an array has no limit): a hostile file would otherwise
    allocate gigabytes. The limit is the generator's own and in no ADR;
    the user decided it stays (review). A `dimIndex` range is counted
    with a saturating sum, so `0-18446744073709551615` is an
    `svd::invalid-dim` (wrong length), not an overflow (review). A range of letters is one case for both
    ends (`A-C`, `a-c`; `A-c` is no range). The label is the repeated
    element, with a second label at its `dim`. A `dimIncrement` without a
    `dim` is not read (so not validated).
  - **Numbers.** Decimal, `0x`/`0X` and `#` binary only, as the plan says:
    no sign, no `_`, no `0b`, no `k`/`m` suffix; a number is a `u64`, and
    `size`, `dim`, `dimIncrement`, `bitOffset`, `bitWidth`, `lsb`, `msb`
    must fit in 32 bits (`svd::invalid-number` either way, with "does not
    fit" for the second). An `enumeratedValue`'s `value` with `x` among
    its `#` digits is `DontCare`; `x` elsewhere is invalid.
  - **A field's bits.** A form counts as stated only when whole
    (`bitOffset` with `bitWidth`, `lsb` with `msb`, a `bitRange`); a field
    stating none has `svd::missing-element` (in the build phase, so a
    derived field can take them from its base). `msb` below `lsb`, a
    `bitWidth` of 0, a `bitRange` that is not `[msb:lsb]` are
    `svd::invalid-number`, for want of a code of their own in ADR 0070;
    the user decided they keep it (review).
  - **`enumeratedValue`.** One with neither `value` nor `isDefault` is
    `svd::missing-element` (SVD requires one of the two); one without a
    `name` is read, with `name: None`.
  - **Document-level.** The device's `name` is required
    (`svd::missing-element` at the device: the header needs it), its
    `version` and `licenseText` are optional. Elements are known by local
    name, namespaces ignored (the files carry `xmlns:xs`). roxmltree's
    default of refusing a DTD is kept (`svd::xml`). A BOM is skipped by
    roxmltree.
  - **Not UTF-8.** `read` takes `&str` as the plan says, since spans index
    a text of the source map; the check is a function of its own,
    `svd::utf8(bytes, diags) -> Option<&str>`, which reports `svd::xml`
    without a span ("byte N is not valid") and which the driver of step 3
    calls before adding the file to the source map. The test is on it.
  - **`svd::xml` spans.** roxmltree gives a row and a column in characters;
    `offset_of` turns them into a byte offset, and the span is the one
    character there (empty at the end of the text).
  - **Architecture.** `LAYERS` gains `("svd", &["syntax"])` (after
    `syntax`; `syntax` is not used yet) and `EXTERNAL` `("roxmltree",
    "svd")`. `PANICS` gains nothing: no file of `src/svd/` has a panic
    outside its test module (no `unwrap`, `expect` or `assert`; arena
    indexing is not counted and the indices come from the arena itself).
  - **Tests.** 60 unit tests in `src/svd`: 6 in `number.rs` (each syntax,
    invalid numbers, don't-care values, bit ranges, `dimIndex` forms and
    errors) and 54 in `read.rs`, one per plan item (plus, from the review, a file
    with a BOM, a doubling chain of `derivedFrom` and the widest `dimIndex`), on small SVD text built
    by helpers (`svd`, `p`, `r`, `f`, `set`...); each error test checks
    the code and the text under the primary label. I also read the
    ESP32-C3's version 18, the STM32F407's and the GD32VF103's SVD files
    (downloaded to a scratch directory, not committed) through `read` in a
    throwaway test: all three read in 0.2 to 0.4 s, the first two with no
    diagnostic, the third with its `access` `write` warnings. That test is
    not kept; step 5 carries the ESP32-C3.

## 3. feat(svd): generate peripheral types, registers and peripherals
- Status: done
- Implements: ADR 0070 ("A subcommand that writes source", the header,
  the format); ADR 0071 for peripherals, peripheral types, modules,
  registers, clusters, cluster types and groups (the names of structs,
  enums and variants are step 4's); ADR 0072 "Peripherals",
  "Registers", "Clusters", "Comments", and the warnings of those
  sections.
- Changes:
  - `src/svd/names.rs`: the steps of ADR 0071 (the index, the
    characters, the case, a leading digit), the escape with `_` of
    keywords (`syntax::token::TokenKind::keyword`), `core` and built-in
    type names, names that meet, `svd::renamed` and `svd::invalid-name`.
  - `src/svd/write.rs`: from the model, the generated text: the header
    (ADR 0070), a module per peripheral type, a module per cluster type
    inside it, the peripherals; each register with its mode (stated,
    inherited, or from its fields, ADR 0067), its type (the unsigned
    integer of its size, until step 4 gives registers with fields their
    struct), its offset, its `step`, its read effect and its group; lists
    expanded; cluster arrays with their `step`; derived peripherals
    sharing their base's type; `over` from `alternatePeripheral` or
    computed from the extents with ADR 0072's rule (`svd::overlap`, and
    no `over`, when one cannot say it); `// svd:` comments and
    `svd::not-declared` for a register's size, `writeOnce` and
    `read-writeOnce`, its reset value or `modifiedWriteValues` without
    fields, `writeConstraint` and `protection`; descriptions as comments
    wrapped at 79 columns (a word longer than a line is put alone on
    its line, not cut). The format of ADR 0070, "A subcommand that
    writes source".
  - `src/svd/mod.rs`: `generate(name: &str, text: &str) -> (Option<String>,
    Diagnostics, SourceMap)` or similar, reading then writing.
  - `src/driver.rs`: the entry the command line and the tests use to
    generate (read the file, generate, render the diagnostics, write the
    output only when there is no error); `tests/architecture.rs`: the
    `driver` row gains `svd`.
  - `src/main.rs`: the command `svd <input.svd> [-o <output.ers>]`, in
    `USAGE`; the default output and the refusal of an output that is
    the input (ADR 0070); warnings printed to stderr, exit status
    failure on an error only.
- Tests:
  - `tests/svd.rs`, a new harness: each `tests/svd/*.svd` is generated,
    and its snapshot holds the generated text followed by the rendered
    diagnostics (plain, as the ui snapshots). When it generates, the
    output is written into a directory under `CARGO_TARGET_TMPDIR`, with
    a root module that declares it (`mod generated;`), an `entry fn`, a
    panic function and a `memory` block (without them typeck reports
    `resolve::missing-entry` and the missing panic function), and type
    checked through `driver::dump` (`Stage::Typeck`); a type error fails
    the test.
  - Files of `tests/svd/`, each proving one part:

- Decisions:
  - **Files.** Besides `names.rs` and `write.rs`, three more modules of
    `src/svd/`: `text.rs` (hexadecimal numbers and comments wrapped at 79
    columns, with unit tests), `over.rs` (the extent of a peripheral type and
    the search for `over`, with unit tests) and, in `mod.rs`, `generate` and
    `default_output_name`. `names.rs` holds the conversion and the `Scope`
    that keeps names apart, with unit tests; `write.rs` is the text. They are
    split so that each has one job and its own tests; none of them is a
    layer, so `LAYERS` has nothing to add (`svd` may use `syntax`, and
    `names.rs` uses its table of keywords, `TokenKind::keyword`).
  - **`generate`** is `generate(name, text) -> (Option<String>, Diagnostics,
    SourceMap)` as the plan says: it adds the file to a source map of its
    own and returns it. `name` is the input's file name (no directory), used
    both as the SVD file's name in diagnostics and in the header, so the
    output is a function of the bytes and the file name (ADR 0070). It takes
    `&str`: the driver calls `svd::utf8` first, with a `Diagnostics` and an
    empty source map of its own, and renders `svd::xml` without a span when
    the bytes are not UTF-8 (step 2's decision).
  - **The writer reports through `Reader`**, the type of `read.rs` that counts
    errors and reports an error or a warning once per (code, first span,
    message): a derived element copied into several types keeps the base's
    spans (step 2), so the same warning is found once per copy. `Reader::new`
    and `failed` became `pub(super)` for it, and its doc says it serves both
    passes.
  - **The driver entry** is `driver::svd(input, output, color) ->
    Result<SvdOutput, String>`, `SvdOutput { output, warnings }` holding the
    path written and the rendered warnings (empty when none); `main` prints
    them to stderr and exits with success. The order is: the output's path
    (`-o`, or the input's directory with `svd::default_output_name`), the
    refusal of an output that is the input, reading, `svd::utf8`, `generate`,
    writing. An error returns the rendered diagnostics (warnings included)
    and writes nothing. The refusal compares the two paths with
    `fs::canonicalize` when both exist (a link, `./x`, another case on
    Windows), by the paths themselves otherwise, and says `the output ... is
    the input file; name another with -o`. An input whose name leaves nothing
    for a module name (`@@.svd`) is an error asking for `-o`: ADR 0070 has no
    answer, and a default of any other kind would be a guess. The default
    name of an input without extension is its name (`plain.ers`) and of
    `a.b.svd` is `a_b.ers` (the last extension only).
  - **The command line.** `svd` takes `-o` and one input; any other option
    (`-O`, `--link`, `--emit`) is `unknown option` with exit status 2 as for
    `build`, and an error of the generator exits with 1. `USAGE` lists both
    commands. `parse_args` returns a `Command` (`Build` or `Svd`).
  - **The command's tests run the binary** (`CARGO_BIN_EXE_erebos`, which
    Cargo gives integration tests), not `driver::svd`: the argument parsing,
    the exit statuses and the stderr output are the command's contract, and
    nothing else tests `main.rs`. The e2e harness calls `driver::build`
    because it has no use for them.
  - **Names (ADR 0071).** `convert(name, index, case)` is steps 1 to 5 and
    returns whether step 2 or step 4 changed the name, compared with what
    step 1 made of it (`CH%s` with index 2 is not a rename; `%s_X` removed
    to `_X` and then `X` is). Step 1 is one pass over the text, so an index
    that holds `%s` is not replaced again. A keyword, `core` or a built-in
    type gets its `_` without the warning, as ADR 0071 says only steps 2 and
    4 and meeting are renamed. The set of built-in types is the ADR's
    (`bool`, the eight integer types, `usize`, `isize`, `Option`,
    `Result`).
  - **`svd::renamed` is reported by the item that stands for the SVD
    element**, a peripheral, register or cluster entry, an alternate group,
    for its characters or leading digit, and not again for the module and
    type made from the same element (one warning, not three). A name that
    meets another in its scope is reported by whichever item it is, each
    with the other's span as a second label.
  - **`svd::invalid-name`** is at the element, once per element (the module
    and the type made of one name give one message): "the name `X` of this
    peripheral leaves nothing for an identifier", or "this register has an
    empty name" for an empty name (the reader trims, so `<name> </name>` is
    empty). A cluster's invalid name drops the cluster and its registers;
    an invalid alternate group is an error at its register. The writer goes
    on, so every invalid name of the file is reported, and nothing is
    written. Tested on a peripheral, a register (`-` and a blank one), a
    cluster, and an alternate group (`errors_invalid_name.svd`); a field and
    an enumerated value, which step 4 writes, are step 4's tests.
  - **Scopes.** One `Scope` is the file's: the modules of the peripheral
    types in the order of the file, then the peripherals, in one namespace
    as the language has it (ADR 0049), so a peripheral named `uart` meets
    the module of `UART%s` and becomes `uart__` (the module made from it,
    `uart_`, having met first). A module's items (its type, and in step 4
    its structs and enums, and its clusters' modules) are one scope, and a
    peripheral type's entries (registers and clusters, ADR 0058) another;
    ADR 0071 says "two items of one module, two entries of one peripheral
    type". The type name is taken first in its module. Groups are labels in
    no scope: each is converted in a scope of its own.
  - **`Scope::claim` remembers, for each name asked for, how many `_` the
    next item starts from**, since a name is never freed: without it,
    n items of one name try one another in n^2 steps with names of n
    characters. The output itself is quadratic for n equal names, as ADR 0071
    says ("as many times as it takes"): the hostile file of n equal names
    gets a file of n^2 bytes, which the rule asks for and no cap here
    limits.
  - **The plan before the text.** The names of the modules, types and
    peripherals are taken before anything is written (a peripheral's type
    path and its `over` may name what is declared later), and in a peripheral
    type the names of the clusters' modules are taken before its entries are
    written, in the order ADR 0071 gives (type, structs of the registers,
    then the clusters' modules): step 4 adds the structs' names to that
    plan, before the clusters', without moving the code.
  - **Layout of the text.** `pub peripheral T {}` for a type with no entry;
    a peripheral type is followed by the modules of its clusters, each after
    a blank line; an entry or an instance with a comment is set apart from
    its neighbors by a blank line and ones without are packed; modules are
    always apart. Zero is `0x0`, as the format of ADR 0070 gives it.
  - **Comments.** The 79 columns count the indentation and `// `; a text of
    white space only gives no comment. Every line of a `// svd:` note starts
    with `// svd: `, so a search finds them all, which makes a wrapped note
    repeat it (`// svd: left out: it is 64 bits wide, and a register is 8,
    16 or 32` then `// svd: bits wide`). An element's description is written
    above each element it makes: the peripheral type and every peripheral
    (a list of peripherals repeats it), a cluster's entry and its type, each
    entry of a list of registers or clusters. The `// svd:` comments follow
    the description, the reader's notes (`svd::invalid-value`) first, then
    what has no declaration. A peripheral's notes are above its type, or
    above the peripheral when it shares its base's type and has no type of
    its own. A register left out has a block of comments alone (its
    description and why), and is no entry.
  - **The header** is three comment lines (the generator and the file's
    name; `Device: NAME, version V.` or without the version; the warning
    that edits are lost), then, when the device has a `licenseText`, `//`
    and its lines, each with its white space at the end removed and its
    white space at the start kept, blank ones as `//`; blank lines at either
    end of the text are dropped, as XML writers put the notice on lines of
    its own.
  - **Register modes.** A register's mode is its inherited `access`; with
    none, from its fields: `read` when there is at least one field and every
    one is `read-only`, `write` when every one is `write-only` or
    `writeOnce` (ADR 0072 makes it `write-only`), otherwise `read write`,
    and a field stating no access counts for neither. `writeOnce` and
    `read-writeOnce` on a register are `write` and `read write` with the
    comment and `svd::not-declared`.
  - **What has no declaration, on a register.** The size is not 8, 16 or 32:
    left out (an array or a list too), the warning at the register; a reset
    value that is not 0 (after the cut to the register's size, whatever
    `resetMask` says) and `modifiedWriteValues` other than `modify`, only on
    a register without fields; `writeConstraint` and `protection`, at their
    own elements (the register's when it is the register that is not
    declared). A register with fields and a reset value or a write effect
    is step 4's (the fields carry them).
  - **Extents, and where they live.** `over.rs` computes a peripheral type's
    extent as `layout` does (the end of the last byte, nothing for a size 0
    or a length 0, saturating at 2^32 + 1) because `svd` may use `syntax`
    alone (ADR 0063); the saturation value is a copy of
    `layout::PAST_ADDRESS_SPACE`, and the doc says so. A register left out
    occupies nothing. An empty peripheral type covers no byte and shares
    none.
  - **Finding `over`.** Only two peripherals can be the candidate of ADR
    0072's rule: the first of `S` and the one it is `over`, since the
    candidate is, or is `over`, each of `S`. The code checks those two
    and takes the first in the file, the rule's answer in O(|S|) per
    peripheral. Peripherals that share bytes are looked for in the earlier
    ones only (O(n^2) in the number of peripherals, which a list of
    peripherals can raise to 65 536 as the reader lets it; like step 2's
    lookup, not a stack problem). A comment above the peripheral (`// svd:
    the SVD does not say that it is over ...: found from the bytes it
    shares with ...`) says that it was found, without a warning, as the ADR
    says; `svd::overlap` carries the peripheral's span first and one label
    per peripheral of `S`, with a `// svd:` comment too. An `over` the SVD
    states is written as it is, even to the peripheral itself (the compiler
    reports `resolve::over-itself`), and does not look for bytes.
  - **`alternatePeripheral` naming a list.** The target is the list's first
    peripheral (`TIMG%s` is `over TIMG0`), by the SVD name looked up in step
    2. The user decided this (review), with no change to ADR 0072. When the
    alternate overlaps the list's other elements, the compiler reports
    `ty::peripheral-overlap` for them, since `over` of the first does not
    cover those; the tests state an `alternatePeripheral` from a single
    peripheral to a list (`TIMG_VIEW`).
  - **An `alternatePeripheral` whose target has no peripheral written** (its
    name is invalid, so `svd::invalid-name` is already reported) is as if the
    SVD stated none, and the `over` is computed from the bytes. A choice:
    the generation fails anyway, and the error is the one that matters.
  - **A register left out for its size is never name-converted**, so an
    invalid name on it is not reported (nor a rename). A choice: it is not
    written and takes no name; the file is generated without it and warned,
    and an invalid name is reported once its size is fixed.
  - **In a list of peripherals each element gets its own `svd::renamed`**
    (`names.svd` shows `_0_leading` and `_1_leading` for `%s_LEADING`): the
    messages name the new name, which differs, so `Reader` keeps both. A
    choice, as it says which names the elements were given.
  - **Text of the SVD file in a comment cannot break out of it (review).**
    The device's `name` and `version` and the input's file name are written
    with their white space collapsed (`one_line`), as descriptions and notes
    are by `comment`; the `licenseText` has every control character and
    Unicode line separator but `
` and tab replaced by a space before it is
    split into lines (`break_free`). Without it a `name` with a line break
    wrote the rest as Erebos source. Every other piece of the file's text in
    the output is a name converted to identifiers, a number in hexadecimal,
    or goes through `comment`; `header.svd` has a name and a version of
    several lines, and the type check fails if one escapes.
  - **Alternate groups.** An `alternateGroup` is converted like a name (lower
    case, `_` for a keyword: `continue_`), with `%s` removed; an
    `alternateRegister` makes the group named as the register's entry after
    renaming, element by element for a list; the same for a cluster's
    `alternateCluster`. A group is written whatever it stands against: it
    changes no check but the overlap's.
  - **Tests.** `tests/svd.rs` has one test over `tests/svd/*.svd` (a
    snapshot of the generated text and the rendered diagnostics, or
    "not generated" and them) and eight of the command. The text is also
    written under `CARGO_TARGET_TMPDIR/svd/<file>/` beside a root file of the
    plan (`mod generated;`, an entry, a panic function, a memory block) and
    type checked with `driver::dump` to `Stage::Typeck`; the codes of the
    errors the compiler reports are read from the rendered text (the lines
    that hold a code alone) and must be those of the file's `<!--
    expect-error: ... -->` comments, no more and no fewer. Files, each with
    what it proves: `registers.svd` (modes stated, from the peripheral and
    from the fields, sizes 8, 16, 32 and 64, reset values), `registers_inherited.svd`
    (`size` and `access` from the device, the peripheral and a cluster; the
    device's `access` stops a mode from fields, so the device's inheritance
    could not share `registers.svd`), `arrays.svd`, `clusters.svd`,
    `alternates.svd`, `peripherals.svd` (the cases of the plan, as
    `RNG`, `A`/`B`/`C`, `X`/`Y`/`Z`/`W`, `P`/`Q`/`S`, plus a peripheral
    `over` the first of a list), `registers_unsupported.svd`, `header.svd`,
    `overlap_unresolved.svd` (expects `ty::peripheral-overlap`),
    `names.svd` (the `[%s]` list made by `dimIndex` is `ITEM[%s]`, not `foo2`,
    so as not to meet the register `FOO`; plus names meeting, clusters named
    as keywords, a leading digit, `%s_LEADING`), `access_values.svd`, and
    nine `errors_*.svd` (one error each, but `errors_invalid_name.svd` and
    `errors_invalid_dim.svd` with two or more). The command's tests: the
    default name (five inputs), an input in another directory, `-o` replacing
    a file, an output that is the input (by two spellings and by the default
    name), an error leaving an existing output alone, a file that is not
    UTF-8, warnings with success, and the command line's own errors.
  - **No new panic.** `src/svd/` still has none outside its tests (no
    `unwrap`, `expect`, indexing is by positions the writer made itself), so
    `PANICS` is unchanged; `tests/architecture.rs` only gains `svd` in the
    `driver` row, which ADR 0070 and the plan state.
  - **For step 4**: the fields and enums claim their names in the module's
    `Scope` (structs and enums) in `type_block`'s plan, before the clusters';
    `register` writes `u8`/`u16`/`u32` for every register and returns blocks of
    lines, which is where the struct's name replaces the integer; `register_mode`
