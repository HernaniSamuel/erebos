# Plan: M3.4a Register arrays and clusters

ADRs: 0064, 0065, 0066, 0067
Base: f961410
Program on QEMU: the PLIC's priorities, enable words and contexts, and
the eight virtio-mmio transports through one driver
(`tests/e2e/plic_virtio/`, step 8).
Out of scope:
- `svd2erebos`, its form (a tool of its own or a file read at compile
  time), its naming and what it does with what has no declaration, and
  the real chip's SVD generated and compiled in the tests: M3.4b
  (roadmap, pending decisions);
- SVD's write effects without a neutral value, reset values of
  registers without fields, arrays of bit fields and arrays of
  peripherals: not added (ADR 0067);
- unchecked indexing of register arrays, and indexing a pointer to a
  cluster's type (ADR 0064, Alternatives);
- checking at an access which view of a device (`over`) or which
  alternate group is in use (ADR 0061, 0066);
- moving the existing e2e programs to the new forms: `uart_fields/` and
  `peripherals/` stay as M3.3 left them.

Before step 1: the `docs(adr)` commit that accepts ADR 0064 to 0067 also
sets the status lines of the ADRs they amend, in the files as
`Accepted; amended by NNNN (what changed)`, appended to an existing
amendment list, and in the index (`docs/adr/README.md`) as
`Accepted, amended by ..., NNNN`:
- ADR 0048: amended by 0064 (steps, lengths of register and cluster
  arrays, and cluster types reaching a failed value are failed values;
  the peripheral types of a `ty::infinite-size` cycle reach one);
- ADR 0058: amended by 0064 (register arrays and clusters in a peripheral
  type, their layout, overlaps and accesses; `&raw` of a cluster; arrays
  of a peripheral type as a cluster's type only) and
  0066 (a peripheral `over` another is not checked for overlap with it);
- ADR 0059: amended by 0065 (a bit field may declare an access mode);
- ADR 0060: amended by 0064 (arrays of register types as register types;
  `step` in the register grammar) and 0065
  (fields follow their own access modes in volatile places);
- ADR 0061: amended by 0064 (a cluster may be in an alternate group).

The same commit holds the roadmap's edits written while planning: M3.4
split into M3.4a and M3.4b in the table of M3 steps, the M3 pending
decisions (what ADR 0064 to 0067 settle, what they leave to M3.4b), and
the status line naming M3.4a next.

Order: everything new in the syntax is parsed (1) and resolved (2);
register arrays and clusters are laid out and checked (3), their
accesses type checked (4) and built into MIR, code and compile-time
evaluation (5); field modes (6) and `over` (7) are independent of them
and of each other; the milestone program (8) needs all of them. Until
step 4 the type checker does not handle an access to a register array
or a cluster, and until step 5 MIR building does not: each stops there
with a `todo!` naming the step that removes it, as M3.2 and M3.3 did.
So the ui tests of steps 2 and 3 that accept code are `emit: typeck`
(or earlier) and none reaches an entry that is an array or a cluster in
a body. The fuzz test (`tests/fuzz.rs`) compiles every seed to LLVM IR,
so from step 2 until step 5 it leaves out the seeds whose peripheral
types have a register array or a cluster, as M3.3's `declares_bit_struct`
did; step 5 removes the filter.

## 1. feat(parser): parse register arrays, clusters, `step`, field modes and `over`
- Status: done
- Implements: the grammars of ADR 0064 ("Register arrays": `step`;
  "Clusters"), ADR 0065 (a bit field's mode) and ADR 0066 (`over`).
- Changes:
  - `src/syntax/ast.rs`: a peripheral type's entries are registers or
    clusters (a cluster: visibility, name, type, offset, optional step,
    optional group, span); `RegisterDecl` gains an optional step;
    `BitFieldDecl` an optional access mode with its span;
    `PeripheralDecl` an optional path after `over`. Array types need no
    change.
  - `src/syntax/parser.rs`: after an optional `pub`, an entry whose
    first word is followed by `:` is a cluster of that name; any other
    entry is a register, starting with its access mode (so `read: T` is
    a cluster named `read`, and `read write: u8` a read-only register
    named `write`, as M3.2's rule). `step` after the
    offset, recognized by its text, before the read effect and the
    group. A bit field's `read` or `write` before its name, with the same
    look-ahead; `read write` on a field is `parser::unexpected-token`.
    `over` and a path after a peripheral's address, before `;`.
    The missing-comma errors list what may still come, as M3.3's did,
    now with `step` after an offset. A missing comma before a `write`
    field (`write start: bool`) is the next field, not a write effect:
    `write_effect`, which today takes only `write :` for the next field,
    also takes `write NAME :` for it (a write-only field), so the error
    is still reported where the comma is missing. A `read` field after a
    missing comma is already the next field for `at_read_effect`
    (`read NAME :`).
  - `src/hir/lower.rs`, `src/hir/lower/hardware.rs`: steps, field modes
    and `over` are ignored for now, and clusters whose type is a
    peripheral type or an array of one skipped, each with a comment
    naming step 2, as M3.3's step 1 did. A cluster of any other type is
    already reported as step 2 will report it
    (`resolve::not-a-peripheral-type`, its help naming the missing
    access mode for a register's type, ADR 0064), so that a register
    written without its mode, an error since M3.2, is never accepted.
  - Snapshots that change: the three entries of
    `tests/ui/parse_peripheral_errors.ers` without an access mode
    (`rbr: u8`, `read: u8` and the recovery case) are no syntax error
    any more; they move to a new resolve test (below), and the parse
    test keeps its other cases, with its snapshot regenerated. The
    reference's sentence that such entries are syntax errors is changed
    in step 9.
- Tests (ui):
  - `parse_register_arrays.ers` (`emit: ast`): register arrays with and
    without `step`, with a read effect and a group after the step;
    clusters and cluster arrays, `pub` and private, with a group; a
    cluster named `read` and a register named `step`; a peripheral with
    `over` a name and a path.
  - `parse_register_arrays_errors.ers`: `step` without its value, `step`
    after the read effect, `over` without a path, `over` after `;`, a
    cluster with an access mode word misspelled, a missing comma after a
    step; each a `parser::unexpected-token` at the right token, with
    recovery reaching the next item.
  - `parse_field_modes.ers` (`emit: ast`): `read` and `write` fields,
    with `pub`, effects and defaults; fields named `read`, `write` and
    `step`; and in an errors file of its own, `read write` on a field and
    a mode after the name.
  - `register_array_names.ers` (`emit: typeck`): `step` and `over` as
    names of locals, functions, fields and modules still compile.
  - `resolve_missing_access_mode.ers`: the entries moved from
    `parse_peripheral_errors.ers`, with `u8`, a bit-field struct, an enum
    and `[u32; 2]` as types (`resolve::not-a-peripheral-type`, with the
    help naming the access mode, and for the array no
    `resolve::missing-step`), and a struct as type (the same code, no
    such help).
  - `parse_field_modes_errors.ers`: a missing comma before a `write`
    field and before a `read` field, reported at the comma's place.
- Decisions:
  - `PeripheralTypeDecl.registers` became `entries: Vec<EntryDecl>`, with
    `EntryDecl::{Register, Cluster}` and a `ClusterDecl` of its own, rather
    than one struct with an optional access mode: a cluster has no mode or
    read effect, and the plan says "registers or clusters". Every parse
    snapshot of a peripheral type changed shape (`Register(...)` wrapper,
    `step: None`), as did those of bit-field structs (`access: None`);
    reviewed as shape-only.
  - The parser's `register` lost its "found the register's name" branch:
    a name before `:` is now a cluster, so the error is only reached for a
    token that is no mode and no name. `REGISTER_HELP` says that an entry
    with no access mode is a cluster; `REGISTER_END_HELP` names `step`;
    `CLUSTER_HELP` is new; `BIT_FIELD_HELP` names the mode. These helps
    changed in the existing error snapshots.
  - `step` is recognized by `at_word("step")` with no `:` after it, so a
    cluster named `step` after a missing comma is the next entry and the
    comma is reported; `group` has the same test for `in`, a valid entry
    name, from the review.
  - A cluster takes no read effect: after its offset the missing-comma
    error lists `step`, `in`, `,`, `}`, and `read clears` there is a
    `parser::unexpected-token` at `read`.
  - A bit field's mode is `Option<(AccessMode, Span)>`, never
    `ReadWrite`; `read write x: T` reports at the second word
    ("expected the field's name") with a help of its own; a mode after the
    name is the existing "expected `:`".
  - `write_effect` also yields to `write NAME :` (a name followed by `:`),
    so the `write` field after a missing comma is reported at the comma.
    A write effect always has an integer after `write`, so no real effect
    is mistaken for a field.
  - `over` is an `Option<Path>` on `PeripheralDecl`; the missing `;` error
    says "`over` or `;`" when no `over` was read and "`;`" after one, and
    the peripheral help mentions `over`. `over` twice is that "`;`" error.
  - Lowering: `peripheral_type_decl` keeps only registers for the HIR and
    calls the new `cluster_ty` for each cluster. Only the innermost
    element type of a cluster's (possibly nested) array is judged: a
    peripheral type or `{error}` is skipped silently (step 2 lowers it);
    anything else is `resolve::not-a-peripheral-type` with the label "a
    built-in type / a struct / ... , not a peripheral type" ("an array of
    ..., not of a peripheral type" for arrays). Its help names the access
    mode when the type is one a register may have: `u8`/`u16`/`u32`, or a
    bit-field struct or an enum without payloads on one of them (checked
    on `hir::Ty`, whose bit-field and enum types carry their `int`, since
    `hir` may not use `layout`; from the review, a `u64` one got the help
    first); otherwise a help on what a cluster's type is. `u64`,
    structs, pointers and `Option(T)` get the second help.
    Array lengths, offsets, steps and groups of clusters are not lowered
    in this step, so errors in them appear in step 2. Clusters do not yet
    take part in `resolve::duplicate-register`.
  - No new panic: the `unreachable!` first written in `cluster_ty` was
    removed, and `PANICS` is unchanged.
  - Tests: `parse_peripheral_errors.ers` lost the errors of `NoMode`
    and `NamedRead`: `NamedRead` is deleted, and `NoMode { rbr: u8 at 0 }`
    stays as it is, with a comment saying it now parses and that
    `resolve_missing_access_mode.ers` shows how it is reported (it is
    `resolve::not-a-peripheral-type`, never reached by this test). And its recovery case at the end now has a real syntax error
    (`read rbr: u8 0`), so the recovery after `pub` is still tested.
    `resolve_missing_access_mode.ers` also has `u64`, a pointer and a
    `read: u8` (cluster named `read`) beside the plan's cases.
    `parse_register_arrays.ers` also covers clusters named `write` and
    `in` and registers `read write step` and `read step`.
    `parse_field_modes_errors.ers` holds the plan's second errors file
    (`read write` and a mode after the name) and the missing-comma cases.
    `parse_register_arrays_errors.ers` adds `step` twice, `step` after the
    group, a cluster with a read effect and `step` after a cluster's
    group.

## 2. feat(resolve): register arrays, clusters, field modes and `over` in the HIR
- Status: done
- Implements: ADR 0064, "Register arrays" and "Clusters" (names, types,
  `step`) and its first table; ADR 0065's modes carried into the HIR;
  ADR 0066's `over` resolved, with its table.
- Changes:
  - `src/hir/mod.rs`: an entry of a peripheral type is a register or a
    cluster, with an optional step (`ArrayLen`, as offsets are); a
    register's type may be an array of a register type, a cluster's a
    peripheral type or an array of one; `BitFieldDef` gains its mode;
    `PeripheralDef` the peripheral its `over` names.
  - `src/hir/lower/hardware.rs`: clusters, steps, `over`;
    `resolve::missing-step`, `resolve::misplaced-step`,
    `resolve::not-a-peripheral-type` for a cluster's type (step 1 has
    it already), alone for that entry, `resolve::duplicate-register`
    over every entry. A cluster's type is kept out of the type checker's
    `peripheral_by_value` (`src/ty.rs`), which already rejects a
    peripheral type as an array element, so `*const [P; 2]` stays
    `ty::peripheral-by-value` there, reported by the type checker, not
    while lowering.
    `resolve::not-a-peripheral`, `resolve::over-itself`.
  - `src/hir/lower/item.rs`: a bit field's mode.
  - Every match on entries handles clusters in this step, but the type
    checker's places (step 4) and MIR building (step 5), which stop with
    `todo!` at an access to an entry that is an array or a cluster.
  - `tests/fuzz.rs`: leaves out the seeds whose peripheral types have a
    register array or a cluster until step 5.
  - The `hir` dump shows entries, steps, field modes and `over`.
- Tests (ui):
  - `resolve_register_arrays.ers` (`emit: hir`): register arrays and
    clusters in a module, `pub` and private, the cluster's type from
    another module by a path; steps naming constants; `over` by a name
    and through `use`.
  - `resolve_register_arrays_errors.ers`: each code of the step: a
    cluster array without `step`, `step` on a register and on a single
    cluster, a cluster of type `u32` and of a struct, two entries named
    alike (a register and a cluster), `over` naming a constant and a
    struct, a peripheral over itself; `over` naming nothing and a
    private peripheral of another module (`resolve::unknown-name`,
    `resolve::private-item`); `*const [P; 2]` as a parameter's type.
  - `resolve_field_modes.ers` (`emit: hir`): modes in the dump.
- Decisions:
  - `PeripheralTypeDef.registers` became `entries: Vec<EntryDef>`, `RegisterDef`
    became `EntryDef { name, span, vis, kind, ty, ty_span, offset, step,
    group }` with `EntryKind::{Register { access, read_effect }, Cluster }`,
    rather than an enum of two structs: the fields every entry has are read
    without a match, as the type checker, the queries and MIR building do
    through the index of an entry, which stays the index of the field.
    `EntryDef::access()` and `read_effect()` are `None` for a cluster, and
    `is_cluster()` is the guard of the type checker. The `hir` dump, a
    `Debug` output, shows entries, steps, modes and `over` with no code of
    its own; the two existing HIR snapshots, `resolve_bit_struct` and
    `resolve_peripheral`, changed shape only (entries, `access: None` on
    bit fields, `over: None`). The third, `resolve_peripheral_duplicate_register`,
    is an errors snapshot, whose message and help changed (next entries).
  - `BitFieldDef.access` and `PeripheralDef.over` (`Option<(PeripheralId,
    Span)>`, the span being the path's) carry modes and `over`; an `over`
    that failed is `None`, reported.
  - Duplicate names are found in a pass over all entries before any is
    lowered, so a cluster and a register of one name are reported once
    in source order; the message now says "the entry `x`" and the help names
    register arrays and clusters. `resolve_peripheral_duplicate_register`
    changed for that. The values of an entry are lowered in the order type
    (array lengths), offset, step, as registers' type and offset were.
  - A register's type is lowered by `register_ty`, which follows arrays
    down to their innermost type and lowers that with `memory_ty` at the
    register position, so a peripheral type is allowed there and as the
    element of a register's array (`ty::register-type` in step 3); through
    the ordinary `ty` it would be `peripheral-by-value` with `{error}`.
    `!` inside a register's array is thus reported at the register
    position, not as an array element.
  - `cluster_ty` (step 1's check, now returning the type) judges the
    element of the cluster's array, one level only: an array of arrays
    (`[[P; 2]; 2]`) is `resolve::not-a-peripheral-type` ("an array of
    arrays, not of a peripheral type"), where step 1 judged the innermost
    type. ADR 0064 allows a peripheral type or one array of it. A bad type is
    lowered as `{error}`, the entry stays in the HIR with it (names count,
    layout fails silently), and its length is still lowered for its own
    errors. An unknown name inside is `{error}` and judged fine.
  - `resolve::missing-step` is labeled at the type ("an array of clusters")
    and at the offset ("`step DISTANCE` goes after the offset"), since no span
    of the missing `step` exists; `resolve::misplaced-step` at the step's
    expression (the `step` word has no span in the AST) and at the type.
    A cluster whose type was judged bad has neither, and a cluster whose type
    is `{error}` for an unknown name has them, judged by the written
    type's shape.
  - `over` resolves through `lookup_path` (so unknown paths and
    `resolve::private-item` are the usual ones); a last segment naming nothing
    is `resolve::unknown-name`, as where a value is named; a module is
    `resolve::misused-module`; a variant or any other item is
    `resolve::not-a-peripheral`; the peripheral itself is
    `resolve::over-itself`. `peripheral_decl` takes its own `PeripheralId`
    (the loop in `lower.rs` now counts) to find that. `over` of a later
    peripheral works, names being gathered first.
  - Until step 3, the layout code is unchanged: a cluster or a register
    array is no register type, so a type holding one gets
    `ty::register-type`, naming "the register" and no cluster help, and its
    layout fails. This is the interim the plan accepts ("until step 3");
    tests of this step are `emit: hir` for that reason, but for
    `typeck_cluster_array_by_value.ers`, which has no cluster. In the
    overlap check a cluster has no access mode (`access()` is `None`, never
    `apart`), ready for step 3. The `typeck` dump prints a cluster with no
    mode word.
  - Departure from the plan's "Order" paragraph, by the user's decision
    (from the review): the plan asked the type checker to stop with a
    `todo!` at an access to a register array or a cluster. `Checker::register`
    (`src/ty/place.rs`) instead returns the place as `{error}` with no
    diagnostic of its own when the entry named is a cluster or its type is an
    array of an integer, bit-field struct or enum (the accesses step 4
    types). A `todo!` was reachable from user input, as `UART.r[0]` with
    `r: [u32; 2]`, which before this step got `ty::register-type`; that broke
    ADR 0063 section 4 and the rule that user errors are diagnostics, never
    panics. (The first version of this step recorded the `todo!` and a
    `PANICS` entry as if they met ADR 0063; they did not.) Every program that
    reaches this path still has a diagnostic: the layout reports each such
    entry as `ty::register-type`, or the error of its failed value, and a
    cluster of a type that already failed has that type's error. So none is
    accepted, and MIR building needs no stop. `PANICS` is unchanged from
    before the step. `typeck_register_arrays_interim.ers` shows it for
    `[u32; 2]`, `[u64; 2]` and a cluster; step 3 replaces it with the real
    checks. Step 4 types the accesses and removes the early return.
  - `tests/fuzz.rs`: `declares_register_array_or_cluster` leaves out seeds
    with a peripheral type (`peripheral NAME {`, not a peripheral) holding an
    entry that is a name followed by `:` after an optional `pub` (a cluster,
    or a register missing its mode), or an `: [` (an array type). Text
    scanning, not parsing: a comment holding the same words leaves a seed out
    too, which is harmless. Step 5 removes it.
  - Tests: the plan's `*const [P; 2]` as a parameter in
    `resolve_register_arrays_errors.ers` cannot be there, since the
    error is the type checker's and `emit: hir` stops before it; it is
    `typeck_cluster_array_by_value.ers` (`emit: typeck`), with a by-value
    parameter `[Block; 2]` too, showing it is still reported there.
    `resolve_register_arrays_errors.ers` also has `over` naming a module
    and an array of a non-peripheral type; its other cases are the plan's,
    and `resolve_register_arrays.ers` also has a cluster in an alternate
    group, a private cluster and `over` by a full path.

## 3. feat(typeck): lay out register arrays and clusters
- Status: done
- Implements: ADR 0064, "Layout", "Failed values" and the second table
  of "What is checked".
- Changes:
  - `src/layout.rs`: `PeripheralLayout` holds each entry's offset, and
    for arrays their length and step; its extent and alignment count
    every element and clusters' layouts, every entry counting toward the
    alignment, arrays of 0 elements too. The extent saturates above 2³²
    (ADR 0064, "Layout"), so that nested arrays never overflow.
  - `src/query/hardware.rs`: computes steps and lengths at compile time;
    a cluster's layout is its type's, so a type that contains itself
    through clusters is `ty::infinite-size`, naming every type of the
    cycle, with the help of ADR 0064 (not the struct's, which suggests a
    pointer), and every type of the cycle reaches a failed value;
    `ty::register-type` for an array of arrays, with a help naming
    clusters, and for a peripheral type or an array of one, with a help
    saying a cluster has no access mode; `ty::misaligned-register` for
    an entry's offset against its element's alignment;
    `ty::misaligned-step`; `ty::step-too-small`, both reported when both
    apply, neither a failed value (the type keeps its layout, as with a
    misaligned offset); `ty::register-overlap` between entries, once per
    pair at the later entry, naming the first shared byte, the
    read/write and group rules of ADR 0064 applied, entries whose
    elements occupy nothing and entries whose step is too small left
    out. The overlap check walks the elements of the entry with fewer
    elements and finds by division the elements of the other they may
    meet, so its cost is the smaller length per pair of entries; the
    steps it divides by are never too small, so never 0 for elements
    that occupy bytes. A register type mentioning a type of an
    infinite-size cycle is silent, that cycle's error explaining it.
    Failed steps, lengths and cluster types make the type reach a failed value
    (ADR 0048), seen by the existing predicates, and the checks needing
    them are skipped.
  - `src/ty/dump.rs`: the `typeck` dump lists each entry with its
    offsets, length and step, and the type's extent and alignment.
- Tests (ui, `emit: typeck` where nothing is wrong):
  - `typeck_register_arrays.ers`: the dump of the PLIC of ADR 0064, a
    register array with a step larger than its width, two arrays
    interleaved (`a: [u32; 4] at 0 step 8`, `b: [u32; 4] at 4 step 8`),
    an empty array whose `u32` raises the type's alignment to 4, a
    cluster array of an empty type with step 0, a cluster without
    array, nested clusters, and a type whose extent is exactly 2³² with
    a peripheral of it at 0 (accepted).
  - `typeck_register_arrays_layout.ers`: a misaligned array offset, a
    step of 6 for a `u32`, a cluster step not a multiple of the
    cluster's alignment, a cluster step smaller than its extent, a step
    of 0 for a `u32`, an array of arrays, a register of a peripheral
    type: one error each; a step of 2 for a `u32`, misaligned and too
    small, two errors, and a function using that type with a known
    division by zero, still reported (a bad step is no failed value); a
    peripheral whose type's register array ends
    past 2³² (`ty::peripheral-out-of-range`), and one whose nested
    arrays' extent passes 2⁶⁴, reported as past 2³².
  - `typeck_register_arrays_overlap.ers`: a register inside an array's
    range, two interleaved arrays meeting at their tenth elements, a
    register in a gap of a cluster's registers (an overlap, ADR 0064), a
    `read` array and a `write` array sharing bytes and an array in
    another group (both accepted), a register against a cluster array
    with a `read` register inside (an overlap: a cluster has no mode), a
    cluster in a group over registers of none (accepted), two clusters
    of one group meeting (an overlap); and two interleaved arrays of
    2²⁰ elements each, checked in normal time.
  - `typeck_register_arrays_cycle.ers`: a peripheral type containing
    itself through a cluster, directly and through another type
    (`ty::infinite-size`, with its help), a peripheral of such a type, a
    function reading a register of it, and a register of type `*mut A`
    with `A` in the cycle, reporting nothing more.
  - `typeck_register_arrays_failed_values.ers`: a step and a length that
    fail, a cluster of a type reaching a failed value: each reported
    once, the checks needing them skipped, and a peripheral of such a
    type reporting nothing more.
- Decisions:
  - `layout::PeripheralLayout` keeps `offsets` (the first element of each
    entry, so every existing reader is unchanged) and gains `arrays:
    Vec<Option<(len, step)>>`; `peripheral_layout` takes `&[EntryPlace]`
    (offset, optional length and step, an element's size and alignment)
    instead of `(offset, width)` pairs. `EntryPlace` also owns the extent
    arithmetic (`end`, `exact_end`) and `layout::first_shared` finds the first
    shared bytes of two entries, so both are unit-tested without queries.
  - Saturation: an extent above 2^32 is stored as `PAST_ADDRESS_SPACE`
    (2^32 + 1), not 2^32, so that a saturated type still fails
    `address + extent <= 2^32` for any address. Diagnostics and the dump show
    it as "past 2^32". Since no `usize` step reaches it, a saturated cluster
    used as an array element is always `ty::step-too-small`, and its label
    says "more than 2^32 bytes". Nested arrays passing 2^64 therefore need
    steps that are too small in the test (`typeck_register_arrays_layout.ers`):
    the plan's case cannot be written with valid steps on this 32-bit target.
  - An entry that occupies nothing (0 elements, or elements of size 0) adds 0
    to the extent, as the ADR says; its element's alignment still counts.
  - `Geometry` (private to `query/hardware.rs`) holds one entry's computed
    offset, length, written step, normalized element type and (size,
    alignment) of an element. `peripheral_layout`, `check_peripheral_type`
    and the failed-value logic all read it, so they agree on what fails. A
    register array without `step` steps by the width; a cluster array
    without one (already `resolve::missing-step`) is a failed value, and so is
    a cluster whose type is not a peripheral type. A `step` written on an
    entry that is no array is not even evaluated: `resolve::misplaced-step`
    is its only error.
