# Plan: M5.7 Fewer raw pointers

ADRs: 0116, 0117 (building on 0014, 0024, 0031, 0053, 0077, 0085, 0090, 0094,
0095, 0105, 0108, 0110, 0111, 0114, 0115)
Base: d53244e
Program on QEMU: the e2e programs with references, the same output: every
program of `tests/e2e/`, on both targets at `-O0` and `-O`, written under the
rule of ADR 0117, with the same output and exit code as at the base, except
the panic locations (`file:line:column`) of the programs that print one,
which move with their lines in steps 4 to 6 (ADR 0117, "What the changes
may move").
Out of scope:
- a static placed in a named region, and handles into static arrays with
  range-typed indexes: deferred ideas, not built; the measurement (step 7)
  counts what each would remove (ADR 0117);
- returning a reference tied to the one reference parameter: not built; step 7
  records whether the measurement calls for its ADR (ADR 0117);
- marking the dereference of raw pointers (ADR 0030): moved to the pending
  decisions after M5 with the counts (ADR 0117);
- the ui tests, `tests/layout/`, the snippets of `tests/rejected.rs` and the
  generated programs of ADR 0068, but where ADR 0116 forces a change (an
  `assert` message, a panic function's parameter): not under ADR 0117's rule;
- the boards' UART and the NVIC as peripherals: left to a change of ADR
  0115's rule (ADR 0117, reason 5);
- the functions that print numbers (`print_u32` and the like): they take no
  pointer and stay in the programs (ADR 0117).

Before step 1: the `docs(adr)` commit that accepts ADR 0116 and 0117 also sets
the status lines of the ADRs they amend, in their files and in the index
(`docs/adr/README.md`), keeping each existing parenthesis:
- 0014: `Accepted; amended by 0053 (...), 0116 (the parameter is a
  `&core::PanicInfo`)`; index `Accepted, amended by 0053, 0116`.
- 0031: `Accepted; amended by 0053 (...), 0108 (...), 0116 (an `assert`
  message is a `&[u8]`)`; index `Accepted, amended by 0053, 0108, 0116`.
- 0053: `Accepted; amended by 0059 (...), 0085 (...), 0116 (the parameter is
  a `&core::PanicInfo`; it may not be `mut`)`; index `Accepted, amended by
  0059, 0085, 0116`.
- 0077: `Accepted; amended by 0079 (...), 0088 (...), 0117 (every board
  offers `print`)`; index `Accepted, amended by 0079, 0088, 0117`.
- 0095: `Accepted; amended by 0098 (...), ..., 0112 (...), 0116 (T8: the
  message is a `&[u8]`)`; index `Accepted, amended by 0098, 0103, 0104, 0107,
  0109, 0112, 0116`.
- 0105: `Accepted; amended by 0108 (...), 0110 (...), 0114 (...), 0116 (the
  panic function's parameter is a reference)`; index `Accepted, amended by
  0108, 0110, 0114, 0116`.
- 0108: `Accepted; amended by 0110 (...), 0116 (an `assert` message is a

- 0111: `Accepted; amended by 0116 (the call a check makes is not followed

The same commit holds this plan and the roadmap's edits written while
planning, if any.

Order: the two language changes of ADR 0116 come first (1, 2), each with every
use in the repository that it breaks, so that every later step writes the new
forms. `core` follows (3), alone, since every program links it. The board's
`print` (4) comes with the programs that use it, so that it is tested where it
lands. The remaining programs move by kind of address (5, 6); the measurement
(7) needs them done; the documentation is last (8). Each step gains a
`Decisions:` list while it is built (`/build-step`), for the choices it makes
that this plan and the ADRs do not dictate; steps 4 to 6 list there each
program they leave raw, with its reason of ADR 0117.

## 1. feat(ty): take an `assert` message as a `&[u8]`
- Status: done
- Implements: ADR 0116, "`assert` messages" and "In MIR" (T8, the cast into
  `PanicInfo.message`)
- Changes:
  - `src/ty.rs`: the `Assert` arm expects `&[u8]`; the mismatch of a raw
    slice type, and of `&raw const b"..."`, gains the help of ADR 0116.
  - `src/mir/build.rs`: `assert_panic` assigns `PanicInfo.message` the
    message cast to `*const [u8]`; the operand of `PanicCause::AssertionFailed`
    keeps the reference.
  - `src/mir/validate.rs`: T8 wants a `&[u8]` that is not volatile.
  - `src/eval.rs`: only if reading the message needs it (a `&[u8]` is laid
    out as a `*const [u8]`, ADR 0108).
  - Every `assert` with a message in `tests/ui/`, `tests/e2e/`, the Rust test
    sources (`tests/*.rs`, inline programs and snippets) and `src/` (unit
    tests, doc comments) written with `&b"..."` or `&*msg`; the snapshots
    they change.
- Tests:
  - ui: each type that converts (`&[u8; N]`, `&mut [u8; N]`, `&[u8]`,
    `&mut [u8]`, a sub-slice, a temporary `&f()`) accepted; a `*const [u8]`
    variable, `&raw const b"..."` and `&raw const buf` rejected, each with
    its help (`&*msg`, `&b"..."`, `&buf`); `&volatile [u8]` and `&[u32]`
    rejected; a failing `assert` with a `&b"..."` message at compile time
    (`eval::assertion-failed` shows it).
  - Analysis snapshots: a message borrowing a buffer while a `&mut` of it is
    in use (`analysis::borrow-conflict`), and once that `&mut` is no longer
    used (accepted); a message borrowing a `static mut` in the thread outside
    `critical` while a handler writes it (`analysis::unprotected-static`).
  - MIR snapshot: the operand of type `&[u8]` and the cast into
    `PanicInfo.message`.
  - Validator unit tests: T8 rejects a `*const [u8]`, a `&mut [u8]` and a
    `&volatile [u8]`, accepts a `&[u8]`.
  - e2e: `assert_message.ers` and `panic_assert_message.ers` print the same
    message at both levels on both targets.
- Decisions:
  - `src/eval.rs` needed no code change: `Eval::message` reads the operand's
    place as a (pointer, length) pair, and a `&[u8]` is laid out as one; only
    its doc comment names the type now. The new `eval_assert_messages` output
    proves it.
  - The help of ADR 0116 is built in `Checker::mismatch` (`src/ty.rs`), not in
    the `Assert` arm, because `check` reports the mismatch before the arm
    regains control. A new field `Checker::assert_message: Option<ExprId>` holds
    the id of the message being checked (saved and restored around the check,
    so a nested `assert` in a message block keeps its own); `mismatch` adds the
    help only when the mismatched expression is that message. Function
    arguments of the same raw types get no such help: the ADR scopes it to
    `assert`.
  - The three helps are chosen from what was written (HIR has no source text,
    so they name the forms with placeholders): `AddrOf` of a byte string says
    `&b"..."`; any other `AddrOf` says `&p` instead of `&raw const p` or `&raw
    mut p`; any other expression says `&*msg`. The condition is the found type:
    a non-volatile raw pointer to `[u8]` or `[u8; N]`, of either mutability. A
    `*const volatile [u8]` gets none, and a `&volatile [u8]` gets the existing
    help about volatile references.
  - `assert_panic` (MIR building) casts the message with `Builder::cast`, the
    function `as` uses: it makes the temporary `Cast(&[u8] -> *const [u8])`
    that ADR 0105 describes, and `PanicCause::AssertionFailed` keeps the
    reference operand. The cast is emitted only when the panic function takes
    the information (`self.located`), as the `PanicInfo` itself is.
  - The T8 violation message names `&[u8]`. The validator unit test builds its
    message locals itself (`message_of`) instead of extending `typed()`, so the
    numbering of the other tests' locals does not move; a `&mut [u8]` is moved
    (not copied) to avoid M1, and is rejected by T8 alone.
  - The wrong-argument-count help of `assert` (`hir/lower/expr.rs`) and the
    doc comments of `PanicCause` and `Eval::message` now say `&[u8]`.
  - Migration of existing programs: `&raw const b"..."` becomes `&b"..."`; a
    message that is a raw slice (a call, a parameter, a `const`) becomes
    `&*expr`, keeping the program's functions raw (they are step 4 to 6's).
    The e2e programs keep their line numbers, so no expected output moved.
    `tests/ui/mir_assert_message.ers` takes `&[u8]` and `&mut [u8; 3]`
    parameters, since it tests the conversions of the message.
    `slice_reference_conversion_errors.ers` loses its `assert(c, &b"msg")`
    line, which is accepted now (the rejected messages are in
    `typeck_assert_errors.ers`).
  - New ui tests: `typeck_assert_errors.ers` (rewritten: a `&[u16]`, `&volatile
    [u8]`, `&mut volatile [u8]`, a raw slice variable, `*mut [u8; 2]`, a
    volatile raw slice, `&raw const b"..."`, `&raw const buf`, `&raw mut buf`,
    `&raw const buf[0..2]`, each with the help it gets or none; `&buf[0..2]`
    and `&*p` accepted in the same file), `mir_assert_message_types.ers`
    (`&[u8]`, `&mut [u8]`, `&[u8; N]`, `&mut [u8; N]`, a sub-slice, `&mut`
    sub-slice, `&b"..."`, `&f()`, accepted, shown in MIR),
    `borrow_assert_message.ers` and `borrow_assert_message_accepted.ers`,
    `shared_static_assert_message.ers`. The `eval::assertion-failed` case with
    a `&b"..."` message is `eval_assert_messages.ers`.
  - `borrow_assert_message.ers`: the failing path runs nothing but the panic
    call, so a `&mut` is "in use" there only if the message itself uses it
    after the borrow; the conflicts are therefore written with a block message
    that borrows and then writes through the `&mut`. The accepted file shows
    both a `&mut` last used before the assertion and one used after it on the
    path where it holds (no conflict), which is the flow-sensitive reading of
    ADR 0116's "on the failing path only".
  - `shared_static_assert_message.ers` has the thread-context use outside
    `critical` (error) and the same inside `critical` (not reported).
  - `assertion_line` lines that `insta` adds are removed from the snapshots I
    accepted, as the repository's other snapshots have none.

## 2. feat(ty): the panic function takes a `&core::PanicInfo`
- Status: done
- Implements: ADR 0116, "The panic function"
- Changes:
  - `src/ty.rs`: `panic_params` accepts exactly `&core::PanicInfo`; the
    message and help of `ty::panic-param` name it.
  - `src/mir/mod.rs`, `src/mir/build.rs`, `src/codegen/`: comments that name
    `*const core::PanicInfo`; code only where it tests the parameter's type.
  - `rt/core.ers`: the comment on the panic function's signature.
  - Every panic function with the parameter in `tests/ui/`, `tests/e2e/` and
    the Rust test sources: `info: &core::PanicInfo`, `info.reason` for
    `(*info).reason`, `&*info.message` where a `&[u8]` is wanted (the local
    `print` still takes `*const [u8]` until step 4, so `info.message` is
    passed as it is there); the snapshots they change.
- Tests:
  - ui: `ty::panic-param` for `*const core::PanicInfo`, `&mut`, `&volatile`,
    and ADR 0053's cases (two parameters, another struct, by value);
    `mut info: &core::PanicInfo` as `ty::reference-position`; an explicit call
    passing `&info`; a handler in a module with `use core::PanicInfo;`.
  - Analysis snapshot: an explicit call `on_panic(&INFO)`, with `INFO` a
    static, followed by the check of calls (ADR 0111, as ADR 0116 restates
    it); a check's own call still not followed.
  - MIR snapshot `mir_panic_info`: the parameter of type `&core::PanicInfo`.
  - e2e: every `panic_*` program and the other programs that report a panic
    print the same reason, message, file, line and column.
- Decisions:
  - The validator's P5 (`src/mir/validate.rs`, `role`) tested the panic
    function's parameter as a thin raw pointer, and P8 (`panic_site`) read its
    pointee: both now read a `Ty::Ref` (its referent, not a slice for P5), as
    the parameter is one in MIR. A raw pointer is no longer valid there, since
    `ty::panic-param` rejects it before MIR is built. The P5 message says "not
    a thin reference". ADR 0095's table (P5: "one thin pointer") says the
    old form and ADR 0116 amends 0095 for T8 only; the table is left to step 8's
    reading of the ADRs and is flagged here. The unit tests: `with_panic_info`
    gives the panic function a `&Info`, and `p5_the_roles_have_their_shapes`
    gains "panic takes a raw pointer" and "panic takes a reference to a
    slice" as P5 violations.
  - `src/ty.rs` `panic_params` matches `Ty::Ref { mutable: false, volatile:
    false, referent: Struct(core::PanicInfo) }` and nothing else, so a
    `*const core::PanicInfo`, a `&mut`, a `&volatile` and a reference to a
    same-named struct all report `ty::panic-param`, with the new message and
    help (the help ends "(ADR 0053, 0116)"). `mut info: &core::PanicInfo`
    needs no code: `ty::reference-position` (`MutParameter`) already reports
    it, and `panic_params` accepts the type, so exactly one error is shown.
  - Nothing in `src/codegen/` or `src/mir/build.rs` tested the type of the
    parameter (`located` is `param_count == 1`), so only comments moved:
    `src/mir/mod.rs`, `src/query.rs` (two), `rt/core.ers`.
  - Migration of existing programs: `info: *const [core::]PanicInfo` becomes
    `info: &[core::]PanicInfo` and `(*info).f` becomes `info.f`, by a
    mechanical replacement over `tests/e2e/`, `tests/ui/` and `tests/elf.rs`;
    `info.message` and `info.file` are passed as they are to the programs'
    `print`, which still takes `*const [u8]` until step 4. `extern fn
    report(info: &core::PanicInfo)` in `codegen_panic_info.ers` follows (the
    reference is passed as a pointer; its LLVM IR snapshot did not change).
    The comments of `interrupt_table*.ers` and `mir_panic_info.ers` name the
    new type. No line moved, so no expected output of e2e changed.
  - ui tests: `typeck_panic_param_mut.ers` is now `&mut core::PanicInfo` and
    `typeck_panic_param_volatile.ers` `&volatile core::PanicInfo` (same file
    names, new snapshots); `typeck_panic_param_struct.ers` and
    `typeck_panic_param_two.ers` use `&`; `typeck_panic_param_by_value.ers`
    only has its comment changed. New: `typeck_panic_param_raw.ers` (the
    `*const core::PanicInfo` of ADR 0053 is rejected, its help names the
    reference), `typeck_panic_param_mut_binding.ers` (`ty::reference-position`).
    `typeck_panic_param.ers` loses its `mut` parameter (withdrawn by ADR
    0116), reads `info.line`, and calls `on_panic(&info)` explicitly from a
    module with `use core::PanicInfo;`.
  - Analysis snapshot `borrow_panic_explicit_call.ers`: the panic function
    writes `INFO.line` (a `static mut core::PanicInfo`); `by_name` calls
    `on_panic(&INFO)` and is `analysis::borrow-conflict-in-call`, while
    `by_check` holds `&INFO`, divides by a static zero and reads the reference
    afterwards, and is accepted (the check's own call is not followed). The
    write is of `INFO`, not of a static the reference was taken from, because
    the parameter is a `&` and cannot write through it; the conflict is the
    one a callee naming the lent static has.
  - `assertion_line` lines that `insta` adds are removed from the snapshots I
    accepted, as in step 1.

## 3. refactor(rt): lend the remainder of the 64-bit division by reference
- Status: done
- Implements: ADR 0117, "The rule" and reason 3
- Changes: `rt/builtins.ers`: `__erebos_udivmoddi4(n, d, rem: &mut u64)` and
  `__erebos_divmoddi4(n, d, rem: &mut i64)`, called with `&mut rest`; the
  comments on the `__aeabi_` divisions of `rt/arch/armv7m.ers` say that the
  slot they pass is what a reference needs. Nothing else in `rt/` moves:
  `memcpy` and its family (reason 3), the NVIC's addresses (reason 5), the
  fields of `PanicInfo` (reason 8).
- Tests: the e2e programs that divide 64-bit values (`c_division64.ers`
  through the `__aeabi_` functions on thumbv7m, and those dividing in
  Erebos) keep their output at both levels; the IR snapshots of `core`, if
  any change.
- Decisions:
  - `__erebos_udivmoddi4` and `__erebos_divmoddi4` take `rem: &mut u64` and
    `rem: &mut i64`; their bodies are unchanged (`*rem = ...` writes through a
    `&mut` as through a raw pointer), and the three callers
    (`__erebos_udivmod64`, `__erebos_divmoddi4`, the `sym` of the `__aeabi_`
    functions) pass `&mut rest` or the stack slot. The `__aeabi_` assembly is
    untouched: a `&mut u64` is passed as a pointer to its place (ADR 0108), which
    is the slot those functions already build. Their header comment in
    `rt/arch/armv7m.ers` says so (one sentence, not a comment per function).
  - The comment on `__erebos_udivmoddi4` says the remainder goes in the
    caller's slot, lent as `rem`; no other comment of `rt/builtins.ers` named
    the pointer. It keeps its six lines, so that no line of `core` moves and the
    `resolve_core` snapshot (which shows lines of `rt/builtins.ers`) is
    unchanged.
  - `docs/reference.md` (the "`core`" section's signatures of the two functions)
    is edited here, though step 8 owns the documentation, because the signatures
    are a fact of the code this step changes and the reference must not state
    the old one between steps. Step 8 has nothing more to do for these two
    lines.
  - No test was added or changed: the rule of the step is that the output does
    not move. No program calls these functions by name (they are private to
    `core`); `division64.ers` divides in Erebos (the functions of ADR 0076 on
    thumbv7m) and `c_division64.ers` through the `__aeabi_` functions, both in
    the full test run on both targets and levels, which is the test of the step.
    No IR snapshot of `core` changed.
