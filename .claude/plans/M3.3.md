# Plan: M3.3 Register fields

ADRs: 0059, 0060, 0061, 0062
Base: 9ab654c
Program on QEMU: the UART configured through its fields
(`tests/e2e/uart_fields/`, step 10).
Out of scope:
- register arrays, clusters, `derivedFrom`, and the check against a real
  chip's SVD file (M3.4);
- access modes of fields, the write effects without a neutral value
  (SVD's `clear`, `set`, `modify`), the reset value of a register
  without fields, and peripherals sharing addresses
  (`alternatePeripheral`): M3.4, with the SVD of a real chip (roadmap,
  pending decisions);
- range types and `newtype` (roadmap, deferred ideas), signed bit
  fields, nested bit-field structs, and default values for fields of
  ordinary structs (ADR 0059, Consequences);
- checking at an access that a register's alternate group is the mode
  the device is in (ADR 0061);
- moving the existing e2e programs to fields: `hello.ers` and
  `tests/e2e/peripherals/` stay as M3.2 left them.

Before step 1: the `docs(adr)` commit that accepts ADR 0059, 0060 and
0061 also sets the status lines of the ADRs they amend, in the files as
`Accepted; amended by NNNN (what changed)`, appended to an existing
amendment list, and in the index (`docs/adr/README.md`) as
`Accepted, amended by ..., NNNN`:
- ADR 0017: amended by 0059 (a literal operand of `as` with a bit-field
  struct as its target takes the struct's integer type);
- ADR 0019: amended by 0059 (a bit-field struct converts to integers, and
  from its own integer type);
- ADR 0021: amended by 0059 (`..` in a literal of a bit-field struct;
  bit fields are not taken by `&raw`);
- ADR 0022: amended by 0059 (a bit-field struct has its integer type's
  layout; its fields have no byte offset);
- ADR 0023: amended by 0059 (a bit-field struct is a scalar);
- ADR 0025: amended by 0059 (a bit-field struct crosses calls as its
  integer type);
- ADR 0032: amended by 0059 (a known value that does not fit its field
  is an error; no value of a bit-field struct is known);
- ADR 0035: amended by 0059 (an enum field of a bit-field struct made
  with `as` gives values that are no variant without memory);
- ADR 0036: amended by 0059 (field reads are a source of values that
  are no variant besides memory);
- ADR 0048: amended by 0059 (bit positions and bit field types in error
  are failed values);
- ADR 0050: amended by 0059 (`..` may leave out an invisible field that
  has a default or a write effect);
- ADR 0053: amended by 0059 (the panic reason `FieldOutOfRange`);
- ADR 0058: amended by 0060 (register types, fields reached through
  registers, read effects) and 0061 (registers in alternate groups may
  share bytes).

The same commit holds the roadmap's edits written while planning: the M3
pending decisions (what ADR 0059 to 0061 settle, what they leave to
M3.4) and the deferred idea of Ada-inspired types (representation
clauses done; range types and `newtype` remain).

Order: bit-field structs are parsed with everything new in the syntax
(1), resolved (2), their values computed and checked (3), their uses type
checked (4) and built into MIR (5), and run on QEMU (6), before ADR
0060's registers with fields are checked (7) and built (8), and ADR
0061's groups relax the overlap check (9); the milestone program (10)
needs all of them. Until step 4 the type checker does not handle an
expression whose type is a bit-field struct, and until step 5 MIR
building does not handle `Ty::BitStruct`: each stops there with a
`todo!` naming the step that removes it, as M3.2 did. So the ui tests
of steps 2 to 4 that accept code are `emit: typeck` (or earlier), and
none puts a bit-field struct in a constant, a static or a `comptime`
block, which are built into MIR and evaluated during type checking. The
fuzz test (`tests/fuzz.rs`) compiles every seed to LLVM IR, so from step
2 until step 5 it leaves out the seeds that declare a bit-field struct,
as M3.2's `declares_peripheral` did (the user's decision then); step 5
removes the filter. Code generation needs no step of its own: a
bit-field struct is its integer in MIR, and its fields shifts and masks.

## 1. feat(parser): parse bit-field structs, `..` in literals, and register effects and groups
- Status: done
- Implements: the grammars of ADR 0059 ("Declaration", "Values and
  literals": `..`), ADR 0060 ("Write effects", "Read effects") and ADR
  0061 (`in NAME`).
- Changes:
  - `src/syntax/token.rs`, `src/syntax/lexer.rs`: the tokens `..` and
    `..=`; `0..=1` lexes as an integer, `..=`, an integer.
  - `src/syntax/ast.rs`: `Item::BitStruct(BitStructDecl)` (attributes,
    visibility, name, integer type, fields, span) with `BitFieldDecl`
    (visibility, name, type, bits as a low expression and an optional
    high one, an optional read effect and write effect with their
    spans, an optional default, span); `ReadEffect` (`Clears`, `Sets`,
    `Modifies`) and `WriteEffect` (the bit written, 0 or 1, and
    `Clears`, `Sets` or `Toggles`); `RegisterDecl` gains an optional
    read effect and an optional group name; a struct literal records
    the span of a final `..`.
  - `src/syntax/parser.rs`: `struct NAME :` starts a bit-field struct,
    `struct NAME {` an ordinary one. A bit field needs `at`; in an
    ordinary struct, `at` or `=` after a field's type is
    `parser::unexpected-token` with a help naming bit-field structs.
    The ends of the bits are parsed above the binding power of
    assignment, so that the `=` after them always starts the default
    (`expr` would read `at 7 = false` as an assignment). Effects after
    the bits, in the order of ADR 0060's grammar, then the default;
    after a register's offset, its read effect then `in NAME`. The bit
    of a write effect is an integer literal of value 0 or 1. `read`,
    `write`, `clears`, `sets`, `toggles`, `modifies` and `in` are
    recognized there by their text only (`word_at`, `at_word`), so they
    stay ordinary names elsewhere. `..` may end a struct literal, alone
    or after a comma following its fields.
  - `src/hir/lower.rs`: skips bit-field structs for now, and ignores
    register effects, groups and `..`; step 2 lowers them.
- Tests (ui):
  - `parse_bit_struct.ers` (`emit: ast`): bit-field structs on `u8` and
    `u32` with `pub` and private fields, single bits and ranges, bits
    naming constants, defaults (a literal, `.V`, a constant) after bits
    that are a literal, a name and a binary expression
    (`at BASE + 1 = false`), each read effect and each of the six write
    effects, `write 0x1 clears`, a field with both effects, a trailing
    comma, fields named `read`, `write` and `at`; an empty bit-field
    struct (parsed; step 2 reports it); a literal with `..`, alone and
    after fields.
  - `parse_bit_struct_errors.ers`: a bit field without `at`, `at 0..`
    without its end, `at 0..1` (a half-open range is no bits),
    `write 2 clears`, `write 1 erases`, `read toggles`, two read
    effects, two write effects, an effect after the default, `..`
    before a field in a literal, `f: v ..` without the comma, and `at`
    and `=` in an ordinary struct's field: each a
    `parser::unexpected-token` at the right token, with recovery
    reaching the next item.
  - `parse_register_effects.ers` (`emit: ast`): registers with each
    read effect, with `in NAME`, with both, and the names `in`,
    `clears` and `modifies` for registers and groups; a register with
    two read effects (an error, in `parse_bit_struct_errors.ers`).
  - `bit_struct_names.ers` (`emit: typeck`): `clears`, `sets`,
    `toggles`, `modifies` and `in` as names of locals, functions,
    fields and a module still compile.
- Decisions:
  - The lexer reads `..` and `..=` from a `.` followed by `.`, with
    `with_eq` as for the other operators; `...` lexes as `..` and `.`.
    A unit test (`ranges_and_rests`) shows `0..=1` as three tokens.
  - AST shapes: `WriteEffect { bit: u8, action: WriteAction }`, with
    `WriteAction` (`Clears`, `Sets`, `Toggles`) a separate enum and
    `bit` a `u8` (0 or 1, the only values the parser accepts) so that
    dumps print the bit as written; effects are stored as
    `Option<(effect, Span)>`, the span covering their words
    (`read clears`, `write 1 clears`); the group as `Option<Ident>`;
    `ExprKind::StructLit` gains a third element, `Option<Span>`, the
    span of `..`, rather than becoming a variant with named fields, to
    keep the change to its users small. `ReadEffect`, `WriteEffect` and
    `WriteAction` are `Copy` so that step 2 can re-export them in the
    HIR, as `AccessMode` is.
  - `struct_item` reads `struct NAME` and dispatches on `:` (bit-field
    struct) or anything else (an ordinary struct, whose `{` is then
    expected as before). The field visibility moved into a helper,
    `field_visibility`, shared by both kinds of fields.
  - The ends of the bits are parsed with `expr_bp(ASSIGN_BP.0 + 1)`
    (`bit_end`), so `=` and the compound assignments end them. A
    `comptime` end still covers everything to its right, as everywhere
    (ADR 0029), so `at comptime X = false` reads the `=` into the
    `comptime` expression; bits are computed at compile time anyway, so
    nothing needs `comptime` there, and `(comptime X)` works.
  - `at 0..` and `at 0..1` are the same error, `expected `..=`, found
    `..``, at the `..`, with a help on the two forms of bits; `at 0..=`
    without its end is the ordinary "expected an expression". The test
    has all three.
  - A bit field checks the token after it itself: anything but `,` or
    `}` is `parser::unexpected-token` listing what may still come at
    that point in the grammar's order (`..=` only when no high end was
    written, `read` before any effect, `write` before a write effect,
    `=` before the default). So two read effects report "expected
    `write`, `=`, `,` or `}`" at the second `read`, two write effects
    "expected `=`, `,` or `}`" at the second `write`, and an effect
    after the default "expected `,` or `}`". The errors at the field's
    own words (`:`, `at`, the effects) and at the token after the field
    carry `BIT_FIELD_HELP`, which gives the whole field grammar; the
    errors at `..` carry `BITS_HELP`; errors inside a name, a type or an
    expression (`at 0..=` without its end) carry the help those parsers
    give, if any. (Reworded after review.)
  - A `read` after a register's offset or a bit field's bits starts a
    read effect unless it starts the next register or field after a
    missing `,`: `read:` (a field named `read`), `read NAME:` (a `read`
    register) and `read write` (a `read write` register)
    (`at_read_effect`). Likewise a `write` followed by `:` is the next
    field, not a write effect. So the missing `,` is reported where it
    is missing, with the list of what may come there, as M3.2 reported
    it, instead of "expected `clears`, `sets` or `modifies`" at the next
    name; and `read toggles` is still reported at `toggles`. The
    reviewer suggested taking `read` as an effect only when an effect
    word follows; that would report `read toggles` at `read` with a list
    naming `read` itself, so the look-ahead is on the next declaration
    instead. `parse_bit_struct_errors.ers` has a missing `,` before
    `read b:`, `read write b:`, a field `read:` and a field `write:`.
    (From review.)
  - A write effect's bit that is an integer literal of another value is
    reported at the literal ("expected `0` or `1`"); one that is not an
    integer literal at the token, as a missing one. A literal the lexer
    already rejected (`write 01 clears`) is not reported again: the
    parser recovers silently, since the lexer's error stops the build.
  - Registers check the token after them the same way (`read`, `in`,
    `,`, `}` as they still may come), with a new help on the read effect
    and the group (`REGISTER_END_HELP`), instead of
    `peripheral_type_decl` expecting `,` or `}` with `REGISTER_HELP`.
    This changes the missing-comma error of M3.2's
    `parse_peripheral_errors.ers` and `parse_local_peripheral.ers` from
    "expected `,` or `}`" to "expected `read`, `in`, `,` or `}`", since
    after an offset a read effect or a group may now come.
  - A register's span now ends at its last token (its group, effect or
    offset) instead of at its offset's expression; the two agree for
    every M3.2 register.
  - In an ordinary struct, `at` or `=` after a field's type is reported
    at that token as "expected `,` or `}`", the help saying that bits
    and defaults belong to bit-field structs and showing
    `struct Lcr: u8 { ... }`. `at` is matched by its text after the
    type, so a field named `at` stays accepted.
  - Struct literals are parsed by `struct_lit_fields` rather than
    `brace_list`. `..` followed by anything but `}` (a field after it, or
    a trailing comma) is "expected `}`" at that token; `f: v ..` without
    the comma is "expected `,` or `}`" at the `..`; both with a help on
    where `..` goes. A missing comma before anything else keeps M3.2's
    "expected `}`", so no existing snapshot changes there.
  - HIR lowering skips `Item::BitStruct` (its name is not declared, so a
    use of it is an unknown name until step 2) and ignores the `..` of a
    literal and register effects and groups, each with a comment naming
    step 2 (in `lower.rs`, `lower/expr.rs` and, added after review,
    `lower/hardware.rs`). The AST dumps of M3.2's tests gain `read_effect: None`,
    `group: None` and the literal's `None`: those snapshots changed only
    there.
  - The error test also has `..=` without its end and, as its last item,
    `write` without its bit, so that recovery after the errors before it
    is shown reaching the next item.

## 2. feat(resolve): bit-field structs in the HIR
- Status: done
- Implements: ADR 0059, "Declaration" (names, visibility, integer types,
  attributes) and the `..` rules of "Values and literals"; the first
  table of "What is checked"; the register effects and groups of ADR
  0060 and 0061 carried into the HIR.
- Changes:
  - `src/hir/mod.rs`: `BitStructDef` (path, name span, module,
    visibility, reachability as for structs, integer type, fields) and
    `BitFieldDef` (name, span, visibility, type and its span, bits as
    `u32` values computed at compile time in the item's module, as
    register offsets are, the read and write effects, the default as a
    value of the field's type computed at compile time);
    `Ty::BitStruct(BitStructTy)`, a type of its own rather than
    `Ty::Struct`, so that every match on types handles it (layout, ABI,
    volatile checks); `RegisterDef` gains its read effect and its group;
    the HIR struct literal records `..`.
  - `src/hir/lower/item.rs`: the item in its module's namespace;
    `resolve::bit-struct-type`, `resolve::empty-bit-struct`,
    `resolve::duplicate-field`, `resolve::misplaced-attribute`,
    `resolve::write-effect-default`. A bit
    field's type is a new position of `never_in_memory`,
    `unsized_types` and `peripherals_by_value`, so that `!`, `[T]` and
    a peripheral type there are reported as in other fields.
  - `src/hir/lower/expr.rs`: a literal naming a bit-field struct; with
    `..`, the fields left out take their defaults, or for a field with
    a write effect its neutral value, and one with neither is
    `resolve::missing-default`, as is `..` in an ordinary struct's
    literal; `resolve::missing-fields` gains a help offering `..` when
    every field left out has a default or a write effect. With `..`, an
    invisible field left out is no `resolve::private-field` when it has
    a default or a write effect (ADR 0059 amending 0050).
  - `src/hir/lower/hardware.rs`: a register's read effect and group.
  - Every match on `Ty` handles `Ty::BitStruct` in this step: its layout
    is its integer type's from now on (it needs no computed value), it
    reaches no failed value until step 3 adds them, and dumps show its
    path. The only `todo!`s are for expressions of a bit-field struct
    type in the type checker (step 4) and for `Ty::BitStruct` in
    `Queries::mir_ty` (step 5).
  - `tests/fuzz.rs`: leaves out the seeds that declare a bit-field
    struct (a line starting, after indentation and an optional `pub`,
    with `struct NAME:`) until step 5.
  - The `hir` dump shows bit-field structs, register effects and groups.
- Tests (ui):
  - `resolve_bit_struct.ers` (`emit: hir`): a bit-field struct in a
    module with `pub` and private fields, used from another module by a
    path and through `use`; bits and defaults naming constants of its
    module; a peripheral type with register effects and groups.
  - `resolve_bit_struct_errors.ers`: `resolve::bit-struct-type` for
    `i8`, `usize`, `bool`, a struct and an enum after `:`;
    `resolve::empty-bit-struct`; a duplicate field; `#[packed]` and
    `#[align(4)]`; a default on a field with a write effect; a
    bit-field struct named like another item
    (`resolve::duplicate-item`).
  - `resolve_struct_rest.ers` (errors of name resolution only, so no
    body is type checked): a literal with `..` leaving out a field without a
    default, `..` in an ordinary struct's literal
    (`resolve::missing-default` each), a literal without `..` leaving
    out fields that all have defaults or write effects
    (`resolve::missing-fields`, its help offering `..`) and one leaving
    out a field without either (no such help); from another module, a
    literal with `..` leaving out private fields with defaults and a
    write effect (accepted, in `resolve_bit_struct.ers`), and ones
    naming a private field or leaving out a private field without a
    default (`resolve::private-field`).
  - `typeck_bit_field_never_unsized.ers` (`emit: typeck`): `!`, `[u8]`
    and a peripheral type as a bit field's type, one error each.
- Decisions:
  - HIR shapes: `BitStructId` indexes `Hir::bit_structs`, which follows
    `structs` in the HIR and in its dump; a bit-field struct is
    `Def::BitStruct` in its module's namespace, lowered after the structs
    of its part (program, then `core`). `BitStructTy` carries the integer
    type (`id`, `name`, `int`), as `EnumTy` does, so that its layout needs
    no lookup. `BitStructDef` has `path`, `name_span`, `module`, `vis`,
    `reachable`, `ty` and `int_span` (the span of the type after `:`, kept
    as `RegisterDef` keeps `ty_span`, for the checks of step 3), and its
    fields. `BitFieldDef` has `name`, `span`, `vis`, `ty`, `ty_span`,
    `low` and `high` as `(ArrayLen, Span)`, the effects as
    `Option<(effect, Span)>` and `default` as `Option<(FnId, Span)>`.
    `ReadEffect`, `WriteEffect` and `WriteAction` are re-exported from the
    AST into the HIR, as `AccessMode` is; a register's group is
    `Option<(String, Span)>`.
  - Bits are lowered as register offsets are (`ArrayLen`): known for a
    literal that fits in `u32`, else a body returning `u32`, named `bits`
    in the dumps; a literal too large gets a body, so that type checking
    reports it as a constant's. `comptime_usize` became a wrapper of
    `comptime_int` (any integer type) and `comptime_value` (any type, for
    any `Comptime`). A default is always a body (named `default`, its
    return type the field's), a literal too, since its type is the
    field's. Both go among the bodies of values computed at compile time,
    after every other, so no count is needed before lowering.
  - These bodies are `Comptime::Bits(struct, field)` (both ends of one
    field) and `Comptime::Default(struct, field)`, not `Comptime::Value`:
    `check_all` evaluates every `Value` body as a `usize`, and these must
    wait for step 3's queries and their cycles. Until then they are type
    checked and built into MIR as every body is, never evaluated.
    `describe` names them "the bits of the field `P::f`" and "the default
    of the field `P::f`".
  - A literal of a bit-field struct is a variant of its own,
    `ExprKind::BitStructLit(BitStructTy, fields, Option<Span>)` with the
    span of `..`, rather than `..` added to `StructLit` as the plan's
    wording suggests: `..` in an ordinary struct's literal is always
    `resolve::missing-default`, which stops the pipeline, and steps 4 and
    5 check and build a bit-field struct's literal unlike an ordinary one.
    The `typeck` dump labels it `struct P` or `struct P ..`.
  - `Ty::BitStruct` in every match: its layout is its integer's
    (`layout::of`); it is no aggregate; it displays as its path; operators
    reject it (`require`, for step 4's `ty::invalid-operand`);
    `resolve::not-a-peripheral-type` labels it "a bit-field struct", as
    `Def::what` names it. Matches with a wildcard (`lacks_layout`,
    `mentions_peripheral`, `over_aligned`) leave it reaching no failed
    value until step 3.
  - Placeholders: the type checker stops with `todo!` (step 4) where an
    expression's type is recorded and is a bit-field struct
    (`values_of_bit_structs`, called from `check` and `place_info`), at
    `BitStructLit`, and at `offset_of` of a bit-field struct, which would
    otherwise report `ty::no-fields` instead of step 4's
    `ty::bit-field-offset` (not an expression of the type, so one more
    than the plan lists). `Queries::mir_ty` has the `todo!` of step 5; MIR
    building's `BitStructLit` arm is `unreachable!`, since `ty_of` reaches
    `mir_ty` first.
  - `resolve::bit-struct-type` is checked as `resolve::enum-type` is: the
    type after `:` must be one name among `u8`, `u16`, `u32` and `u64`;
    anything else, an unknown name included, is reported without being
    resolved, at the type ("not `u8`, `u16`, `u32` or `u64`"), and the
    struct gets `u8` as a placeholder. `resolve::empty-bit-struct` is
    reported at the name, worded as `resolve::empty-enum`.
  - Attributes: `#[packed]` and `#[align(N)]` are
    `resolve::misplaced-attribute` with a message of their own ("does not
    apply to a bit-field struct") and a help on the layout, since the
    shared one says they apply to structs; `#[export]` and unknown
    attributes are reported as on other items.
  - `resolve::write-effect-default` points at the default and labels the
    write effect; the default is lowered all the same, so that errors in
    it are reported. `resolve::duplicate-field` is shared with ordinary
    structs through a helper, `duplicate_fields`.
  - A bit field's type is a new `NeverPosition::BitField`, "the type of a
    bit field", with a help of its own for `!` ("a bit field is a `bool`,
    an integer type or an enum without payloads"): the help of other
    fields suggests `()`, which is no bit field type.
  - Literals (`struct_lit`, with `LitOf`, `LitDecl` and `LitField` over
    both kinds of structs): `..` in an ordinary struct's literal is one
    `resolve::missing-default` at the `..` ("the fields of `S` have no
    defaults"), whatever it leaves out, and no `resolve::missing-fields`.
    The visibility check runs before the defaults, so a field left out by
    `..` that is not visible and has neither a default nor a write effect
    is `resolve::private-field` (ADR 0059's table keeps
    `resolve::missing-default` for visible fields), labeled "declared here
    without `pub` or a default"; the help of `resolve::private-field` for
    a bit-field struct says what `..` leaves out. Visible fields left out
    by `..` without either are one `resolve::missing-default` listing
    them, at the `..` and at each field's name. `resolve::missing-fields`
    offers `..` only when every field left out has a default or a write
    effect.
  - `resolve::duplicate-item`'s help is unchanged: "structs" covers
    bit-field structs, and no snapshot changes for it.
  - `reachability` gained a fifth list of items; to stay within clippy's
    argument limit, the four lists became a struct, `Reachable`, whose
    `of` gives an item's `reachable`.
  - The fuzz filter is `declares_bit_struct`: a line that starts, after
    its indentation and an optional `pub`, with `struct`, a name and `:`.
  - Tests: `resolve_bit_struct.ers` also has a literal with `..` that
    leaves out no field (inside the struct's module) and the struct as a
    register's type (checked in step 7). `resolve_bit_struct_errors.ers`
    also has `#[export]`, and the struct as a peripheral's type and as a
    value, to snapshot the new labels of `resolve::not-a-peripheral-type`
    and `resolve::unknown-name`. `resolve_struct_rest.ers` has `..`
    leaving out one and two fields without defaults (both messages), and
    from another module a literal without `..` leaving out private fields
    that have defaults (`resolve::private-field`, not
    `resolve::missing-fields`). The `hir` snapshots of `resolve_ok.ers`,
    `resolve_memory.ers` and `resolve_peripheral.ers` gain
    `bit_structs: []`, and the last one `read_effect` and `group` for
    each register.

## 3. feat(typeck): compute and check bit-field structs
- Status: done
- Implements: ADR 0059, "Declaration" (bits, widths, overlap), the
  defaults of "Values that do not fit", "Layout" (size and alignment),
  "Failed values", and the second table of "What is checked".
- Changes:
  - `src/layout.rs`: a helper giving the bits a field type can hold and
    needs (`bool`, integers, an enum by its integer type and its
    variants), with unit tests; the layout itself is step 2's.
  - `src/query/bit_struct.rs` (new, beside `src/query/hardware.rs`):
    computes each field's bits, and whether the struct reaches a failed
    value, in one query, and its defaults in another, so that a default
    needing only the struct's bits (`= size_of(Lcr) == 1`, or a field of
    a constant of the type) is no cycle (as ADR 0062 states, amending
    0059); and checks every bit-field
    struct of the program, used or not: `ty::bit-field-type`,
    `ty::reversed-bit-range`, `ty::bit-field-outside`,
    `ty::bit-field-width`, `ty::bit-field-overlap` (once per pair, at the
    later field, labeling the earlier) and `ty::field-value-out-of-range`
    for defaults; a bit position or default needing the struct's own
    bits is `ty::cycle` (ADR 0062 makes this the struct's bits, meaning
    its bit positions, field types and enum field variants, needing
    those bits, or a default needing its own value). A default reported in error is recorded as

    `query/bit_struct.rs`): field reads, field writes, compound
    assignments, literals and their checks. `build.rs` only dispatches, by
    arms guarded with `Tables::bit_field` (a field read in `expr_kind`, an
    `Assign` and a `CompoundAssign` whose place is a bit field), and
    `place_then` leaves a bit field to the value arm, since it is no place.
  - HIR: a bit-field struct literal's fields became
    `(u32, Span, Expr)`, with the span of each field's name, so that the
    run-time check is located at the field's name in the literal, as ADR
    0059 says; an assignment has it in `ExprKind::Field`. The `hir` dump of
    `resolve_bit_struct.ers` gains these spans; `Expr::walk` gives the two
    literals arms of their own.
  - Field read: one copy of the whole value into a temporary; a `bool`
    field is `BitAnd` with its bit's mask then `Ne` 0 (no shift, one
    operation fewer); any other field is `Shr` by its low bit (left out at
    0), `BitAnd` with its largest value (left out when the field reaches
    the integer's top bit) and a `Cast` to its type when that is not the
    integer's (`u64` in a `u8`, `u8` in a `u32`, an enum on another
    integer). Shift amounts are `u32` constants, as written in source.
  - Field write: the field's bits cleared (`BitAnd` with the other bits),
    the value cast to the integer and shifted up, `BitOr`. A field covering
    every bit of its integer keeps nothing of the copy, which is still
    made: ADR 0059's order has the read of the whole value before the
    write, and through a volatile pointer that read is a load.
  - Which writes are checked: those whose field type's bits
    (`layout::bit_field_holds`) differ from the field's width. That leaves
    out a `bool` and a type exactly as wide as the field, an enum's
    integer type included (an enum on `u8` in eight bits holds any `u8`);
    an enum on a wider integer is checked, since a value that is no
    variant can fail (ADR 0059). The check is `Le(value, max)` in the
    field's type and `panic_unless(.., FieldOutOfRange, name)`; its
    statements and terminator carry the span of the field's name, so a
    failure at compile time points there too. `src/eval.rs` needed no
    change: every cause but an assertion is reported as `eval::panic` with
    `PanicCause::describe`, "value does not fit its field".
  - Known values: a known value that fits gets no run-time check; one
    that does not is `ty::field-value-out-of-range` where ADR 0032's
    checks apply, and keeps its run-time check (in code that cannot run,
    as `divide` keeps the panic of a known zero divisor). Wording, as the
    default's of step 3: "the value written to the field `count` does not
    fit in its bits", labeled at the value ("`16` needs 5 bits") and at
    the field's bits ("4 bits, holding 0 to 15"), help on masking and the
    panic at run time. `bit_count` and `max_value` of
    `query/bit_struct.rs` became `pub(crate)`, re-exported by `query`.
  - `compute_known` returns `Unknown` first for any expression whose HIR
    type is a bit-field struct (`Tables::expr_ty`), before the MIR type is
    looked at.
  - Literals: there is no `BitOr` with 0: the first value that is not a
    constant starts the result; values that are constants (`true`, a
    literal, a variant) are placed at compile time and folded with the
    fields `..` fills into one constant, or-ed in last, so a literal of
    constants only, `Control { .. }`, is one constant. A value is read
    into a temporary when a later value is not simple, as `operands` does;
    in an assignment, when the base is not simple.
  - Defaults: `filled_bits` stops at the first default in error, the body
    being unused already: asking for the defaults after it could reach
    one that is in progress in the same cycle and report it again, headed
    by that default (as `Crossed`'s `dlab` would be).
  - The `mir` dump: `Mir::bit_structs` (`mir::BitStruct`, `BitField`),
    listed after structs and before enums, as
    `struct P: u8 { f: u8 at 0..=1, g: bool at 7 }`: each field with its
    MIR type (an enum shows as its integer) and its bits, no defaults, no
    effects; `LeftOut::bit_structs` leaves out `core`'s.
  - The e2e panic functions' new arms print "value does not fit its
    field", the `describe` text, as their other arms do.
  - Tests: `mir_bit_field_known.ers` writes
    `(comptime { 40 as Lcr }) as u32`: without the parentheses `comptime`
    covers the cast too (step 1), and is a known `u32`. The cycle cases
    use structs of their own (`Positioned`, `Itself`, `Crossed`, `B` and
    `Outer`), `Crossed` declaring `parity` before `dlab` so that `CD`'s
    literal takes `parity`'s default first and the cycle is headed by
    `CC`. `Positioned`'s cycle (`at L as u32`) is headed by its bit
    layout, not by `L`, and does not name `L`: the bits' body has an
    expression of type `Positioned`, so building it asks for
    `Positioned`'s bits (ADR 0048) before `L`'s value; `L` fails with the
    struct. The plan had predicted `L` at its head; the user decided, after
    review, to keep the cycle as built, and the Tests text above was
    corrected. The other three are headed by the constant, as planned. The
    cycle file also has `defaults`, whose literals take the defaults that
    failed and are built (checked by hand: a division by zero added there
    is reported) reporting nothing, and `failed`, not built.
    `mir_bit_struct.ers` also has a known value and a variant written
    without a check; `eval_bit_struct.ers` checks reserved bits through
    `0x60 as Lcr`, a `write 0 sets` field filled with ones, and compound
