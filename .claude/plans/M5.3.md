# Plan: M5.3 Linear values

ADRs: 0094, 0101, 0102, 0103, 0104 (written and accepted in step 5)
Base: 7aeaf40
Program on QEMU: a transfer to a device whose handle must be waited for, on
riscv32 and thumbv7m at `-O0` and `-O`: a module `dma` declares
`#[linear] pub struct Transfer` with a private field, starts transfers over a
device simulated by `static mut` words (the boards have no DMA), and ends a
transfer only in `wait`, with `end`; the program starts two transfers, waits
for them in another order, tries a third through `Option(Transfer)`, and
prints the copied bytes over the UART. The wrong uses (a transfer never
waited for, a discarded `start(...)`, a transfer overwritten, `end` outside
`dma`) are ui tests.
Out of scope:
- `#[linear]` on enums (ADR 0101, "Alternatives considered"): later, if a
  program needs it;
- statics and arrays of linear types and linear values written through
  pointers: errors here (ADR 0101); M5.6 decides how a context owns what a
  static holds, and may relax the rule for statics;
- references, M5.4; methods, M5.5; ownership of peripherals, M5.6 (roadmap,
  "M5 steps");
- linear types in the generated programs of ADR 0068, which have only scalar
  types (roadmap, deferred ideas);
- `erebos svd`: it writes bit-field structs only, which are copy, so its
  output does not change.

Before step 1: the `docs(adr)` commit that accepts ADR 0101 to 0103 also sets
the status lines of the ADRs that 0103 amends, in their files and in the
index (`docs/adr/README.md`):
- 0095: `Accepted; amended by 0098 (the operand `move` and the rules M1 to
  M4), 0103 (the rules L1 to L4)`; index `Accepted, amended by 0098, 0103`.
- 0097: `Accepted; amended by 0100 (...), 0103 (`end` may use a partly moved
  place)`; index `Accepted, amended by 0100, 0103`.
- 0098: `Accepted; amended by 0103 (a struct's definition says whether it is
  `#[linear]`)`; index `Accepted, amended by 0103`.
- 0099: `Accepted; amended by 0100 (...), 0103 (`end` is an event of the
  analysis of moves)`; index `Accepted, amended by 0100, 0103`.
The same commit holds this plan and the roadmap's edits written while
planning (the M5.3 pending decisions settled; `#[linear]` on enums, and
statics and arrays of linear types, left open).

Order: the attribute and the kind come first (1), since every later step
asks whether a type is linear. The places a linear value may not be held
(2) are rejected by type checking before MIR gains the rules that assume
them (3). `end` (4) needs the MIR kinds of step 3 and its rule L1. The
analysis (5) reads `end` and the kinds. A diagnostic code gets, in the step
that adds it, both its snippet in the catalog of ADR 0069
(`tests/rejected.rs`) and its row in the check tables of `docs/reference.md`;
the prose of the reference comes in the last step. Each step gains a
`Decisions:` list while it is built (`/build-step`), for the choices it
makes that this plan and the ADRs do not dictate.

The tests of the rule on returns are in functions that return: the entry
function and handlers returning `!` are checked only for overwrites (ADR
0102, "Consequences").

## 1. feat(ty): the `#[linear]` attribute and which types are linear
- Status: done
- Implements: ADR 0101, "The attribute", "Which types are linear".
- Changes:
  - `src/hir/lower/item.rs`: `linear` in `struct_attrs`, no argument, once
    (`flag_attr`); on a bit-field struct, an enum and every other item,
    `resolve::misplaced-attribute` (`enum_attrs` and the other attribute
    tables name `linear` explicitly, so that it is misplaced there, not
    unknown), with `linear` in the `applies_to` table
    ("structs, other than bit-field structs") and a help giving ADR 0101's
    reason on an enum; with `#[copy]` on the same struct,
    `resolve::conflicting-attributes`, labeling both; the `unknown_attr`
    help lists it.
  - `src/hir/mod.rs`: `linear: Option<Span>` on `StructDef`.
  - `src/ty/linear.rs` (new, re-exported by `ty`): `is_linear(&Queries, Ty)`,
    computed from the parts as ADR 0101 lists, through fields, payload
    values, array and slice elements and `Option`/`Result` arguments, not
    through pointers; a type whose
    layout is a cycle is already `ty::cycle`, and the computation must not
    loop on it (a visited set, or the answer `false` for `{error}`).
- Tests:
  - ui: `linear_attribute.ers` (accepted on a struct, with `#[packed]` and
    `#[align(N)]`, layout dump unchanged); `linear_attribute_misplaced.ers`
    (on a bit-field struct, an enum with and without payloads, a function, a
    static); `linear_attribute_argument.ers`,
    `linear_attribute_duplicate.ers`, `linear_attribute_copy.ers` (with
    `#[copy]`); in `copy_field_not_copy.ers`, a `#[copy]` struct with a field
    of a `#[linear]` type and one with an `Option` of one
    (`ty::copy-field-not-copy`, as for any non-copy field).
  - unit tests of `is_linear` in `src/ty/linear.rs`: a marked struct, a
    struct and an enum holding one, `Option`/`Result` of one, an array of
    one and a slice of one (linear here; step 2 rejects them), a pointer to
    one (not linear), a zero-field marked struct.
  - `tests/rejected.rs`: no new code (the `resolve::` codes are in the
    catalog); `docs/reference.md`: the row of
    `resolve::misplaced-attribute` and of `resolve::conflicting-attributes`
    name `#[linear]`.
- Decisions:
  - `struct_attrs` returns a private `StructAttrs` struct (`packed`, `align`,
    `copy`, `linear`) instead of a four-element tuple: clippy's
    `type_complexity` rejects the tuple.
  - `linear` is matched explicitly in `bit_struct_attrs`, `no_attrs`,
    `enum_attrs` (for enums with and without payloads), `fn_attrs` and
    `static_attrs`, so that it is misplaced there and not unknown; the
    `misplaced_attr` label names the item (`not allowed on an enum`).
  - The help of `resolve::misplaced-attribute` for `#[linear]` has two texts,
    chosen by whether `what` names an enum: the reason of ADR 0101 (the mark
    would bind nobody, any module that sees the enum builds a value and takes
    it apart with `match`; an enum is linear by holding a linear value), and
    for every other item a line saying what the attribute does and that no
    other item has values.
  - `resolve::conflicting-attributes` for `#[copy]` with `#[linear]` is one
    error per struct whatever the order; it labels `#[copy]` "its values are
    copied" and `#[linear]` "its values must not be copied", with a help
    giving ADR 0101's reason. Both spans stay in `StructDef` as written, so
    `ty::copy-field-not-copy` is still checked on a struct with both.
  - `is_linear` takes the types as they are, normalized or not: `Applied`
    looks at its arguments, an enum at its payload values (a normalized
    `Option`/`Result` is an enum instance whose payloads are the arguments),
    so it needs no `&mut Queries` and calls no `normalize`. Containment cycles
    end by a stack of the structs and enums being looked into: one met again
    counts for nothing (`false`), so a cycle that holds a linear value
    elsewhere is still linear. A struct marked `#[linear]` answers before its
    fields are looked at. `Ty::Peripheral`, `Ty::BitStruct`, `Ty::Error`,
    `Ty::Never`, scalars and pointers are not linear.
  - `ty::linear` is a private module of `ty`, with `is_linear` re-exported as
    `copy`'s functions are.
  - `copy.rs` (outside the plan's list): the helps that suggest `#[copy]`
    (`mark_copy`, now `copy_help`, and `suggest_copy`) would suggest it for a
    linear type, where it is `resolve::conflicting-attributes` or again
    `ty::copy-field-not-copy`. For a linear culprit the help says
    "`T` is linear, so it cannot be copy: <alternative>" and `suggest_copy`
    gives `None`. `copy_help(q, ty, instead)` builds the four helps; their
    text for a type that is not linear is unchanged. The same help in
    `src/analysis/moves.rs` (`suggest_copy` on MIR types) still suggests it
    for a `#[linear]` struct whose fields are all copy; MIR has no linear flag
    before step 3, which must make that function return `None` for a linear
    type (`Ty::is_linear`).
  - Existing snapshots changed only in the help of `resolve::unknown-attribute`
    (`resolve_attribute_errors`, `resolve_memory_attributes`,
    `resolve_peripheral_attributes`), which now lists `#[linear]`.
  - `linear_attribute.ers` is `--emit=mir`, the stage that dumps layouts: each
    marked struct sits beside the same struct unmarked (`Plain`,
    `PlainHeader`, `PlainAligned`), and two functions sum the
    `size_of`/`align_of`/`offset_of` of each group; the dump shows equal
    constants and equal struct lines. It also has a zero-field marked struct
    and one with only `pub` fields.
  - `linear_attribute_misplaced.ers` also covers a constant, a `mod`, an
    `extern fn` and an `extern static`, as `copy_attribute_misplaced.ers`
    covers the first two.
  - `linear_attribute_copy.ers` has both orders of the two attributes.
    `copy_field_not_copy.ers` gained a `#[copy]` struct with a `#[linear]`
    field, one with an `Option` of one, and an enum with a payload value of
    one.
  - The unit tests of `is_linear` read a program through `driver::hir_of`
    and build the types by hand (`Ty::Applied`, `Ty::array`, `Ty::slice`,
    `Ty::ptr`); `Option`/`Result` cases are checked as written and
    normalized. Besides the plan's cases they cover a marked struct with no
    fields, a struct holding a struct that holds one, nested `Option`, a
    containment cycle without a linear part, with one, and through two
    structs. No code was added to the catalog of `tests/rejected.rs`: the
    `resolve::` codes are in it.
  - `docs/reference.md`: only the two rows of the check table, as the plan
    says; the `unknown-attribute` help is not quoted there.
  - From the review: the linear branch of `copy_help` and `suggest_copy` is
    covered through each place that calls them. `non_copy_constant.ers`
    gained a `#[linear]` `Ticket` as a `const`, as `Option(Ticket)`, and in a
    `comptime` expression; `non_copy_repeat.ers` gained `[Ticket {..}; 2]`;
    `move_out_of_place.ers` gained `let t: Ticket = *p` with `Ticket` a linear
    struct whose fields are all copy, which reaches the general help because
    `suggest_copy` gives `None`. All show "`Ticket` is linear, so it cannot be
    copy: ..." or the general help, never `#[copy]`. No linear static is in
    these tests: step 2 rejects it. `non_copy_repeat.ers`' `[Ticket; 2]`
    is an array of a linear type, so step 2 adds `ty::linear-array` to its
    snapshot: step 2 updates it.

## 2. feat(ty): no static, array or write through a pointer of a linear type
- Status: done
- Implements: ADR 0101, "Where a linear value may not be held".
- Changes:
  - `src/ty/linear.rs`, called from the checker and from `check_all`:
    - `ty::linear-static`, at the type of a static whose type is linear;
    - `ty::linear-array`, for an array or slice type whose element type is
      linear, once per type: at the type where it is written (fields,
      payload values, parameters, returns, `let`, statics, type arguments,
      pointees, layout queries, casts), and at an expression whose type
      reaches one while its operands' types do not and no type was written
      for it (array literals, repeat expressions, `slice(p, n)`; the rule is
      general, checked on every expression's type, not a list);
    - `ty::linear-through-pointer`, at an assignment whose place goes
      through a pointer (`*p`, `p[i]`, `(*p).f`, `(*s)[i]`) and whose value
      is of a linear type.
  - Each with a help pointing to ADR 0101 and saying what to do instead
    (keep the value in a local; for statics, that M5.6 decides).
- Tests:
  - ui: `linear_static.ers` (a static and a `static mut` of a `#[linear]`
    type and of an `Option` of one; a static of a pointer to one is valid);
    `linear_array.ers` (a field, a parameter, a `let`, a static,
    `[.None; 4]` of `Option(Transfer)`, `size_of([Transfer; 2])`, nested
    `[[Transfer; 2]; 2]` reported once, `*const [Transfer; 4]` and
    `*const [Transfer]`; the array literal `[start(1), start(2)];` as a
    statement, `([start(1), h])[0].channel` and `len(slice(p, 2))` with
    `p: *const Transfer`, with no written type, which must not reach the
    validator); `linear_through_pointer.ers`
    (`*p = t`, `p[i] = t`, `(*p).h = t`, `*p = .Some(t)`; writing a copy field
    through `&raw mut t` is valid).
  - `tests/rejected.rs`: a snippet per code; `docs/reference.md`: their rows.
- Decisions:
  - The written array types need their spans, which the types of fields,
    parameters and the like do not keep, so HIR lowering records them:
    `Hir::array_types: Vec<(Span, Ty)>`, pushed in `Lowerer::ty` for each
    `[T; N]` written (not when `T` is `{error}`) and each `[T]` written as the
    pointee of a pointer; a `[T]` written as a value is `ty::unsized` and
    `{error}` already. It is not in the dump of the HIR and has no entry in
    `CoreStart`: the dump would change for every `--emit=hir` snapshot, for a
    list that says nothing the others do not, and `core` has no linear type.
  - `is_linear_outside_arrays` (private, in `ty/linear.rs`) is `is_linear`
    without counting arrays and slices as linear. The three rules use it: an
    array is in error when its elements are linear in that sense (so
    `[[Transfer; 2]; 2]` is one error, at the inner array, and a struct with
    a `[Transfer; 2]` field does not make `[Table; 2]` a second error); a
    static of `[Transfer; 2]` is `ty::linear-array` and not also
    `ty::linear-static`; writing such an array through a pointer is not also
    `ty::linear-through-pointer`. Each mistake is reported where it is made.
  - A written type is reported once, at the first place recorded for it (the
    order of `Hir::array_types`), as ADR 0101 says "once per type"; the later
    places that write the same normalized type are silent (from the review:
    the first version reported each occurrence). An expression is reported
    when its type reaches an array or slice of linear
    elements (through arrays, fields, payload values, pointees, as
    `arrays_reached` walks them) that is not in `Queries::linear_arrays`,
    the list of the types reported so far, which the pass on written types
    fills first (`check_all`, before any body is checked) and the expressions
    extend. That is the ADR's "once per type" for expressions: two literals of
    `[Transfer; 2]` are one error, at the first, and a variable, a call or a
    literal whose type was written is not reported again. The operands are
    visited first (`operands_of`, the direct operands of every kind of
    expression), so the expression reported is the one that makes the type,
    not one above it that only has it (`len(slice(p, 2))` is reported at
    `slice(p, 2)`, `[[a, b, c, d], [e, f, g, h]]` at the inner literal).
    Types compare normalized, as the tables hold them.
  - The pass on expressions runs at the end of `Checker::fn_`, so a body that
    makes such a type counts as failed, like any error found while checking
    it, and is not lowered. It does nothing in a program without a
    `#[linear]` struct, which keeps the cost off every other program. A
    written array in a signature is an error of the item, as the others
    (`ty::unsized`, `ty::copy-field-not-copy`): the function still type
    checks and is lowered. Step 3's validator (L3) will meet such a body; the
    entry `ty::linear-array` of `tests/rejected.rs` (`Mir` stage) fails there
    if MIR building or the validator panic on it.
  - `report_linear_arrays` and `report_linear_statics` decide from the types as
    lowered, and normalize only the ones in error: normalizing every written
    array and every static type first evaluated their lengths earlier, which
    moved where `typeck_const_length_errors.ers` reports its cycles.
  - `ty::linear-static` is reported for every static whose type is linear
    outside arrays, `extern static` included, at `ty_span`, with the label
    "`T` is linear". The message says `static` or `static mut`. The help gives
    ADR 0094's reason and says M5.6 decides how a context owns what a static
    holds.
  - `ty::linear-through-pointer`: `Checker::place_via` is `place` returning
    also whether `PlaceInfo::via` is set (the last pointer of the path); `=`
    uses it, `place` is `place_via(..).0`. It is reported once the value is
    checked, at the whole assignment, with the type of the value (not of the
    place, so a value of type `!` is not reported). Compound assignments are
    integer-only and not checked. The help says to keep the value in a
    variable or to write its copy fields through the pointer.
  - `ty::linear-array`: "`T` has elements of the linear type `E`"; the label
    on a written type says its elements are linear, on an expression that it
    "makes" the type; one help (`ARRAY_HELP`) for both.
  - Tests: `linear_array.ers` has the written positions and the expressions
    that have the written types (not reported again); the expressions that
    make a type are `linear_array_made.ers`, since a type is reported once and
    the written ones would hide them (lengths differ in each position for the same
    reason). `linear_static.ers` has `extern static`, a struct and an enum
    that hold a transfer. `linear_through_pointer.ers` has `p[i] = ..`,
    `(*n).first.h`, and a slice `(*s)[i]`, which is also `ty::linear-array`
    (a slice of a linear type has no valid element to write). The static of an
    array in `linear_array.ers` is an `extern static`: a `static` initialized
    with a `loop {}` ran to `eval::step-limit`. Unit tests in
    `ty/linear.rs` cover `is_linear_outside_arrays`, `linear_elements` and
    `arrays_reached` (fields, payload values, `Option`, nested arrays, a
    pointer to the struct itself).
  - `tests/rejected.rs`: the three snippets are at `Mir`, `Items`.
    `non_copy_repeat.ers` now also has `ty::linear-array` for its
    `[Ticket; 2]`, as step 1 foresaw. The reference has only the rows of the
    check table. No `PANICS` count changed.

## 3. feat(mir): linear kinds, `new`, and the rules L1 to L4
- Status: done
- Implements: ADR 0103, "Kinds, `new` and `end` in MIR" (the flag, the
  linear parts, `new`), "Rules of the validator" (L1 for `new`, L2 to L4).
- Changes:
  - `src/mir/mod.rs`: `linear: bool` on `StructDef` (and `StructRef::new`);
    `Ty::is_linear`; `Ty::linear_parts`, the projection paths that reach a
    struct marked linear, through `Field` and every variant's `Payload`, the
    empty path included; `Statement::New(Place, Span)`, in
    `visit_operands`, `for_each_operand` and every match on statements;
    dumps print `new _1;`; the MIR dumps of struct definitions show the flag
    only if they show `copy` today.
  - `src/mir/build*`: the flag from the HIR declaration; `New(place, span of
    the literal)` after the last field write of every struct literal of a
    type marked linear and before its value is moved, and where the literal
    is for one with no fields.
  - `src/analysis/moves.rs`: its `suggest_copy` (the help of
    `analysis::use-after-move`) returns `None` for a linear type
    (`Ty::is_linear`), as `ty::suggest_copy` does since step 1: `#[copy]` on
    a `#[linear]` struct is `resolve::conflicting-attributes`.
  - `src/eval.rs`, `src/codegen/`: `New` does nothing;
    `src/analysis/shared_statics.rs` and `src/analysis/moves.rs` ignore it.
  - `src/mir/validate.rs`: L1 (for `new`), L2, L3 (through arrays, slices,
    fields, payload values and pointees, each definition once, as M4), L4.
- Tests:
  - ui: `mir_linear_new.ers` (`--emit=mir`, pinning where `new` is: a
    literal with fields, after the last field write; one whose fields use
    `?`, after the last `?`; one with none; `Tok {};` discarded; a literal
    inside `.Some(...)`; a literal of a non-linear struct with a linear
    field, which has no `new` of its own).
  - ui: `use_after_move_linear.ers` (`--emit=mir`): a use after a move of a
    `#[linear]` struct whose fields are all copy; the help of
    `analysis::use-after-move` does not suggest `#[copy]`, which it does for
    the same struct unmarked. A unit test of
    `suggest_copy` in `moves.rs` says the same.
  - unit tests of the validator in `src/mir/validate.rs`: one body breaking
    each of L1 (`new` of a non-linear struct, through a pointer), L2, L3 (a
    local, a static, a pointer to a slice), L4; `Ty::linear_parts` of a
    marked struct, a struct with a marked field, `Option(Transfer)`, a
    marked struct holding another.
  - every test of the suite passes the validator with the new rules (the
    validator runs on every program, ADR 0095).
- Decisions:
  - `StructRef::new` takes `linear: bool` after `copy`; `Queries::mir_struct`
    passes `def.linear.is_some()`. The struct lines of the MIR dump show no
    flag (they show none for `copy` either), so no snapshot of an existing
    program changed.
  - `Statement::New(Place, Span)` holds its span as the ADR says, besides the
    block's `spans` entry (which is the same span, the literal's). It is a
    no-op in `eval.rs`, `codegen/mod.rs`, `shared_statics.rs` and
    `moves.rs`, each arm with a comment, since those `match`es have no `_`
    arm; `leave_out` and `Statement::asm` name it, and it has no operand.
  - MIR building emits `New` in the `StructLit` arm, right after the loop over
    the fields and before `read(value)`, for a type that is a struct with the
    flag; its span is `self.span`, the literal's, as `expr` sets it. A
    literal with no fields has an empty loop, so its `new` is where the
    literal is, discarded or not. No other code builds a value of a struct
    that is not copy: bit-field literals are copy, `[v; N]` only repeats
    variants, and a `const` or `comptime` value of a non-copy type is
    rejected by type checking.
  - `Ty::is_linear` and `Ty::linear_parts` (MIR) walk with a stack of the
    struct and enum definitions being looked into, and treat a definition
    whose fields are not set as having nothing: the validator may call them on
    a type that is wrong, and must not panic. `linear_parts` lists the paths
    in a walk in declaration order, a part before the parts it holds, and goes
    on into the fields of a linear struct, so a marked struct holding another
    gives both paths; it does not go through arrays or pointers.
  - `Ty::is_linear_outside_arrays` (`pub(crate)`, MIR; the twin of the HIR one
    of step 2) is `is_linear` where an array or a slice never makes a type
    linear. The validator uses it where ADR 0103 says "linear" but an array
    of linear elements is already L3's: the second half of L3 (a static's
    type is not linear) and L4 (the type written through a pointer), so that
    one fault is one violation, as the validator keeps to elsewhere.
  - L1 is `Checker::linear_place`, with `what` ("`new`") so that step 4's
    `end` shares it. It reports, each as its own violation, a local bound to
    read-only data, the first projection other than `Field` and `Payload`, and
    a type that is not a struct with the flag; the place is first checked by
    the rules of places (S7, T1), and a place they reject gets no type
    judgment.
  - L2 is in the walk of M4 (`copy_kind`), so it is checked, as M4 is, on the
    definitions that the types of a body's locals reach, each once; a struct
    no local reaches is not looked at.
  - L3 has two parts. `linear_kinds` walks the type of every local of a body
    (one set of definitions seen per body) and `linear_static` the type of
    every static of the program (one set for all); both use the free function
    `linear_arrays`, which goes through arrays, slices, fields, payload values
    and pointees and reports an array or a slice at the innermost level
    (`[[Transfer; 2]; 2]` is one violation), judging its elements with
    `is_linear_outside_arrays`. A static of `[Transfer; 2]` is one violation,
    not also "its type is linear".
  - L4 is `Checker::linear_write`, called from the three places that write a
    place (`Assign`, a call's destination, an `asm` output) with the type
    `written` found. An `asm` output of a linear type is also T9, so the
    unit test has no case for it, only the three call sites.
  - What step 2 left: a function with a `[T; N]` or `[T]` of linear `T` in its
    signature type checks and was lowered, and the validator's L3 would have
    panicked on it. `Queries::lacks_layout` now returns true for an array or
    a slice type whose elements are linear (`ty::has_linear_elements`, a new
    export of `ty/linear.rs`), the mechanism that already keeps out of MIR the
    body that uses a type in error (`ty::unsized`, a `#[copy]` that
    `ty::copy-field-not-copy` rejected: `copy_declaration_fails` in the same
    function). `needs_missing_layout` then makes `mir_body` return `None`
    with no new diagnostic: the error is the `ty::linear-array` already
    reported at the written type, and the program is rejected as before. It
    covers parameters, the return type, locals, the types of expressions and
    of `size_of`, behind fields, payload values and pointees (a `*const
    [Transfer]` is one). `lacks_layout` also answers `is_erroneous`, so `?` and
    a `match` on an enum that reaches such an array now give `{error}` and add
    no error of their own; no existing snapshot changed. The unit tests and
    `tests/rejected.rs` (`ty::linear-array`, stage `Mir`) show it does not
    panic; `linear_array_lowering.ers` shows the shapes (a parameter, a
    pointee, a pointer to a slice, a field, a payload value, a caller) at
    `--emit=mir`, and a `7 / 0` in a function with no such type, which is
    still built and reported.
  - Tests: `mir_linear_new.ers` and `use_after_move_linear.ers` have the
    `entry` and `panic` functions that every ui program that reaches MIR needs

  a discarded `start`, an overwritten transfer).
- Decisions:
  - The device is three `static mut` arrays of four words (`SRC`, `DST` as
    `usize` addresses, `LEFT` as the bytes still to copy, zero meaning the
    channel is free) and a `POLLS` counter, all private to `dma`. Addresses are
    kept as `usize` and cast back (`src as *const u8 as usize`, `usize as *mut
    u8`) because a static of a pointer needs an initial pointer value and a
    slice pointer is two words: this uses only casts the language has.
  - `poll` is private to `dma` and advances every channel in flight by one byte,
    as a device runs by itself, so the program shows the point of the handle:
    while `b` is waited for, `a` also advances, and waiting for `a` then polls
    only for what is left. `wait` loops on `LEFT[channel] != 0` and calls `poll`.
    `wait` reads `t.channel` into a local before `end(t)` (the field is copy,
    `end` takes the whole value) and returns it.
  - `try_start` tests `LEFT[channel] != 0`: a channel is busy from `start`, not
    from its first poll, so the attempt made between the starts and the waits
    gives `.None`; after both waits the same channel gives `.Some`.
  - The numbers: `a` is channel 2 with `"erebos "` (7 bytes, to `out[0]`), `b`
    channel 1 with `"dma"` (3 bytes, to `out[7]`), the third attempt on channel
    2 is refused, then channel 2 again with `"!"` (1 byte, to `out[10]`). Waiting
    for `b` takes 3 polls (`a` is left with 4), for `a` 4, for the last 1: 8
    polls, and the output `erebos dma!` then `polls 8`. The channels that `wait`
    returns are checked with `assert` in `run` (2 and 1), so a handle that
    ended the wrong transfer would reach `on_panic` (exit 1) and fail the test.
    `assert(refused)` and `assert(accepted)` check the two `match`es.
  - `run(out: *mut u8) -> u32` returns the poll count and `main` prints, as the
    plan has it; the buffer is `main`'s `[u8; 16]`, `run` offsets into it with
    `&raw mut out[7]`. Both `match`es have the `.Some` arm consume the handle
    (`dma::wait(t)`), the refused one included, because the rule on returns
    holds there as in any program; the arm that cannot happen is not left to
    forget its handle.
  - `main` has no linear value; the rule on returns is checked in `run` and in
    `dma`'s functions that return, as the plan says. The program has no
    `// targets:` header: it runs on both targets, at `-O0` and `-O`.
  - No test other than the program itself, as the plan says: the wrong uses are
    the ui tests of steps 4 and 5. The program was run through the full `e2e`
    test (four builds and boots); with `expect-output` changed to `polls 9`
    all four failed with the output `polls 8`, so the harness does check it.
  - No `PANICS` count changed and no compiler change: the program compiled and
    ran the first time.

## Left open

Minor findings the reviews left open, with the step that found them. Each is
also in `docs/open-findings.md`, ending with `(M5.3)`. The first is an
imprecision of ADR 0103 the user accepted in the review of step 5; it awaits
an amendment of the ADR.

- Code (step 5 review, user decision): a value of one origin with several
  linear paths (`let p: Pair = pair(); let mut x = p.a; x = p.b;`) written
  over by another of its paths is `analysis::linear-not-consumed`, not
  `linear-overwritten`, because ADR 0103 takes "same origin" as "came round
  a loop"; the label no longer claims a loop. Precise origins per linear
  part need an ADR amending 0103. Pinned by `same_origin` in
  `tests/ui/linear_not_consumed.ers`.
- Code (step 1 review): `is_linear` in `src/ty/linear.rs` keeps only the
  stack of open types, no memo of finished ones, so a non-linear acyclic nest
  (A holds two B, B two C, ...) is walked 2^depth times.
- Code (step 2 review): `report_made_arrays` in `src/ty/linear.rs` walks the
  whole type of every expression of a program with a `#[linear]` struct;
  quadratic in the worst case.
- Code (step 3 review): the L1 violation for a bad projection in
  `linear_place` (`src/mir/validate.rs`) prints `{elem:?}`, the `Debug` form
  of `PlaceElem`, where other violations print the MIR dump form.
- Code (step 5 review): `hop_labels` in `src/analysis/linear.rs` tells "moved
  here" from "moved into `x` here" by comparing the description with `THIS`;
  comparing the local's `name.is_none()` would not depend on `describe`'s
  text. `type Key` in `linear.rs` repeats what `bits::key` returns; export the
  alias from `bits.rs`.
- Code (step 4 and final review): `is_reserved` in `src/svd/names.rs` renames
  no built-in function name (`assert`, `len`, `slice`, now `end`), so an SVD
  item named `end` would give `resolve::reserved-name` in the generated
  program; not confirmed with an SVD.
- Tests (step 2 review): `linear_array_made.ers` covers array literals in
  plain statements, nested and in `slice(..)`, not inside an `if`, `match` or
  `loop` (they work, checked by hand).
- Tests (step 5 review): `end.ers` lost the shape `end(if c { t } else
  { make(2) })` with a parameter moved inside the `if` when the analysis made
  the old `parameter` function an error; `expression` now holds only calls.
  `EnumDef::set_value` and `Queries::known_discriminant` have no unit test of

  `eval_enum_payload_values.ers`); the `debug_assert_eq!` in `into_mir` that

- Docs (step 7 review): in `docs/reference.md`, "In MIR", the L3 summary
  leaves out "through fields, payloads and pointees" (ADR 0103), and the L1

  struct" is ambiguous about what is of the struct. A few lines of the "M5.3
  done" entry in `docs/roadmap.md` run past the usual wrap.
