# Plan: M5.11 Stack bound

ADRs: 0121 (a second panic stops), 0122 (`#[stack(N)]`), 0123 (the stack
bound); building on 0014, 0020, 0026, 0057, 0076, 0078, 0079, 0082, 0084,
0085, 0086, 0087, 0088, 0093, 0119, 0120
Base: 5b81efc
Program on QEMU: an e2e program whose stack fits, which measures what it used
and is checked against the bound, on both targets at `-O0` and `-O`; and the
same program built with a stack too small, rejected with
`analysis::stack-overflow` and the path that needs the most, on both targets
at both levels (`tests/elf.rs`).
Out of scope:
- priorities and nested maskable handlers (after M6; ADR 0123,
  Consequences);
- function pointers (deferred ideas; ADR 0123 says how they will fit);
- a hook for what a second panic does other than spin (ADR 0121,
  Consequences);
- unsafe attributes (ADR 0119, "What stays out"; ADR 0122);
- the findings of `docs/open-findings.md`: worked off between steps, not here.

Decided with the user while planning (2026-11-16):
- A guard inside the panic function stops a second panic, which spins with
  interrupts as they are (ADR 0121).
- A function the bound reaches that needs `#[stack(N)]` and has none is an
  error, not a default (ADR 0122).
- `#[stack(N)]` is a plain attribute, not under `unsafe` (ADR 0122).
- The bound is always on, on every `erebos build`, at the level built, and
  `--emit=stack` prints its report (ADR 0123).
- Handlers add up by kind: the deepest maskable one, every unmaskable one, and
  the faults that reach default handlers (ADR 0123, "Contexts and the total").
  The planner refined the user's "one default-handler path" into the faults'
  two entries (one before a panic, one inside the panic function), the
  maskable words without a handler, and thumbv7m's NMI without a handler,
  each of which the model allows; flagged to the user.
- The calls MIR does not show are assumed from every function to each
  inserted function, and an oracle in the tests checks the machine's calls
  against the graph (ADR 0123).
- `#[stack(N)]` on an `extern fn` counts everything it calls, Erebos callbacks
  included; a `sym` operand is an edge, so a cycle through assembly is
  rejected (ADR 0122, 0123).
- One step, the guard first.

Frame sizes come from LLVM's `"warn-stack-size"` warnings, which the planner
tried with LLVM 22's `llc` on both targets at both levels (ADR 0123,
Context); no dependency is added.

Where Erebos source lives (as in the M5.10 plan; each migration step searches
all of them): `rt/`, `tests/boards/`, `tests/e2e/`, `tests/ui/`,
`tests/svd/chips/`, the snippets of `tests/rejected.rs`, the programs
embedded in `tests/elf.rs`, `tests/e2e.rs`, `tests/svd.rs` and
`tests/fuzz.rs`'s corpus, the source `tests/common/generator.rs` writes, and
`tests/layout/`. Only the programs that `erebos build` builds reach the bound.

## 1. feat(codegen): stop a second panic in the panic function
- Status: done
- Implements: ADR 0121
- Changes:
  - `src/codegen/mod.rs`: when it defines the body `Mir::panic`, code
    generation emits the guard before the body's first block: a volatile load
    of `__erebos_panicking` (an `i8` global, zero-initialized, so in `.bss`,
    private to the object), a branch to a block that branches to itself when
    it is not 0, and otherwise a volatile store of 1 and the body. The global
    is defined only when the panic function is (a dump that leaves `core` out
    still defines the panic function, so the IR shows it). The panic
    function's LLVM function gets `noinline` (ADR 0121, 0123), and no
    `mustprogress`, which no Erebos function has today.
  - `tests/e2e/panic_in_panic.ers` (both targets): the thread arms the timer
    (the CLINT's on riscv32 as `interrupt_clint.ers` does, SysTick on
    thumbv7m as `interrupt_systick.ers` does; the builder chooses whether the
    two are one program with per-target code in the board or two programs,
    and records the choice and its reason in Decisions) and
    enables interrupts, then fails a check. The panic function prints `first`
    and fails a check of its own; the timer's handler prints `stopped` and
    exits with 1.
  - `tests/e2e/fault_in_panic_riscv32.ers`, rewritten as ADR 0121 says: the
    first panic from a fault, the second from a check after the panic function
    enables interrupts and arms the timer.
- Tests: `tests/ui/panic_guard_llvm.ers` and `panic_guard_llvm_thumbv7m.ers`
  (the guard and the flag, a panic function with and without
  `&core::PanicInfo`); every LLVM IR snapshot that shows a panic function
  changes, and the update is reviewed for the guard alone; the two e2e
  programs at both levels. `tests/architecture.rs`'s count of codegen's
  panics and wrap flags is unchanged or updated with the reason.
- Decisions:
  - Where the guard lives: `FnCodegen::guard` in `src/codegen/mod.rs`, called
    from `FnCodegen::define` when the function being defined is the panic
    function (`self.function == self.function(self.panic)`); the flag's name is
    the constant `PANICKING`. The guard adds the flag to the module itself, so
    the flag exists exactly when the panic function is defined and `Shared`
    gained no field. The panic function is never naked (item lowering refuses
    it), so the guard is only in the non-naked path of `define`.
  - The guard's block is a new entry block `guard`, prepended before the MIR
    body's first block (`prepend_basic_block`); the stack slots and the stores
    of the parameters go in it, not in `bb0`, and the flag's check follows
    them. LLVM promotes (`mem2reg`) only the allocas of the entry block, so
    leaving them in `bb0` would have kept every local of the panic function in
    memory at both levels. The stores do not touch the flag, so the plan's
    "before the body's first block" still holds. The blocks are `guard` (load,
    compare, branch), `spin` (branches to itself) and `first` (volatile store
    of 1, branch to `bb0`), laid out in that order before `bb0`.
  - The flag has `internal` linkage, not `private`: it is local to the object
    either way, and `internal` keeps a symbol (`__erebos_panicking`) in the
    symbol table, which a person reading `llvm-readelf` and the machine tests
    of later steps can find. It is zero-initialized, so it lands in `.bss`
    (`.sbss` on riscv32), which the linker script already collects
    (`src/link.rs`). Alignment 1, as an `i8`.
  - `noinline` is added in `lower`, right after the functions are declared, to
    `fns[mir.panic]`, not in `declare`, which does not know which body is the
    panic function. No `mustprogress` is added (no Erebos function has it); the
    `-O` snapshots of `panic_guard_llvm.ers` show the spin kept.
  - `PANICS` of `src/codegen/mod.rs` goes from 72 to 83: the guard's 11 builder
    calls (`build_load`, `as_instruction_value`, `set_volatile` and
    `set_alignment` for the load; `build_int_compare`; the conditional branch
    and the two unconditional ones; `build_store`, `set_volatile` and
    `set_alignment` for the store) each `expect` something true by
    construction: the builder is positioned in a block of the function being
    built, a load and a store are instructions, and they can be volatile and
    aligned. No user input reaches them: the guard is the same for every
    program. The wrap-flag count is unchanged.
  - Two e2e programs, not one: `panic_in_panic_riscv32.ers` and
    `panic_in_panic_thumbv7m.ers`, each with a `// targets:` header. The timers
    differ in where they live and in how a tick is cleared (the CLINT's compare
    value must be moved; SysTick is periodic), and the programs they follow
    (`interrupt_clint.ers`, `interrupt_systick.ers`) are already per target; a
    board function that arms "a timer" would have added an interface to both
    boards for one test. The plan's name `panic_in_panic.ers` is therefore
    split by target.
  - In the three e2e programs the handler prints `stopped` and exits only once
    the panic function has set `SECOND`, a `static mut` that it sets just
    before its failing check; before then the handler only re-arms the timer
    (SysTick needs nothing). Without the flag a tick could fire during the
    first print, so the output would depend on timing, and a tick before the
    second panic would not show the guard at all. The write is in a `critical`
    block: the race analysis (ADR 0093) rejects a write to a `static mut` that
    a handler reads, reached from the panic function through a check outside
    `critical`; found by building the first version of the programs.
  - The check that fails inside the panic function is
    `print_u32(divide(1, 0))` with `fn divide(a: u32, b: u32) -> u32 { a + a / b }`,
    the form of `panic_division.ers`: a division by a zero known at compile
    time still compiles to the check and the call of the panic function, at
    `-O` too. The panic function takes no parameter, to keep the programs short.
  - `fault_in_panic_riscv32.ers`: the first panic is still `asm("unimp")` in
    `main`; the panic function prints `first`, then does what the entry function
    of `panic_in_panic_riscv32.ers` does (CLINT `MTIMECMP_HIGH`, `arm`,
    `csrs mie`, `enable_interrupts`), sets `SECOND` and fails the check. The
    CLINT constants and `arm` are repeated in the program, as the e2e programs
    repeat their MMIO; the header keeps the remark on thumbv7m's lockup.
  - Two ui snapshots, one per target: `panic_guard_llvm.ers` (riscv32, a panic
    function without a parameter, and a division that calls it) and
    `panic_guard_llvm_thumbv7m.ers` (thumbv7m, a panic function with
    `&core::PanicInfo`, and an indexing that passes it the `PanicInfo`), each at
    both levels. The other two combinations are shown by the existing
    snapshots that changed (`codegen_panic_info`, `codegen_panic_no_info`, the
    interrupt-table ones).
  - The 78 changed snapshots were reviewed by a script (not committed) that
    undoes the guard in the new text (drops the flag's line, the `guard`,
    `spin` and `first` blocks, the `noinline` attribute, attribute-group
    numbering, `preds` comments) and compares it with the old text. 48 are equal
    after that. The 30 others differ only at `-O`, in one way: the panic
    function used to be inlined (its body is a loop, so a check's failing
    branch was `br label %self`) and `noinline` makes it a `tail call void
    @on_panic()` followed by `unreachable`, in the checks and in the default
    handlers (which pass `ptr nonnull poison` for the `PanicInfo` when
    the panic function ignores it), with the `memory(...)` attributes of the
    callers following from the call. The snapshots' `assertion_line` metadata
    was not kept, as in the old files.

## 2. feat: `#[stack(N)]` on functions
- Status: done
- Implements: ADR 0122, "The attribute"
- Changes: where `#[align(N)]` on functions is handled (ADR 0087), the same
  path for `stack`: resolution (`resolve::misplaced-attribute` on other items,
  with the help listing functions; `resolve::duplicate-attribute`), the
  computation of `N` as a `usize` at compile time, `hir`/`ty` as `align` has
  it, `Body::stack: Option<u64>` in `src/mir/`, and `--emit=mir` showing it
  next to the alignment. On an `extern fn` it is accepted (unlike `align`). No
  check reads it yet.
- Tests: ui snapshots `stack_attribute.ers` (on a plain function, a naked
  function, the entry function, the panic function, a handler, a function of
  a type and an `extern fn`, with a constant expression, at `--emit=mir`);
  `stack_attribute_errors.ers` (on a struct and a static, twice);
  `stack_attribute_invalid.ers` (a value that is no `usize`, a failed
  computation; split out because lowering errors stop the pipeline, see
  Decisions).
- Decisions:
  - Where it lives: `Fn::stack: Option<(ArrayLen, Span)>` in `src/hir/mod.rs`
    next to `align`; `Lowerer::fn_attrs` in `src/hir/lower/item.rs` parses it
    (it now returns a `FnAttrs` struct, since the tuple would have had four
    members); `Queries::fn_stack` in `src/query.rs` computes it with
    `array_len` (a `usize`, as `align` does); `Body::stack` in `src/mir/mod.rs`
    is set by `Builder::finish`. `fn_stack` has no cache of its own, because
    `array_len` already caches each value and reports a failure once; the
    function is still called for every function in the loop that evaluates
    every `#[align]`, so that a failed computation is reported for a function
    nobody builds.
  - On an `extern fn`, `fn_attrs` now reads `#[stack]` and sends every other
    attribute to `no_attrs` one at a time, so the diagnostics of the other
    attributes on an `extern fn` are those they had.
  - `Body::stack` is `None` for a `comptime` body (a constant, an argument, a
    `comptime` block, a body of an expression), as `align`, so "no effect and
    no diagnostic" on a function run only at compile time holds for those. A
    plain function that happens to be called from a constant is also a
    runtime function and keeps its number.
  - `Mir::leave_out` clears `stack` of the `core` bodies it turns into
    `extern` declarations, as it clears `align`: such a body then stands for
    code outside the dump, and a `stack` on an external body would read as the
    depth of a C function.
  - `--emit=mir` prints `#[stack(N)]` on the line after `#[align(N)]` (before
    `naked`, `extern`, `entry`, ... which are part of the `fn` line). Nothing
    reads `Body::stack` yet.
  - `resolve::misplaced-attribute` for `stack`: "applies only to functions",
    with a help that says what `N` counts and that no other item has a stack.
    The help of `resolve::unknown-attribute` lists `#[stack(N)]` on functions
    (ADR 0122), so nine `resolve_*` snapshots changed: three show the new
    help, six the new `stack: None` of the HIR dump (`Fn` is printed with
    `Debug`). `resolve::duplicate-attribute` and `resolve::attribute-argument`
    (`#[stack]` without an argument: "takes a number of bytes, such as
    `#[stack(64)]`") are as `align`'s.
  - Three ui programs, not two: `stack_attribute_errors.ers` has the
    resolution errors (misplaced on a struct, a bit-field struct, an enum, a
    static, an `extern static`, a constant, a module and an `impl` block;
    twice, on a function of a type, a plain function and an `extern fn`;
    without an argument, on both), and `stack_attribute_invalid.ers` the
    values that resolution lets through and type checking or the evaluator
    reject (`-1`, `true`, a `u32`, `1 / 0`, on a plain function and on an
    `extern fn`), plus 0 and 7 as valid. They are separate because lowering
    errors stop the pipeline, so one file could not show both, as
    `align_fn_errors.ers` and `align_fn_invalid.ers` are separate.
  - `stack_attribute.ers` (`--emit=mir`, riscv32) shows a plain function, a
    function of a type, the entry function, the panic function, a handler, a
    naked function, an `extern fn`, 0, a constant expression (`BASE * 2`) and
    a function with both `#[align]` and `#[stack]`. The number of
    the stack is 0 in `zero` and 17 in `aligned` (not a multiple of the stack
    alignment) to show that any value is kept as written.

## 8. test: check the stack bound against the machine
- Status: todo
- Implements: ADR 0123, "Tests", the oracles
- Changes:
  - `tests/common/mod.rs`: `llvm-objdump` found like `llvm-readelf`
    (`EREBOS_OBJDUMP`).
  - `tests/stack.rs`: for every e2e program, on both targets at both levels,
    `--emit=stack` and the built executable; every call and every jump to
    another function's symbol in `llvm-objdump -d` must be an edge of the
    report's lines, or leave a function with `#[stack(N)]` (naked, `asm`) whose

    an error of the test unless it is the compiler's (default handlers, the
    vector table) or C's.
  - `tests/e2e/stack_measured.ers` (both targets): at entry it fills the stack
    below its own frame with a pattern, down to `__stack_start`; it arms a
    timer whose handler preempts the path below; it runs a deep path (calls
    with array locals, one of 512 bytes, an aggregate copy) that ends in a
    failed check. The panic function counts how many bytes of the pattern
    were overwritten before it prints anything, then prints the count and
    exits.
  - `tests/e2e/stack_measured_fault.ers` (both targets, `takes-exceptions`):
    the same path, with the same 512-byte local, but ending in a fault
    (`unimp`, `udf`) that reaches a default handler and the panic function,
    which counts the same way and exits.
  - `tests/stack.rs` checks each number against the report's total (at most)
    and against 512 (at least, so a broken count fails), on both targets at
    both levels.
- Tests: the three above. A failure of the calls oracle points at a call the
  graph misses; the fix is an edge or a number, made in this commit.
