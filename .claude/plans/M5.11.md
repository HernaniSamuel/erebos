# Plan: M5.11 Stack bound

ADRs: 0121 (a second panic stops), 0122 (`#[stack(N)]`), 0123 (the stack
bound); building on 0014, 0020, 0026, 0057, 0076, 0078, 0079, 0082, 0084,
0085, 0086, 0087, 0088, 0093, 0119, 0120
Base: 5b81efc
Program on QEMU: an e2e program whose stack fits, which measures what it used
and is checked against the bound, on both targets at `-O0` and `-O`; and the
same program built with a stack too small, rejected with
`analysis::stack-overflow` and the path that needs the most, on both targets
at both levels (`tests/elf.rs`).
Out of scope:
- priorities and nested maskable handlers (after M6; ADR 0123,
  Consequences);
- function pointers (deferred ideas; ADR 0123 says how they will fit);
- a hook for what a second panic does other than spin (ADR 0121,
  Consequences);
- unsafe attributes (ADR 0119, "What stays out"; ADR 0122);
- the findings of `docs/open-findings.md`: worked off between steps, not here.

Decided with the user while planning (2026-11-16):
- A guard inside the panic function stops a second panic, which spins with
  interrupts as they are (ADR 0121).
- A function the bound reaches that needs `#[stack(N)]` and has none is an
  error, not a default (ADR 0122).
- `#[stack(N)]` is a plain attribute, not under `unsafe` (ADR 0122).
- The bound is always on, on every `erebos build`, at the level built, and
  `--emit=stack` prints its report (ADR 0123).
- Handlers add up by kind: the deepest maskable one, every unmaskable one, and
  the faults that reach default handlers (ADR 0123, "Contexts and the total").
  The planner refined the user's "one default-handler path" into the faults'
  two entries (one before a panic, one inside the panic function), the
  maskable words without a handler, and thumbv7m's NMI without a handler,
  each of which the model allows; flagged to the user.
- The calls MIR does not show are assumed from every function to each
  inserted function, and an oracle in the tests checks the machine's calls
  against the graph (ADR 0123).
- `#[stack(N)]` on an `extern fn` counts everything it calls, Erebos callbacks
  included; a `sym` operand is an edge, so a cycle through assembly is
  rejected (ADR 0122, 0123).
- One step, the guard first.

Frame sizes come from LLVM's `"warn-stack-size"` warnings, which the planner
tried with LLVM 22's `llc` on both targets at both levels (ADR 0123,
Context); no dependency is added.

Where Erebos source lives (as in the M5.10 plan; each migration step searches
all of them): `rt/`, `tests/boards/`, `tests/e2e/`, `tests/ui/`,
`tests/svd/chips/`, the snippets of `tests/rejected.rs`, the programs
embedded in `tests/elf.rs`, `tests/e2e.rs`, `tests/svd.rs` and
`tests/fuzz.rs`'s corpus, the source `tests/common/generator.rs` writes, and
`tests/layout/`. Only the programs that `erebos build` builds reach the bound.

## 1. feat(codegen): stop a second panic in the panic function
- Status: done
- Implements: ADR 0121
- Changes:
  - `src/codegen/mod.rs`: when it defines the body `Mir::panic`, code
    generation emits the guard before the body's first block: a volatile load
    of `__erebos_panicking` (an `i8` global, zero-initialized, so in `.bss`,
    private to the object), a branch to a block that branches to itself when
    it is not 0, and otherwise a volatile store of 1 and the body. The global
    is defined only when the panic function is (a dump that leaves `core` out
    still defines the panic function, so the IR shows it). The panic
    function's LLVM function gets `noinline` (ADR 0121, 0123), and no
    `mustprogress`, which no Erebos function has today.
  - `tests/e2e/panic_in_panic.ers` (both targets): the thread arms the timer
    (the CLINT's on riscv32 as `interrupt_clint.ers` does, SysTick on
    thumbv7m as `interrupt_systick.ers` does; the builder chooses whether the
    two are one program with per-target code in the board or two programs,
    and records the choice and its reason in Decisions) and
    enables interrupts, then fails a check. The panic function prints `first`
    and fails a check of its own; the timer's handler prints `stopped` and
    exits with 1.
  - `tests/e2e/fault_in_panic_riscv32.ers`, rewritten as ADR 0121 says: the
    first panic from a fault, the second from a check after the panic function
    enables interrupts and arms the timer.
- Tests: `tests/ui/panic_guard_llvm.ers` and `panic_guard_llvm_thumbv7m.ers`
  (the guard and the flag, a panic function with and without
  `&core::PanicInfo`); every LLVM IR snapshot that shows a panic function
  changes, and the update is reviewed for the guard alone; the two e2e
  programs at both levels. `tests/architecture.rs`'s count of codegen's
  panics and wrap flags is unchanged or updated with the reason.
- Decisions:
  - Where the guard lives: `FnCodegen::guard` in `src/codegen/mod.rs`, called
    from `FnCodegen::define` when the function being defined is the panic
    function (`self.function == self.function(self.panic)`); the flag's name is
    the constant `PANICKING`. The guard adds the flag to the module itself, so
    the flag exists exactly when the panic function is defined and `Shared`
    gained no field. The panic function is never naked (item lowering refuses
    it), so the guard is only in the non-naked path of `define`.
  - The guard's block is a new entry block `guard`, prepended before the MIR
    body's first block (`prepend_basic_block`); the stack slots and the stores
    of the parameters go in it, not in `bb0`, and the flag's check follows
    them. LLVM promotes (`mem2reg`) only the allocas of the entry block, so
    leaving them in `bb0` would have kept every local of the panic function in
    memory at both levels. The stores do not touch the flag, so the plan's
    "before the body's first block" still holds. The blocks are `guard` (load,
    compare, branch), `spin` (branches to itself) and `first` (volatile store
    of 1, branch to `bb0`), laid out in that order before `bb0`.
  - The flag has `internal` linkage, not `private`: it is local to the object
    either way, and `internal` keeps a symbol (`__erebos_panicking`) in the
    symbol table, which a person reading `llvm-readelf` and the machine tests
    of later steps can find. It is zero-initialized, so it lands in `.bss`
    (`.sbss` on riscv32), which the linker script already collects
    (`src/link.rs`). Alignment 1, as an `i8`.
  - `noinline` is added in `lower`, right after the functions are declared, to
    `fns[mir.panic]`, not in `declare`, which does not know which body is the
    panic function. No `mustprogress` is added (no Erebos function has it); the
    `-O` snapshots of `panic_guard_llvm.ers` show the spin kept.
  - `PANICS` of `src/codegen/mod.rs` goes from 72 to 83: the guard's 11 builder
    calls (`build_load`, `as_instruction_value`, `set_volatile` and
    `set_alignment` for the load; `build_int_compare`; the conditional branch
    and the two unconditional ones; `build_store`, `set_volatile` and
    `set_alignment` for the store) each `expect` something true by
    construction: the builder is positioned in a block of the function being
    built, a load and a store are instructions, and they can be volatile and
    aligned. No user input reaches them: the guard is the same for every
    program. The wrap-flag count is unchanged.
  - Two e2e programs, not one: `panic_in_panic_riscv32.ers` and
    `panic_in_panic_thumbv7m.ers`, each with a `// targets:` header. The timers
    differ in where they live and in how a tick is cleared (the CLINT's compare
    value must be moved; SysTick is periodic), and the programs they follow
    (`interrupt_clint.ers`, `interrupt_systick.ers`) are already per target; a
    board function that arms "a timer" would have added an interface to both
    boards for one test. The plan's name `panic_in_panic.ers` is therefore
    split by target.
  - In the three e2e programs the handler prints `stopped` and exits only once
    the panic function has set `SECOND`, a `static mut` that it sets just
    before its failing check; before then the handler only re-arms the timer
    (SysTick needs nothing). Without the flag a tick could fire during the
    first print, so the output would depend on timing, and a tick before the
    second panic would not show the guard at all. The write is in a `critical`
    block: the race analysis (ADR 0093) rejects a write to a `static mut` that
    a handler reads, reached from the panic function through a check outside
    `critical`; found by building the first version of the programs.
  - The check that fails inside the panic function is
    `print_u32(divide(1, 0))` with `fn divide(a: u32, b: u32) -> u32 { a + a / b }`,
    the form of `panic_division.ers`: a division by a zero known at compile
    time still compiles to the check and the call of the panic function, at
    `-O` too. The panic function takes no parameter, to keep the programs short.
  - `fault_in_panic_riscv32.ers`: the first panic is still `asm("unimp")` in
    `main`; the panic function prints `first`, then does what the entry function
    of `panic_in_panic_riscv32.ers` does (CLINT `MTIMECMP_HIGH`, `arm`,
    `csrs mie`, `enable_interrupts`), sets `SECOND` and fails the check. The
    CLINT constants and `arm` are repeated in the program, as the e2e programs
    repeat their MMIO; the header keeps the remark on thumbv7m's lockup.
  - Two ui snapshots, one per target: `panic_guard_llvm.ers` (riscv32, a panic
    function without a parameter, and a division that calls it) and
    `panic_guard_llvm_thumbv7m.ers` (thumbv7m, a panic function with
    `&core::PanicInfo`, and an indexing that passes it the `PanicInfo`), each at
    both levels. The other two combinations are shown by the existing
    snapshots that changed (`codegen_panic_info`, `codegen_panic_no_info`, the
    interrupt-table ones).
  - The 78 changed snapshots were reviewed by a script (not committed) that
    undoes the guard in the new text (drops the flag's line, the `guard`,
    `spin` and `first` blocks, the `noinline` attribute, attribute-group
    numbering, `preds` comments) and compares it with the old text. 48 are equal
    after that. The 30 others differ only at `-O`, in one way: the panic
    function used to be inlined (its body is a loop, so a check's failing
    branch was `br label %self`) and `noinline` makes it a `tail call void
    @on_panic()` followed by `unreachable`, in the checks and in the default
    handlers (which pass `ptr nonnull poison` for the `PanicInfo` when
    the panic function ignores it), with the `memory(...)` attributes of the
    callers following from the call. The snapshots' `assertion_line` metadata
    was not kept, as in the old files.

## 2. feat: `#[stack(N)]` on functions
- Status: done
- Implements: ADR 0122, "The attribute"
- Changes: where `#[align(N)]` on functions is handled (ADR 0087), the same
  path for `stack`: resolution (`resolve::misplaced-attribute` on other items,
  with the help listing functions; `resolve::duplicate-attribute`), the
  computation of `N` as a `usize` at compile time, `hir`/`ty` as `align` has
  it, `Body::stack: Option<u64>` in `src/mir/`, and `--emit=mir` showing it
  next to the alignment. On an `extern fn` it is accepted (unlike `align`). No
  check reads it yet.
- Tests: ui snapshots `stack_attribute.ers` (on a plain function, a naked
  function, the entry function, the panic function, a handler, a function of
  a type and an `extern fn`, with a constant expression, at `--emit=mir`);
  `stack_attribute_errors.ers` (on a struct and a static, twice);
  `stack_attribute_invalid.ers` (a value that is no `usize`, a failed
  computation; split out because lowering errors stop the pipeline, see
  Decisions).
- Decisions:
  - Where it lives: `Fn::stack: Option<(ArrayLen, Span)>` in `src/hir/mod.rs`
    next to `align`; `Lowerer::fn_attrs` in `src/hir/lower/item.rs` parses it
    (it now returns a `FnAttrs` struct, since the tuple would have had four
    members); `Queries::fn_stack` in `src/query.rs` computes it with
    `array_len` (a `usize`, as `align` does); `Body::stack` in `src/mir/mod.rs`
    is set by `Builder::finish`. `fn_stack` has no cache of its own, because
    `array_len` already caches each value and reports a failure once; the
    function is still called for every function in the loop that evaluates
    every `#[align]`, so that a failed computation is reported for a function
    nobody builds.
  - On an `extern fn`, `fn_attrs` now reads `#[stack]` and sends every other
    attribute to `no_attrs` one at a time, so the diagnostics of the other
    attributes on an `extern fn` are those they had.
  - `Body::stack` is `None` for a `comptime` body (a constant, an argument, a
    `comptime` block, a body of an expression), as `align`, so "no effect and
    no diagnostic" on a function run only at compile time holds for those. A
    plain function that happens to be called from a constant is also a
    runtime function and keeps its number.
  - `Mir::leave_out` clears `stack` of the `core` bodies it turns into
    `extern` declarations, as it clears `align`: such a body then stands for
    code outside the dump, and a `stack` on an external body would read as the
    depth of a C function.
  - `--emit=mir` prints `#[stack(N)]` on the line after `#[align(N)]` (before
    `naked`, `extern`, `entry`, ... which are part of the `fn` line). Nothing
    reads `Body::stack` yet.
  - `resolve::misplaced-attribute` for `stack`: "applies only to functions",
    with a help that says what `N` counts and that no other item has a stack.
    The help of `resolve::unknown-attribute` lists `#[stack(N)]` on functions
    (ADR 0122), so nine `resolve_*` snapshots changed: three show the new
    help, six the new `stack: None` of the HIR dump (`Fn` is printed with
    `Debug`). `resolve::duplicate-attribute` and `resolve::attribute-argument`
    (`#[stack]` without an argument: "takes a number of bytes, such as
    `#[stack(64)]`") are as `align`'s.
  - Three ui programs, not two: `stack_attribute_errors.ers` has the
    resolution errors (misplaced on a struct, a bit-field struct, an enum, a
    static, an `extern static`, a constant, a module and an `impl` block;
    twice, on a function of a type, a plain function and an `extern fn`;
    without an argument, on both), and `stack_attribute_invalid.ers` the
    values that resolution lets through and type checking or the evaluator
    reject (`-1`, `true`, a `u32`, `1 / 0`, on a plain function and on an
    `extern fn`), plus 0 and 7 as valid. They are separate because lowering
    errors stop the pipeline, so one file could not show both, as
    `align_fn_errors.ers` and `align_fn_invalid.ers` are separate.
  - `stack_attribute.ers` (`--emit=mir`, riscv32) shows a plain function, a
    function of a type, the entry function, the panic function, a handler, a
    naked function, an `extern fn`, 0, a constant expression (`BASE * 2`) and
    a function with both `#[align]` and `#[stack]`. The number of
    the stack is 0 in `zero` and 17 in `aligned` (not a multiple of the stack
    alignment) to show that any value is kept as written.

## 3. feat(mir): list the inserted functions
- Status: done
- Implements: ADR 0123, "The graph" (`Mir::inserted`)
- Changes: `src/mir/`: `Mir::inserted: Vec<BodyId>`, the `#[export]` functions
  of `core` other than `_start`, in the order of their bodies, set where
  `critical_enter` and `reset` are; empty once `leave_out` drops `core`.
  `src/driver.rs`'s test `inserted_roots` reads it, plus `critical_enter` and
  `critical_exit`, instead of telling the functions by their names.
- Tests: the driver's existing test, unchanged in what it checks; a unit test
  that the list on each target holds `memcpy`, `memset`, `memmove`, and on
  thumbv7m the `__aeabi_` functions, and not `_start`.
- Decisions:
  - Where the list is set: `Queries::into_mir` in `src/query.rs`, where `reset`
    and `critical_enter` are set. The bodies are collected into a local first,
    so the list is computed from them, and the `Mir` takes both. The test is
    the one `inserted_roots` used: `runtime` (a function of `core`), a symbol
    that is no path (an `#[export]` one; the others keep their module path),
    and not the `reset` body. `Body` gained no field and `hir` is untouched:
    what `#[export]` does to a symbol is already what the old test read.
  - `Mir::leave_out` clears the list (`self.inserted.clear()`), as it sets
    `reset` to `None`, even though a function a body kept calls stays as an
    external declaration: such a declaration is kept for its call, and the list
    is for the bound's inserted edges, which only a dump with `core` would
    have. No renumbering code is needed.
  - `inserted_roots` in `src/driver.rs` now clones `mir.inserted` and adds
    `critical_enter` and `critical_exit`, which stay separate from the list
    (ADR 0123 lists the `#[export]` functions only; the two of a `critical`
    block are a `Statement`'s callees, edges of their own). The test
    `the_inserted_roots_are_there` is unchanged.
  - `mir_lists_the_inserted_functions` (in `src/driver.rs`, next to the tests
    that read the list, where `whole_mir` is) checks membership, not an exact
    list: the three memory functions, the twelve `__aeabi_mem*` functions and
    the four 64-bit division functions of `core::builtins` on both targets
    (they are defined on every target, ADR 0074; the plan's "on thumbv7m the
    `__aeabi_` functions" holds for `__aeabi_uldivmod` and `__aeabi_ldivmod`
    only, which are in `core::arch` of thumbv7m and are absent on riscv32,
    which the test also checks). It also checks no name is `_start`, a path or
    `__critical_*`, and that the ids ascend. Membership, so that a new
    `#[export]` function of `core` is not a failure of this test but is in the
    list and so in the walk of the neighbouring test.
  - `leaving_out_core_empties_the_inserted_functions` (in `src/mir/mod.rs`)
    is the unit test of the clearing, on `with_table`.
  - `validate.rs` does not check the list (its test constructor got
    `inserted: Vec::new()`): the ids come from `finish`, which lists bodies
    that exist, and no later step edits the list.

## 4. test: declare the stack the compiler cannot measure
- Status: done
- Implements: ADR 0122, "Programs migrated"
- Changes:
  - `rt/arch/riscv32.ers`: `#[stack(0)]` on `_start`, `#[stack(64)]` on
    `__erebos_trap`; `rt/arch/armv7m.ers`: `#[stack(0)]` on `_start`,
    `#[stack(24)]` on `__aeabi_uldivmod` and `__aeabi_ldivmod`. A comment on
    each number.
  - Every `extern fn` of the places listed above that `erebos build` builds:
    `#[stack(N)]` from `clang -fstack-usage` on its C definition at `-O0` and
    `-O2`, with the flags `tests/common/qemu.rs` compiles it with, the larger,
    plus what it calls. For a C function that calls back into Erebos, the
    Erebos function's depth is not known yet: this step adds a provisional
    number (the C depth plus 256), and step 7 replaces it with the depth its
    report gives, in step 7's commit. The numbers and how they were measured
    go in this step's Decisions.
  - Every `asm` without `nostack` in those places: `nostack` where the
    template does not touch the stack; `#[stack(N)]` on the function where it
    does.
- Tests: every test as before; nothing reads the attribute yet. The bound in
  step 6 finds what this step missed, and step 6 fixes it in its own commit.
- Decisions:
  - How the C was measured: `clang` 23.1.3 (`C:\Program Files\LLVM\bin`, the
    one `tests/common` finds on `PATH`; the compiler builds against LLVM 22, the
    tests have always used this clang for C). For each program that links C
    (the 24 of `tests/e2e/` that declare `extern fn`, plus `tests/elf.rs`'s
    `eabi_division` and the generator's `OPAQUE_C`), each target (the program's
    `// targets:` header, or both) and each level, the C file is compiled with
    the arguments of `qemu::compile_c` (`clang_target(target)`, `-std=c11 -Wall
    -Werror`, `-O0` or `-O2`, the program's `// c-flags:`), with `-S
    -fstack-usage` added. `-S` and not `-c` so that the same run gives the
    assembly. The `.su` file gives each function's frame; the call graph comes
    from the assembly (`call`/`tail`/`jal` on riscv32, `bl`/`b`/`b.w` to a
    symbol on thumbv7m, a branch to a label of the function not being a call).
    A scratch script (not committed, as the review scripts of step 1) computed
    `depth(f) = frame(f) + max depth(callee)` for each `extern fn` the program
    declares, over the C functions of the file.
  - The number: the largest `depth` over targets and levels, so one number
    serves both, as ADR 0122 asks. Where `f` reaches a symbol the C file does
    not define (an Erebos function, `memcpy`/`memset`/`__aeabi_*`/`__udivdi3`
    that clang emits, which `core` defines, or `_start`), the number is that
    depth plus 256, provisional, for step 7 to replace with the depth the
    report gives. 256 is the plan's figure, not a measurement of those Erebos
    functions; nothing checks it until step 7. No indirect
    call was found other than in `aeabi_memory.c`'s `check_*` helpers at `-O0`,
    which call function pointers to `__aeabi_mem*`, themselves external, so
    that function (`c_check_aeabi`) is in the +256 class. No recursion was found.
  - The numbers per program (functions; N of those that call nothing outside
    the C file; N of those that do, +256 included):
    `aapcs_c` 110 (16, 64, 80, 88, 96, 104, 120, 152, 160, 168, 176; 272 to
    584), `aeabi_memory` 2 (16; 464), `bit_structs_c` 9 (16; 272), `c_abi` 12
    (16, 32, 48, 64, 120; 336), `c_division64` 6 (none; 288),
    `comptime_differential` 17 (16, 32), `debug_dwarf4`, `debug_dwarf5` and
    `debug_gnu` 1 each (64 each, measured with their own `-g` flags), `enum_payloads_c` 5 (16, 32; 352), `enums_c` 5 (16; 272), `export_c`
    2 (16; 272), `extern_c` 5 (16, 32; 288), `extern_statics` 1 (16),
    `naked_armv7m` and `naked_riscv32` 1 each (none; 272), `options_c` 8 (16,
    32; 288, 304, 352), `references_c` 3 (16; 272, 288), `returned_references_c`
    5 (none; 288), `slice_references_c` 4 (32; 288), `slices` 4 (32, 64; 288),
    `small_data` 2 (16), `startup_bss` 1 (none; 272), `statics` 2 (16),
    `elf.rs`'s `eabi_division` 2 (none; 288), the generator's 10 `opaque_*`
    (16: 16 on riscv32 and 4 or 8 on thumbv7m at `-O0`, 0 at `-O2`; they call

  - A comment above the first `extern fn` of each program says where the

    that have such a function.
  - `rt/`: the plan's numbers, with a comment above each function (the trap

  - `asm` without `nostack` outside naked functions, in `tests/e2e/`

    list of `Call`s per body in which a check is `check: true` and every other

    `Edges::Calls` is exactly "the graph without panic edges" and
    `Edges::CallsAndPanics` the whole graph. What an edge is (`Kind`) is kept
    next to the list, in `Scan::kinds`, for the labels and the paths. The only
    change to `call_graph.rs` is `Reach::steps`, which `path` now uses: the

    a call. `Scan::kind_of` finds the kind of a `&Call` that `cycle` returns by
    pointer, since `cycle` hands back references and not indices.

    block in ascending order (as `recursion.rs` does), statements in order then
    the terminator, as ADR 0123's "Which path" asks. A `Statement::CriticalEnter`
    or `CriticalExit` is an edge to `Mir::critical_enter`/`critical_exit` when
    they exist (`None` once `core` is left out). An edge to a `comptime` body is
    left out. A body with no blocks that is not external has no edges (no
    `reachable` call on an empty body).

    set for an `asm` statement or `noreturn` terminator without `nostack` in a
    reachable block of a body that is neither naked nor external. A body that is
    `comptime` has none.

    `Reach::search(.., &mir.inserted, Edges::Calls)` (calls, `critical`, `sym`;
    no checks), checks it, and adds the inserted edges, last, in the order of
    `Mir::inserted`, to every body that is not comptime, external, naked or in
    the closure. The check is a `panic!` (the ADR's "internal error of the
    compiler"): a closure body that is not `runtime` (`Body::runtime` is "a
    function of `core`") or is the panic function. `tests/architecture.rs`'s
    `PANICS` gains `src/analysis/stack.rs: 1`. No user input reaches it: the
    closure is built from `Mir::inserted` (the `#[export]` functions of `core`)
    and the edges between `core`'s bodies, so only a change to `core` (a
    function of `core` that calls the program's code, or the panic function)
    can trip it; two unit tests build the cases by hand.
  - Cycles are looked for on every node (every body that is not `comptime`),
    not only on those a part reaches, as ADR 0120's check does over the run-time
    roots: a depth that exists only if the graph is acyclic is also shown for
    the bodies no part reaches.
  - The order of the checks and what stops what: cycles, then `missing-stack`,
    both always reported (a program can have both); with a cycle the depths are
    not computed (the report's `depths` are all `None`); with only a missing
    stack the depths are computed with unknown propagating (`None` for a body
    that reaches a function that needs `#[stack(N)]` and has none) and the total
    is not; the overflow is checked only when both are clear (ADR "Diagnostics",
    last bullets).
  - What "reached" is, for `missing-stack` and `Report::reached`: a breadth-first
    search over all edges (checks included) from the thread's root (the reset
    entry, or the entry function if MIR has none), the handlers in the order of
    their bodies, and the panic function (the default handlers call it). The
    note of `missing-stack` is that search's path: "the stack bound reaches it
    through `_start` -> `main` -> `f`", the shortest found (inserted edges
    included).
  - The depth uses a work list, not recursion (a long chain of calls must not
    overflow the compiler's stack; a test builds a chain of 1500 functions). A
    pair (body, state) that is in progress when it is met again is treated as
    unknown instead of followed, a guard that only a graph with a cycle could
    reach and that `bound` does not compute on.
  - A refinement of ADR 0123's "Which path": an edge whose target has depth 0
    is never the chosen one, so a path ends at the last body that costs
    something instead of at a leaf of 0 (every body has edges to the inserted
    functions, and most of those cost 0 on riscv32: `-> main (0) -> memcpy (0,
    inserted)` at the end of every note would say nothing). The bytes are the
    same; among targets of equal positive depth the first edge is still the one.
  - The four parts are as the ADR's table. Details it leaves open: the faults
    part is always counted (even when every fault has a declared handler: the
    bound stays pessimistic, as the ADR says of the sum); the maskable default
    is `E + D_def` when some word of the vector table is a `Default` and
    `maskable_word`, found in `Mir::vector_table` (no table, no default); a word
    is "handled" for the NMI by `Mir::handlers`' `word`; `D_def` is the largest
    default frame plus `D_before(panic)`; `D_while(panic)` is the panic
    function's frame alone, without its `N` (the guard spins before the body, and
    so before any `asm` that `N` describes).
  - `Report` is the data step 7 renders: `total`, `declared`, the four `Part`s
    (context, bytes, one or more paths of `Step { name, cost, kind }` with
    `kind` body / inserted / exception entry / default handler), the depth

    part reaches it. It does not list each body's edges: step 7 adds what its
    report needs. A path is rendered as `` `name` (cost) `` with ", inserted"
    inside the parentheses for an inserted edge, and the steps that are no body
    as `exception entry (64)` and `default handler (N)`. A part's note is
    "the thread context needs N bytes: path" (and "maskable handler context",
    "unmaskable handler context", "fault context"); an unmaskable part is the
    sum of several handlers, and the fault part of two paths, which are joined
    by " + ". `Diagnostic` has one note, so the notes of the parts that are not
    0 are one note with a line each.
  - `analysis::stack-cycle` labels: "`a` names `b` with `sym` here" (the `asm`
    statement's span), "`a` calls `b` here", "`a` calls `b` in a `critical` block
    here", "`a` may call `b`, which the compiler inserts" (the body's span); the
    message for one body is "`a` reaches itself through assembly, so the stack
    has no bound", for two "`a` and `b` reach each other ...", for more "`a`, `b`
    and `c` reach each other ...". The note is "the cycle: ...", no help.
    `analysis::missing-stack` has the label "its stack is not declared" at the
    body's span, the note above and the ADR's help.

  graph misses; the fix is an edge or a number, made in this commit.
- Decisions:
  - The calls oracle found no undercount: with the rules below, every machine
    call of the 167 programs of `tests/e2e/` (524 builds: each on the targets it
    runs on, at both levels) is an edge of the report's lines (or explained as
    below), so no edge and no number changed in
    this commit. Mutation checks, done by hand and not kept: dropping `memcpy`
    and `__divdi3` from the inserted functions made 200-odd calls fail; strict
    edges at `-O` (below) made hundreds fail, all after inlining.
  - **Strict at `-O0`, transitive at `-O`.** The plan says every call is "an edge
    of the report's lines". At `-O` LLVM inlines a callee into its caller, so the
    caller's machine code calls what the callee called (`main` calls `on_panic`
    that `consume`, inlined, called); that is no missing edge: the bound's depth
    of the caller is at least its cost plus the callee's depth, which is at least
    the callee's callees'. At `-O` the oracle therefore accepts anything the
    line reaches through other lines (`Report::reaches`, with `transitive`); at
    `-O0`, with no inlining, it requires the direct edge, which is the plan's
    rule and the sharper test of the graph. The user decided (review of step 8,
    2026-11-16) to amend ADR 0123, "Tests", to say so: the bullet of the
    machine's calls now states the direct edge at `-O0` and the reach through
    other lines at `-O`, and why the relaxation is sound for the bound.
  - **Inserted functions come from `core`'s source**, not from the report: the
    report says "inserted calls" and not which functions, and a test cannot ask
    MIR. `inserted_functions` reads the `#[export]` functions (other than
    `_start`) of `rt/builtins.ers` and the target's `rt/arch/` file, as
    ADR 0123 defines `Mir::inserted`. So that a wrong `Mir::inserted` is not
    hidden by this, `check_inserted` requires each of them to be a body of the
    report, and each body with the inserted edges to be at least as deep as its
    own cost plus theirs (a set the compiler used that left one out would show as
    a body that is not deep enough; one it used that has more, which only makes
    the bound larger, is not seen).
  - **What the oracle skips, each said in `check_machine`.** (1) Calls made by
    C's code: the `extern fn` lines of the report stand for the C function with
    its `N`, which counts what it calls (ADR 0122), so a transfer whose origin
    is a function of a C object (read with `llvm-readelf --symbols` from the
    objects the test links) is not checked (`extern fn`s that call C helpers and
    Erebos callbacks, inside their `N`). (2) The functions of the executable that
    are in no line: the default handlers (`__erebos_unhandled*`) are the
    compiler's, C's functions are C's; any other is an error. **A gap:** the
    calls the default handlers make (to the panic function) are not checked as
    edges, since they are in no line; the fault part of the bound models them,
    and the `stack_measured_fault_*` programs exercise that path at run time. (3) A jump to
    `_start`: `interrupts_masked_restart_riscv32.ers` ends in `asm("tail _start")`
    and `startup_bss`'s C calls `_start`. It is a restart, which sets the stack
    pointer to `__stack_end` (ADR 0122's "cycle through C" says the same of C's),
    so it is not a callee; the template names `_start` without `sym`, which the
    bound does not read. (4) Indirect transfers (`bx r0`, `jr` through a
    register without a name in the disassembly) have no target to compare:
    `_start`'s own jump to the entry function on thumbv7m is one, and it is an
    edge of the line anyway. A `#[stack(N)]` covers a call its line does not
    show when the callee's depth in the report is at most `N`; the plan said "a
    number covers it" and this is the reading (N counts what the function
    calls, so it holds the callee's whole depth). No program needed it; a unit
    test pins it.
  - **The machine is read by name, not by decoding.** `read_machine` takes the
    `<name>:` headers of `llvm-objdump -d` as functions (the `.L` labels, such as
    riscv32's `.Lpcrel_hi4` inside `_start`, are not functions), and an
    instruction whose mnemonic starts with `j`, `b` or `cb` and that has a
    `<name+off>` after its operands as a transfer. A target that is a `.L` label is
    placed by its address. This covers riscv32's `jal`, `j`, `jr`, `jalr` and
    thumbv7m's `bl`, `b.w`, `b`, `bx` with a name, `cbz`; the tool's own
    resolution of `auipc`+`jalr` pairs names the callee. No instruction set is
    decoded here, so no per-target disassembler is written. Unit tests feed
    it riscv32 and thumbv7m text.
  - `tests/stack.rs` builds every program on `min(available_parallelism, 8)`
    threads (each program in a work directory of its own, C objects included,
    since two programs may link a C file of the same name). The two tests run in
    parallel under cargo and both build the `stack_measured*` programs, and

    subdirectory: `CARGO_TARGET_TMPDIR/stack/calls/<target>/` and

    another format reads as none). It is a floor per build, not a count of what
    each program should have; a unit test feeds it text it cannot read.

  - **The path.** `main` reads `sp`, `la`/`movw`+`movt` of `__stack_start` in `asm`
    (a name that starts with `__` is reserved, so `extern static __stack_start`
    is `resolve::reserved-name`; the assembly names it as `core::arch`'s `_start`
    does), fills every word from `__stack_start` to `sp` with `0xA5A5A5A5` in a
    loop with no call (a callee's frame would lie in what is being filled), arms
    nothing yet, and enables interrupts as ADR 0119 asks. Then `middle` (a
    64-byte array) -> `with_buffer` (the 512-byte array, read after the call so
    it is live across it, index from a volatile read so `-O` keeps it) ->
    `with_block` (a 128-byte `Block` passed by value) -> `deepest`, which arms
    the timer (the CLINT's compare register, or SysTick's reload and control),
    waits in `critical` reads of `TICKS` so that the handler runs on top of
    every frame above, then fails the check (`seed / zero` with `zero` the tick
    count minus 1, known only at run time) or faults. The handler calls a
    function with a 96-byte array so that it has a frame of its own, writes the
    result to a static only it touches, and stops the timer (riscv32's compare
    value to `0xFFFF_FFFF`, SysTick's control to 0 and its pending bit cleared)
    so there is one tick. `BASE` and `START` are read in `critical` by the panic
    function and written in `critical` by `main`: a handler's check may call the
    panic function, so `analysis::unprotected-static` demands it.
  - **What the count is.** `used` in the panic function reads from `START` up

    first word that is not: the bytes written below the entry function's frame.

    and not in the count (ADR 0123 says so); the frames of `on_panic` and `used`
    are in both. Measured on this machine (count / worst case): riscv32 check
    1988 / 3232 at `-O0` and 944 / 1600 at `-O`; thumbv7m check 1980 / 3644 and

    check (512) would fail, which is what it is there for.
