# Plan: M5.10 No recursion

ADRs: 0120 (building on 0014, 0027, 0029, 0033, 0051, 0057, 0063, 0069, 0077,
0093, 0099, 0114)
Base: 24981a6
Program on QEMU: every program of `tests/e2e/`, migrated, with the same output
on both targets at `-O0` and `-O` (ADR 0077); and rejected programs for
direct and mutual recursion on both targets
(`tests/ui/recursion_errors.ers` and `recursion_errors_thumbv7m.ers`).
Out of scope:
- the worst-case stack depth and everything it needs: frame sizes,
  `#[stack(N)]`, the handlers' share, a panic that re-enters the panic
  function, cycles through C or assembly (M5.11; the roadmap lists them under
  "Left for the planner of M5.11");
- function pointers (deferred ideas) and M6's `comptime` function parameters
  (ADR 0120, Consequences, says how they will fit);
- the findings of `docs/open-findings.md`: worked off between steps, not here.

Decided with the user while planning (2026-11-16):
- Recursion in code that runs on the target is forbidden, with no annotation
  that allows it.
- A check that calls the panic function (`Terminator::Panic`) is no edge of the
  graph. The re-entry of the panic function is M5.11's to bound.
- Every body compiled for the target is a root, except those only compile time
  reaches. MIR gains no `export` flag.
- One error per strongly connected component, with a label on each call of
  the cycle.

Order: first the migrations that a text search finds, each keeping its
program's output or its test's point (steps 1 and 2). Then the check, which
finds what the search missed and rewrites it in the same commit (step 3). Then
the count by the compiler, and the documentation.

Where Erebos source lives (as in the M5.9 plan; each migration step searches
all of them): `rt/`, `tests/boards/`, `tests/e2e/`, `tests/ui/`,
`tests/svd/chips/`, the snippets of `tests/rejected.rs`, the programs
embedded in `tests/elf.rs`, `tests/e2e.rs`, `tests/svd.rs` and
`tests/fuzz.rs`'s corpus, the source `tests/common/generator.rs` writes, and
`tests/layout/`. The generator calls each generated function from `main` only,
but it writes a recursive `print_u64` into every generated program (found in
step 1); step 3 rewrites it to use the board's `print_u64`, and confirms the
generated programs then pass through the check.

## 1. test(e2e): print numbers through the board's `print_u32` and `print_u64`
- Status: done
- Implements: ADR 0120, "Programs migrated" (the digit-printing idiom)
- Changes:
  - `tests/boards/riscv32imac-unknown-none-elf.ers` and
    `tests/boards/thumbv7m-none-eabi.ers`: `pub fn print_u32(n: u32)` and
    `pub fn print_u64(n: u64)`. Each is a loop that writes the decimal digits
    into a fixed-size buffer (10 bytes for `u32`, 20 for `u64`) from the
    least significant, then sends them through `putc` from the most
    significant. The same text in both boards, with a comment on the idiom
    it replaces.
  - Every program of `tests/e2e/` that defines its own `print_u32` or
    `print_u64` printing plain decimal drops it and imports the board's
    (`use board::{..., print_u32};`), recursive or not.
  - A copy that prints something else (padding, a sign, another base, a
    different parameter type) stays in its program. If it recurses, it is
    rewritten there as a loop.
- Tests: the e2e suite on both targets at both levels, with every expected
  output unchanged: that proves the board's functions print what the copies
  did, `0`, `u32::MAX` and `u64::MAX` included where a program prints them.
  The search that finds the copies, and the list of copies left in their
  programs with the reason for each, go under Decisions.
- Decisions:
  - The search. (1) A throwaway script (not committed) read every `fn` of
    every `.ers` under `tests/e2e/` (subdirectories included), grouped them by
    parameter list and body with the function's own name masked, and flagged
    the bodies that call their own name. That gave 28 recursive `u32` copies,
    14 recursive `u64` copies, and 28 non-recursive digit loops (26 `u32`, 2
    `u64`), all named `print_u32` or `print_u64`, plus `modules/uart.ers`
    (recursive) whose body the script saw as a 29th recursive `u32` copy
    (`panic_location/fmt.ers` is one of the 26 loops). (2) A text search for the loop's own
    marks, `[%/]=? ?10\b` (and 100, 1000, `-= 10`, `>= 10`, `1_000_000_000`,
    `b'0' +`), over `tests/e2e/`, `rt/`, `tests/svd/`, `tests/layout/`,
    `tests/boards/`, `tests/ui/`, `tests/*.rs` and `tests/common/`, to find
    printers under another name; it found none besides those listed below.
    (3) The same script listed the self-calling functions that are not
    printers (`fib`, `walk`, and the false hits `putc` in `structs.ers` and
    `slice_elements.ers`, which call `board::putc`): they are step 2's.
  - Migrated: 62 programs lose their copy and import the board's. 27 recursive
    `u32` and 14 recursive `u64` copies, and 19 `u32` and 2 `u64` digit loops
    that were not recursive: the plan says "recursive or not", and a board
    function that the programs share is the point of ADR 0120. The import is
    kept in alphabetical order (`use board::{exit, print, print_u32, putc};`),
    and a `print` or `putc` that no other line used would have been dropped
    from it (none was).
  - The board functions are the same text in both boards, apart from the
    header comment that lists what the board offers (extended with both
    names, since it did list `print` of ADR 0117). Variable names: `digits`,
    `count`, `rest`, `i`. They send the digits through `putc`, as the
    `handler_stack_*` copies did, not through `print`, which the plan names
    (`putc` from the most significant), and which keeps the two functions
    independent of `print`'s slice parameter.
  - `modules/uart.ers` and `panic_location/fmt.ers` keep their files and
    become `pub use crate::board::print_u32;`. `modules/main.ers` calls
    `uart::print_u32` on purpose (the program is about calls by path between
    files), and `panic_location/main.ers` expects its division at line 12 and
    says the program has four files: dropping `mod fmt;` or the `use` would
    shift line 12 and change the output. `uart.ers` keeps its other items
    (`LINES`, `newline`).
  - `ring_methods.ers`: `mod ring` had `use super::print_u32;`; it is now
    `use super::board::print_u32;`, as the line above it does for `putc`.
  - Copies left in their programs, and why:
    - `structs.ers` `print_u32`: prints through the program's own `putc`, which
      writes to a struct-described register in the board's scratch RAM (the
      point of that program). It recursed, so it is rewritten there as a loop,
      with the board's text but for the `putc` it calls.
    - `print.ers` `print_u32` and `print_number`: print through the program's
      own `print`, which counts the bytes written in `WRITTEN` (its output
      shows the count); `print_hex` is a different base.
    - `subslices.ers` `print_u32`: its comment says the range with a start not
      known at compile time is the point (ADR 0108).
    - `slices.ers` and `slice_elements.ers` `print_u32`: they build the slice
      of the digits with `slice(&raw const digits[..], n)` (ADR 0117) and print
      it through the program's own `print`/`putc` on raw slices and a
      volatile cell: both exercise what they test.
    - `uart_chain_armv7m.ers` and `uart_chain_riscv32.ers` `print_u32`: write
      through the program's UART object (`UART.write`, `UART0.write`), the
      chain of method calls the program tests; not through the board's `putc`.
    - `slice_driver.ers` `decimal`: writes into a caller's buffer and returns
      where the digits start; another signature, not a printer.
    - `functions.ers` `print_u8`: a `u8` parameter and a subtraction loop (a
      different parameter type, as the plan says).
    - `print_i32`, `print_i64` (`conversions`, `division`, `division64`,
      `bit_structs`, `c_division64`, `enums_c`): print a sign; they call the
      imported `print_u32`/`print_u64` and are not recursive.
    - `print_hex`, `print_digit`, `print_pair`, `print_line`, and the
      two-digit printers of `ecall_handler_riscv32.ers`,
      `handler_check_armv7m.ers` and `vector_unhandled_systick.ers` (padding to
      two digits): other bases, one digit, or fixed width.
    - `tests/common/generator.rs` writes a recursive `print_u64` into every
      generated program (`fn print_u64` in its template, with `mod board;`
      above it). It is outside `tests/e2e/`, so not touched here. The plan's
      statement that the generator "writes no recursion" is wrong for this
      function: step 3's check will reject every generated program until it is
      changed to `board::print_u64`. Left for the planner to place (step 3 as
      "what the search missed", or here).
  - Tests: no test was added. The e2e suite (`cargo test --test e2e`, both
    targets, both levels) passes with every expected output unchanged. Among
    the values it prints through the board's functions: `0` (several
    programs), `u32::MAX` (`conversions`, `number_parser`, through
    `print_u32`) and `u64::MAX` (`options_c`, through `print_u64`).

## 3. feat(analysis): reject recursion in code that runs on the target
- Status: todo
- Implements: ADR 0120, "The rule", "The call graph", "What runs on the
  target", "The diagnostic"
- Changes:
  - `src/analysis/call_graph.rs`: the strongly connected components of a
    graph given as `calls` (the same shape `Reach::search` takes), in the
    order of their first body, and the shortest cycle through a body within
    its component, breadth first, each body's calls in order. Iterative,
    with no recursion in the compiler either, so that a deep chain of calls
    in a program cannot overflow the compiler's stack.
  - `src/analysis/recursion.rs`, new:
    - a scan of each body's `Statement::Call`s in the blocks reachable from
      its start, with their spans, `comptime` bodies included (unlike
      `shared_statics::Scan`, which skips them);
    - the compile-time-only set, from the `comptime` bodies, with
      `Reach::search` and `Edges::Calls`;
    - the run-time roots and their reach;
    - the components of the run-time graph, and one `analysis::recursion`
      per component with a cycle, worded as ADR 0120's "The diagnostic"
      says, names through `bits::shown`.
  - `src/analysis/mod.rs`: `check` runs it after `call_borrows::check`; the
    module comment names it among the analyses of the whole program.
  - Whatever the check rejects that steps 1 and 2 missed is rewritten here as
    they would have done, and listed under Decisions.
  - `docs/reference.md`: the row of `analysis::recursion` in the table of
    error codes (the section on the rule comes in step 5); `tests/rejected.rs`
    reads that table.
- Tests:
  - Unit tests in `call_graph.rs`:
    - a body that calls itself is a component with a cycle of one call;
    - a body with no call to itself, alone, is a component without one;
    - two cycles through one body give the shorter;
    - the cycle follows the order of a body's calls;
    - components come in the order of their first body.
  - `tests/ui/recursion_errors.ers` (riscv32), one error each for:
    - direct recursion called from `entry`;
    - mutual recursion of two functions;
    - a cycle of three;
    - a cycle through a method call (`x.f()`, ADR 0114);
    - a recursive function that nothing calls;
    - a function that a constant calls and `entry` calls too;
    - a function that calls itself twice (one label, on the first call);
    - mutual recursion where the first function calls the second twice
      (one label, on the first of the two calls);
    - an interrupt handler that calls a recursive function;
    - a panic function that calls a recursive function.

    The labels in the snapshot show the span of each call, a method call's
    included.
  - `tests/ui/recursion_errors_thumbv7m.ers`: direct and mutual recursion on
    thumbv7m, so that the rejected program runs on both targets.
  - `tests/ui/recursion_modules/`: a cycle across two modules, its labels
    in both files and the names shown as paths with `::`.
  - `tests/ui/recursion_accepted.ers`:
    - a recursive function that only a constant's initializer calls;
    - one that only a `comptime` block in a function calls;
    - a recursive function that a function calls, where only a constant
      calls that function (compile-time reach is transitive);
    - a function whose call to itself is in a block that cannot be reached,
      which is no edge. The block must exist in MIR, or the test proves
      nothing: the implementer finds a form whose dead block MIR keeps (after
      `return`, after `loop {}`, or after a call to a `-> !` function), shows
      it with a MIR dump, and records the form under Decisions. If MIR keeps
      no such block, the case moves to a unit test of the scan, on a body
      built by hand.
    - a panic function that prints its message through a function with a
      bounds check, which is no edge.
  - `tests/rejected.rs`: two snippets of items for `analysis::recursion`, a
    function that calls itself and two that call each other, all uncalled
    (ADR 0120, Consequences).
  - Every existing test passes, the e2e programs and the generated programs
    of ADR 0068 among them: they now pass through the check.
  - `tests/architecture.rs` passes with its tables unchanged: the new module
    names only `mir` and the shared modules.
  - No test of its own puts a cycle through `core` (ADR 0120, Consequences).
  - The analysis keeps its orders in `Vec`s and `BTreeMap`s, never by
    iterating a `HashMap` or `HashSet`, so that the snapshots are
    deterministic (ADR 0120, "The diagnostic").
