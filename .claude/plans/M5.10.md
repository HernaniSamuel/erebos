# Plan: M5.10 No recursion

ADRs: 0120 (building on 0014, 0027, 0029, 0033, 0051, 0057, 0063, 0069, 0077,
0093, 0099, 0114)
Base: 24981a6
Program on QEMU: every program of `tests/e2e/`, migrated, with the same output
on both targets at `-O0` and `-O` (ADR 0077); and rejected programs for
direct and mutual recursion on both targets
(`tests/ui/recursion_errors.ers` and `recursion_errors_thumbv7m.ers`).
Out of scope:
- the worst-case stack depth and everything it needs: frame sizes,
  `#[stack(N)]`, the handlers' share, a panic that re-enters the panic
  function, cycles through C or assembly (M5.11; the roadmap lists them under
  "Left for the planner of M5.11");
- function pointers (deferred ideas) and M6's `comptime` function parameters
  (ADR 0120, Consequences, says how they will fit);
- the findings of `docs/open-findings.md`: worked off between steps, not here.

Decided with the user while planning (2026-11-16):
- Recursion in code that runs on the target is forbidden, with no annotation
  that allows it.
- A check that calls the panic function (`Terminator::Panic`) is no edge of the
  graph. The re-entry of the panic function is M5.11's to bound.
- Every body compiled for the target is a root, except those only compile time
  reaches. MIR gains no `export` flag.
- One error per strongly connected component, with a label on each call of
  the cycle.

Order: first the migrations that a text search finds, each keeping its
program's output or its test's point (steps 1 and 2). Then the check, which
finds what the search missed and rewrites it in the same commit (step 3). Then
the count by the compiler, and the documentation.

Where Erebos source lives (as in the M5.9 plan; each migration step searches
all of them): `rt/`, `tests/boards/`, `tests/e2e/`, `tests/ui/`,
`tests/svd/chips/`, the snippets of `tests/rejected.rs`, the programs
embedded in `tests/elf.rs`, `tests/e2e.rs`, `tests/svd.rs` and
`tests/fuzz.rs`'s corpus, the source `tests/common/generator.rs` writes, and
`tests/layout/`. The generator calls each generated function from `main` only,
but it writes a recursive `print_u64` into every generated program (found in
step 1); step 3 rewrites it to use the board's `print_u64`, and confirms the
generated programs then pass through the check.

## 3. feat(analysis): reject recursion in code that runs on the target
- Status: done
- Implements: ADR 0120, "The rule", "The call graph", "What runs on the
  target", "The diagnostic"
- Changes:
  - `src/analysis/call_graph.rs`: the strongly connected components of a
    graph given as `calls` (the same shape `Reach::search` takes), in the
    order of their first body, and the shortest cycle through a body within
    its component, breadth first, each body's calls in order. Iterative,
    with no recursion in the compiler either, so that a deep chain of calls
    in a program cannot overflow the compiler's stack.
  - `src/analysis/recursion.rs`, new:
    - a scan of each body's `Statement::Call`s in the blocks reachable from
      its start, with their spans, `comptime` bodies included (unlike
      `shared_statics::Scan`, which skips them);
    - the compile-time-only set, from the `comptime` bodies, with
      `Reach::search` and `Edges::Calls`;
    - the run-time roots and their reach;
    - the components of the run-time graph, and one `analysis::recursion`
      per component with a cycle, worded as ADR 0120's "The diagnostic"
      says, names through `bits::shown`.
  - `src/analysis/mod.rs`: `check` runs it after `call_borrows::check`; the
    module comment names it among the analyses of the whole program.
  - Whatever the check rejects that steps 1 and 2 missed is rewritten here as
    they would have done, and listed under Decisions.
  - `docs/reference.md`: the row of `analysis::recursion` in the table of
    error codes (the section on the rule comes in step 5); `tests/rejected.rs`
    reads that table.
- Tests:
  - Unit tests in `call_graph.rs`:
    - a body that calls itself is a component with a cycle of one call;
    - a body with no call to itself, alone, is a component without one;
    - two cycles through one body give the shorter;
    - the cycle follows the order of a body's calls;
    - components come in the order of their first body.
  - `tests/ui/recursion_errors.ers` (riscv32), one error each for:
    - direct recursion called from `entry`;
    - mutual recursion of two functions;
    - a cycle of three;
    - a cycle through a method call (`x.f()`, ADR 0114);
    - a recursive function that nothing calls;
    - a function that a constant calls and `entry` calls too;
    - a function that calls itself twice (one label, on the first call);
    - mutual recursion where the first function calls the second twice
      (one label, on the first of the two calls);
    - an interrupt handler that calls a recursive function;
    - a panic function that calls a recursive function.

    The labels in the snapshot show the span of each call, a method call's
    included.
  - `tests/ui/recursion_errors_thumbv7m.ers`: direct and mutual recursion on
    thumbv7m, so that the rejected program runs on both targets.
  - `tests/ui/recursion_modules/`: a cycle across two modules, its labels
    in both files and the names shown as paths with `::`.
  - `tests/ui/recursion_accepted.ers`:
    - a recursive function that only a constant's initializer calls;
    - one that only a top-level `comptime { }` item calls (a `comptime`

      body, so it is a case of `recursion_errors.ers`; user decision of

  - `tests/rejected.rs`: two snippets of items for `analysis::recursion`, a
    function that calls itself and two that call each other, all uncalled

  - Every existing test passes, the e2e programs and the generated programs

  - No test of its own puts a cycle through `core` (ADR 0120, Consequences).

    deterministic (ADR 0120, "The diagnostic").
- Decisions:
  - What the check found that steps 1 and 2 missed: only
    `tests/common/generator.rs`'s recursive `print_u64`, which the task named
    in advance. The full suite (e2e on both targets at both levels, the
    generated programs, the ui snapshots, `elf`, `svd`, `fuzz`) passes through
    the check with no other change. The generator's template drops its
    `print_u64` and `check` calls `board::print_u64` (every generated program
    has `mod board;` above it). No other file of the tree needed a rewrite.
  - The note of ADR 0120's diagnostic needed a field `Diagnostic` did not
    have: `Diagnostic::note` and `note: Option<String>` in `src/diag.rs`.
    `miette` has no notes, so `render` builds the handler per diagnostic and
    gives it the note as its footer, which `miette` prints after the help,
    separated by a blank line (the snapshots show `help:` and then the line
    `the cycle: ...`). A footer is the nearest thing `miette` offers; the
    alternative, folding the note into the help, would have mixed a fact with
    advice. One unit test in `diag.rs` shows the note after the help and only
    on its own diagnostic. The arrow in the note is `\u{2192}` (the ADR writes
    it so).
  - `call_graph.rs` gets `components` and `cycle` and the type `Component`
    (`bodies` in ascending order, `cyclic`). `components` takes the graph as
    the `calls` of `Reach::search` plus a `nodes: &[bool]` (the bodies that
    are vertices; a call to another body is no edge) and the `Edges`, so the
    run-time reach is passed as a mask rather than as a copy of the graph.
    It is Tarjan's algorithm with an explicit work list. `cycle` returns the
    calls of the cycle each with the body that holds it (a call knows its
    callee only), so that a label can name the caller. `BodyId` has no `Ord`,
    so the orders are by its number.
  - `recursion.rs` scans every body that is not external, `comptime` bodies
    included, with `bits::reachable` for the blocks and the same span rule as
    `shared_statics::Scan` (the statement's span, else the terminator's). A
    `Call` there has `outside: true` and `check: false`; `Site` is reused as
    it is. `Terminator::Panic` is never scanned, so `Edges::Calls` would be
    enough even if it were.
  - The message for three or more functions is "`a`, `b` and `c` call each
    other in a cycle"; the label of a self-call is "`f` calls itself here";
    the note and the help are those of ADR 0120. A cyclic component whose
    `cycle` comes back empty (it cannot) is skipped rather than panicking,
    so the file adds no panic (`PANICS` unchanged).
  - `analysis/mod.rs` runs it last, after `call_borrows::check`, and its
    module comment lists it.
  - Tests. `call_graph.rs`: the five the plan names, plus one that shows checks and
    bodies not marked as vertices are no edges, and one with a chain of 200,000 calls closed
    into a cycle (the compiler's stack does not grow with it). `recursion.rs`
    (unit): a call in a block that no block reaches is no edge; the order of
    the calls; a `comptime` body is scanned and an external one is not.
    `tests/ui/recursion_errors.ers`: the ten cases of the plan, in the order
    the plan lists them (the method case is a cycle of `Counter::step` and
    `through_method`, whose call `c.step()` is labeled whole).
    `recursion_errors_thumbv7m.ers`, `recursion_modules/` (`ping.ers` and
    `pong.ers`, labels in both files, names as `ping::start`),
    `recursion_accepted.ers`. `tests/rejected.rs`: two snippets (one function,
    two functions), `Mir` stage, `Items`; the existing catalog test reads the
    table row in `docs/reference.md`, which is added.
  - The dead block of the plan. MIR keeps no block that nothing reaches, in any
    form tried (code after `return`, after `loop {}`, after a call to a
    `-> !` function, after `continue` and `break`, after a `match` or an `if`
    whose branches all return, after `while` with a `return` in it): the
    builder emits nothing once control has diverged (`current` is `None`).
    The case is therefore the unit test of the scan on a body built by hand,
    as the plan allows; the ui test says so in its header.
  - `recursion_accepted.ers` shows, in its MIR dump, `first_byte` with its
    `panic(index out of bounds ...)` terminator called from the panic function
    and no error: the panic-function case.
  - The limit on `comptime` expressions (user decision, 2026-11-16). A
    `comptime` expression inside a function body
    (`fn g() -> u32 { comptime power(2, 3) }`) is run by the evaluator and its
    body is dropped (`Queries::comptime_value`), so it is not in `Mir::bodies`
    and the check cannot see its calls. A recursive function reached only that
    way has no caller in MIR: it is a run-time root and is rejected. The user
    chose to accept this limit. Exempt are only the bodies in `Mir::bodies`
    marked `comptime`: constants, statics, array lengths written without the
    `comptime` keyword, and the top-level `comptime { }` item. A `comptime`
    expression is never exempt, inside a function or inside an array length.
    `recursion_accepted.ers` has a constant, a static, an array length with a
    repeat count (`static BUFFER: [u8; width(3)] = [0; width(3)];`) and a
    top-level `comptime { }` item (a review finding added the static and the
    array length). ADR 0120 was amended
    for this, in "What runs on the target" and in Consequences, its status
    staying Accepted, with a note that M6 may reopen it; the row of
    `analysis::recursion` in `docs/reference.md` says the same. Options not
    taken: keeping the dropped bodies in `Mir` as `comptime` bodies, or
    recording their callees on the function's body.
  - The case lives in `recursion_errors.ers` (`only_in_comptime`, called only
    by `comptime only_in_comptime(2)` in `uses_comptime`), not in
    `recursion_accepted.ers`, since it is rejected: one more error in the
    snapshot (11 in all), and its header names the limit. In
    `recursion_accepted.ers` the `comptime`-only case is the top-level
    `comptime { }` item, and its header says the expression is not there
    (its body is dropped).
