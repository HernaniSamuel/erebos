# Plan: M2.5a Follow-ups of M2.5: zero-sized payload offsets and failed lengths or alignments

ADRs: 0047, 0048
Base: 54771a2
Program on QEMU: none. This step changes only what is reported for
programs with errors, and adds tests; no program that runs changes.
Out of scope:
- a pointer to a type that reaches a failed value staying usable where
  its pointee is not reached, and the false `ty::cycle` that follows
  (ADR 0048, revisited in M6);
- the minor findings left open by M2.5 (`.claude/plans/M2.5.md`, "Left
  open"), unless a step below touches the same line.

Decided while planning (with the user):
- Diagnostics on a type that *contains* a type reaching a failed value,
  computed from the layout that type keeps, are kept: a `#[packed]`
  struct holding it (`ty::aligned-in-packed`), an `#[align(N)]` below
  its alignment (`ty::invalid-align`), an array of it too large
  (`ty::too-large`). An `#[align(N)]` only raises an alignment and a
  failed length is laid out as empty, so the kept layout is a lower
  bound and these errors hold whatever the failed value would have
  been: they are errors of the program, not a cascade. Lengths already
  behave so (a47eb48); alignments follow the same approach: the struct
  keeps the layout it has without the attribute, and `lacks_layout`
  finds the error.
- ADR 0048 says a static whose alignment is in error is compiled with
  its natural alignment. `static_align` returns `None` after the error
  today, which nothing before codegen can observe; step 3 makes it
  return the natural alignment, so the code says what the ADR says.

## 1. test(layout): zero-sized payload values have an offset
- Status: todo
- Implements: ADR 0047, "Conformance tests".
- Changes: tests only.
  - `tests/ui/typeck_option_result.ers`: in its `comptime` block,
    `size_of(Option([u32; 0])) == 4` and `align_of(Option([u32; 0])) ==
    4`, and a use of `Option([u32; 0])` so that the dump lists it with
    `Some([u32; 0] at 4)`.
  - `tests/layout/structs.ers` and `structs.h`: a field
    `Option([u32; 0])` in `WithOptions`. Its C twin gives the payload a
    zero-length array member, `uint32_t p0[0]` (a GNU C extension, as
    `struct {} p0` already is for `Option(())`), so that
    `tests/c_layout.rs` checks the offset 4 against clang.
  - `tests/c_layout.rs`: `c_name` writes an array type `[T; N]` as
    `<T>x<N>` (`Option([u32; 0])` → `OptionU32x0`), since `OptionU320`
    reads as a 320-bit integer; update the naming comment in
    `tests/layout/structs.ers`.
- Tests: the above; the layout test fails if the offset or size of
  either zero-sized payload changes.

    `typeck_failed_length_values.ers` if the snapshot would mix two

      struct P { h: Holder }` with `struct Holder { a: A8, b: Broken }`

    does not use `Broken`, reported, showing that lowering ran.
  - ui (MIR): the `ty::cycle` of ADR 0048's Consequences,
    `const N: usize = f(0 as *const S); fn f(p: *const S) -> usize { 4 }

## 3. fix(layout): a struct whose alignment failed is erroneous
- Status: todo
- Implements: ADR 0048 for `#[align(N)]`: a struct's alignment that
  fails to evaluate or to type check, or is `ty::invalid-align`, makes
  the struct erroneous; a static's does not.
- Changes:
  - `src/query.rs`: today `struct_layout` lays such a struct out as if
    it had no attribute (`checked_align` returns `None` and `align`
    keeps the natural value). Keep that layout, and make
    `lacks_layout` (hence `is_erroneous` and `needs_missing_layout`)
    find a struct whose alignment failed, for every failure kind:
    `array_len` giving no value covers evaluation and type errors, but
    `ty::invalid-align` is decided in `checked_align`, so its outcome
    must be known there too (recorded with the layout, for example), and
    reported once. Effects, as ADR 0048 lists: uses type check and
    report their own errors, except `match` coverage, payload-pattern
    types and `?`; `size_of`, `align_of`, `offset_of` have no value, and
    what depends on them is not evaluated; code reaching the struct is
    not built into MIR. The diagnostics of "Decided while planning"
    stay.
  - `static_align`: after reporting a failed or invalid alignment,
    return the natural alignment of the static's type instead of `None`
    (see "Decided while planning").
- Tests:
  - ui (typeck) `typeck_failed_align.ers`, one struct per failure kind:
    `#[align(1 / 0)]` (evaluation), `#[align(true)]` (type), and
    `#[align(3)]` and an alignment below the natural one
    (`ty::invalid-align`). For each: only the alignment's error;
    `assert`s on `size_of`, `align_of` and `offset_of(T, x)` silent; a
    mismatch on `*const T` still reported; a `match` on an enum with a
    `*const T` payload not checked for coverage, a wrongly typed pattern
    in that payload and `?` over such an enum silent. Values that depend
    on `T`: `#[align(align_of(T))] struct U { x: u8 }` and
    `struct V { a: [u8; size_of(T)] }`, with an `assert` on each, silent
    (they become erroneous in turn). Kept diagnostics: `#[packed] struct
    P { t: T }`, `#[align(2)] struct W { t: T }` and a struct field
    `[T; 0x4000_0000]`, each reported once, at its one written place. Do not test an alignment above the maximum: it
    can only be written as a literal above `usize`, which lowering
    accepts as a `u64` (see "Found while planning").
  - ui (MIR) `mir_failed_align.ers`: for each failure kind, functions,
    constants, statics and `comptime` code using its struct by value,
    behind a pointer, in an array, a field and a payload, at compile time
    and at run time, each holding a MIR-only error (`7 / 0`) that is not
    reported, beside a control function whose `7 / 0` is. The alignment
    cycle `#[align(f(0 as *const T))] struct T { x: u32 }` with
    `fn f(p: *const T) -> usize { 8 }`, a `ty::cycle` today, pinned.
    `#[align(1 / 0)] static X: u32 = 0;` and `#[align(3)] static Y: u32
    = 0;` with a function using them: that function is still built, its
    `7 / 0` reported.
  - Each new test reports more without the fix (check it, and say so in
    the report), except the static and cycle cases, which pin today's
    behaviour.

## Found while planning

- A literal array length or `#[align(N)]` argument is taken as a `u64`
  without a `usize` range check (`src/hir/lower.rs`, around line 934):
  `#[align(4294967296)]` reaches "alignments go up to 2147483648", and
  `[u8; 4294967297]` is `ty::too-large`, where `const X: usize =
  4294967296;` is `ty::literal-out-of-range`. Not part of this step.
- `ty::too-large` is reported at each place a too-large type is
  written, so `static A: [u32; 0x4000_0000] = [0; 0x4000_0000];` gives
  it twice, at the type and at the repeat expression, for any element
  type. This looks intended (ADR 0045 reports "at each place it is
  written"); the tests above write such arrays as struct fields, which
  have one place.
