# Plan: M2.3b Statics and byte strings

Base: 7569c2d8092447d621823ed541e44133b6e95703
ADRs: 0030, 0031, 0032, 0033, 0034
Program on QEMU: prints with a real `print` function: byte strings and
numbers written to the UART through slices, using statics (ADR 0031).
Out of scope:
- sharing a `static mut` with interrupt handlers, and moving `_start` into
  the language (M4, ADR 0030);
- passing the `assert` message to the panic function, and symbol names
  with modules (M2.6, ADR 0030, 0031);
- revisiting the `(*s)[i]` syntax with references, and statics that
  must not be copied (M5);
- `compile_error` (M6, ADR 0031);
- memory regions declared in the language (M3); until then the generated
  linker script splits QEMU's RAM (ADR 0030).

ADR 0033 changes no code: it redraws ADR 0003's diagram to match what
M2.3a built. The last step checks that its claims about the code still
hold.

Before step 1: the `docs(adr)` commit that accepts ADR 0030 to 0033 also

## 1. fix(eval): compare pointers as at run time, and reject dangling ones
- Status: done
- Implements: ADR 0030, "Comparing pointers at compile time" and
  "Dangling pointers" (for the evaluation's own variables; statics, byte
  strings and `extern static`s follow in steps 3, 5 and 7)
- Changes: `src/eval.rs`:
  - `compare`: `==`/`!=` between different objects answered only when
    both pointers are strictly inside non-empty objects; orderings within
    one object only with both offsets in [0, size]; everything else
    `eval::pointer-compare`.
  - The objects of a frame are marked dead when it returns; comparing a
    pointer to one, or accessing memory through it, is
    `eval::dangling-pointer`. Copying it is allowed.
- Tests: ui `eval_` snapshots: ordering within one array; `==` and `!=`
  between two live locals, answered; `==` with one pointer one past the
  end of its local, an error (it answered `false` before); `==` with a
  zero-sized local, an error; `<` across locals, an error; `<` with an
  offset that wrapped (`&raw const p[0xFFFF_FFFF] < p`), an error;
  `addr(1) == addr(2)` and a read through `addr(1)`, where `addr` returns
  the address of its own local, `eval::dangling-pointer`.

## 1a. fix: never take the address of data computed at compile time
- Status: done
- Implements: ADR 0029, "A constant is a value, not a place": it has no
  address, so `&raw` of it is `ty::not-a-place`. Today `&raw const T` is
  rejected but `&raw const T[1]` and `&raw const S.f` are accepted, which
  makes pointers into constant data; compile-time comparisons of those
  could disagree with run time, where codegen may merge identical data
  (found reviewing step 1).
- Changes: `src/ty.rs`: a place expression rooted in a constant, through
  any chain of indexing and field projections, is not a place for `&raw`
  (`ty::not-a-place`, with the existing help). Reading `T[i]` and `S.f`
  stays as it is (ADR 0029). Indexing or projecting through a pointer held
  in a constant (`(*P).f`, `BASE[1]` with `BASE` a pointer) stays a place.
- Also (user decision, found implementing this step): an aggregate
  `comptime` expression is bound to the same read-only data, so
  `&raw const (comptime t())[1]` pointed into it too. A `comptime`
  expression is a value like the call it replaces: when it is projected
  for `&raw`, MIR building copies it into a fresh local first, as for any
  value that is not a place (`&raw const (t())[1]`). Reading
  `(comptime t())[1]` still goes straight to the data.
- Tests: ui: `&raw const T[1]`, `&raw const S.f`, `&raw const S.a[2]`
  and `&raw mut T[0]`, each `ty::not-a-place`; `&raw mut (*UART).ctrl`
  and `&raw mut BASE[1]` through constant pointers, still accepted;
  reading `T[i]` and `S.f`, unchanged. MIR snapshot: `&raw const
  (comptime t())[1]` takes the address of a fresh local holding a copy;
  eval: two functions returning such pointers compare by the rules for
  locals (dangling once returned), never as one shared object.

## 1b. fix(mir): copy values that are not places before using them as places
- Status: done
- Implements: ADR 0018 ("a read happens where it is written"); found
  reviewing step 1a. Type checking treats a value that is not a place
  (`{ x }`, a call, a cast) as a temporary, but MIR building, in the
  fallback arm of `place_then` (`src/mir/build.rs`), reuses the place of
  the local the value came from when it is not constant data:
  - `&raw const ({ x })[0]` points into `x` itself, so a later
    `x[0] = 9` shows through the pointer;
  - `({ x })[{ x[0] = 9; 0 }]` reads `9`, since the read of `x` is
    deferred past the index's side effect, where ADR 0018 gives `1`.
- Changes: `src/mir/build.rs`: when an expression that is not a place is
  used as the base of a place (indexing, a field, `&raw`), and its operand
  is a place another expression can write (a user variable or one of its
  parts), it is copied into a fresh temporary where it is evaluated.
  Temporaries nothing else can write (a call's result) need no copy.
  Constant data keeps its step 1a rule (copy only for `&raw`).
- Tests: MIR snapshots for both cases above, showing the copy; e2e (or
  a differential test): both programs give `1`, unoptimized and with
  `-O`, and the same at compile time; existing snapshots where no copy is
  needed (a call's result indexed) unchanged.

## 2. feat: check shift amounts, divisors and indices known at compile time
- Status: done
- Implements: ADR 0032
- Changes:
  - `src/ty.rs`: drop the literal-only checks (`constant_index`,
    `check_divisor`, the range check in `shift_amount`).
  - `src/mir/build.rs` (or a small module beside it): when building a
    shift, `/`, `%` or an array index, compute the operand if it is known
    at compile time (literals, `const` items, `comptime` expressions,
    `size_of`/`align_of`/`offset_of`, unary `-` and `!`, binary
    operators, `as`, parentheses; never `*`, `&raw` or static reads, so
    computing one never reads memory). Values of constants and `comptime` expressions come from
    the queries (`src/query.rs`); arithmetic and casts reuse the
    evaluator's functions (`src/eval.rs`, made `pub(crate)`), so the
    target's arithmetic has one implementation. A known operand whose own
    computation fails (`1 / ZERO`) reports that failure.
  - Shift amounts are compared with their own type's sign (a negative
    amount is out of range); compound assignments are checked too.
  - Code that cannot run: while building an `if` with a known condition,
    the branch it never takes; `&&`/`||` with a known left operand that
    decides the result, the right operand; a `while` known `false`, its
    body. They are built with these checks off.
  - A failure is reported once, at the innermost operation.
  - Diagnostics keep their `ty::` codes and say the value when the operand
    is not a literal (`BITS is 32`).
  - `src/query.rs`, `src/driver.rs`: every function that type checks is
    lowered to MIR and checked, even when others have errors; the driver
    stops after that phase (the diagnostics of the MIR phase are reported
    before `into_mir`, never dropped), and `--emit=typeck` still stops
    before it. A body with such an error is marked failed, so an
    evaluation that needs it reports nothing more.
  - Also (user decision, found implementing this step): a function whose
    types reach a struct without a layout (one that contains itself, or
    is too large; already reported) is left out of MIR without a new
    diagnostic, as a body that does not type check is. Building its MIR
    used to crash the compiler, already at the base commit when a
    constant called it, and lowering every function makes that common.
    A regression test covers it.
- Tests: ui snapshots for each of the three checks with a constant, a
  `comptime` expression, `BITS - 1 + 1` and `IDX as usize`; a negative
  shift amount; `<<=`, `>>=`, `/=`, `%=`; `if`, `&&`, `||` and `while`
  with a known condition, not reported, and with an unknown one,
  reported; `x / (A / ZERO)`, reported once; `x >> *CTRL` with a constant
  pointer to a volatile register, accepted; a check failing in one
  function while another has a type error, both reported; a compile-time
  call to a function with such an error, reported once. The existing
  `// emit: typeck` snapshots that hold these checks alongside type
  errors (`typeck_int_errors`, `typeck_division_errors`,
  `typeck_array_errors`, `typeck_byte_zero_divisor`,
  `typeck_failed_length_users`) are split: the type errors stay at
  `typeck`, the checks move to `mir` snapshots, with the same codes and
  messages.
