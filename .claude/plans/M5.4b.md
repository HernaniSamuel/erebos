Order: references to slices go through every layer at once (1), since a type
that checks must reach MIR, evaluation and code generation; it brings places
of type `[T]` with `Index`, which the conversion (2) and sub-slices (3) build
on. The conversion (2) adds `ConstSubslice`, which sub-slices of arrays with
known bounds (3) reuse. The program (4) needs all three. Each step that adds a
projection extends the validator, the borrow analysis, the analyses of moves
and linearity, the check of shared statics, code generation and the evaluator
in the same commit, so that no layer meets a projection it does not know. A
diagnostic case gets, in the step that adds it, its ui test and, where it
changes a row, its row in the check tables of `docs/reference.md`; the prose
of the reference comes in the last step. No code is new (ADR 0108), so
`tests/rejected.rs` gains no snippet unless a step's `Decisions` say why. Each
step gains a `Decisions:` list while it is built (`/build-step`), for the
choices it makes that this plan and the ADRs do not dictate.

- Decisions:
  - Syntax: a range is `ExprKind::Subslice { base, from, to, open }` in the AST
    (a variant of the postfix node, as `Index` is; no range value exists),
    built by `Parser::index_or_range`, which `postfix` calls after a `[`: it
    parses the first expression with `nested_expr`, which stops at `..` since
    no infix operator is `..`, so `a + 1..b as usize` is the plan's
    `(a + 1)..(b as usize)` without a precedence level of its own. `..=` (after
    a bound or first) is "expected `..`, found `..=`" at the `..=`, with a help
    giving `base[a..b + 1]`; `..` alone is "expected a bound next to `..`,
    found `]`" at the `..`, with a help giving `&*s` and the conversion. Both are
    `parser::unexpected-token` (constants `CLOSED_RANGE_HELP` and
    `WHOLE_RANGE_HELP`). The AST dump is the derived `Debug`, so it needed no
    code.
  - HIR: `ExprKind::Subslice` has the AST's shape; `walk` visits base, `from`,
    `to`; the typeck dump labels it `subslice`; `ty/linear.rs`'s `operands_of`,
    `ty/asm.rs` (an `inout` place) and `place::is_place` name it, so it is a
    place wherever `Index` is one.
  - Type checking: `Checker::subslice` (`ty/place.rs`) mirrors `Index`'s arm: an
    array base (a place, or the value in a temporary: `PlaceInfo::temporary`,
    so `MSG[1..3]` is `constant` and `&raw mut f()[1..3]` `Temporary`) and a
    `[T]` base reached through a pointer or a reference (`Ty::Slice` with a
    place, the `layout_of` check of `Index` kept) give a place of type `[T]`
    with the base's `PlaceInfo` (`via`, `immutable`, `misaligned`, `static_mut`,
    `via_ref`), so `&`, `&mut`, `&raw` and the volatile, packed and `static mut`
    rules need no case of their own. A base of type `!` gives a place of type
    `!`, as `Index` does, and `has_address` reports it under `&` and `&raw`.
    The array of `!` of the plan's error list cannot be tested: `[!; N]` is
    `ty::never-in-memory` at its type and its elements become `Ty::Error`, so
    the check has no code.
  - A range on a register array or a cluster array is `ty::register-address`
    at the range itself, whatever follows, by calling `has_address` on the
    array's place and returning `PlaceInfo::ERROR`. Leaving the register in the
    sub-slice's `PlaceInfo`, so that only `&` and `&raw` report it, would let
    `P.regs[1..3][0]` read an element as a register with no entry access
    recorded. The message is that of the register array.
  - `may_be_misaligned` takes the element's alignment for a place of type
    `[T]`, so a range on a `[u32; 2]` of a packed struct is
    `ty::packed-field-address` ("a `[u32]` that may be misaligned") and one on
    a `[u8; 2]` is not; the help for a slice says to copy the array (the
    existing help says the value).

    without a length: `ty::slice-pointer-index` for a raw slice and
    `ty::cannot-index` for the rest, "cannot take a range of a value of type
    `T`", with the label of ADR 0108 ("a range needs the length of an array or
    a slice"; "a reference, not an array or a place of type `[T]`" and "a slice,
    not an array..." for the two with a help `(*s)[a..b]`). The helps: `(*s)[a..b]`
    for a reference to a slice, `(*p)[a..b]` / `(*r)[a..b]` for a pointer / a
    reference to an array, `slice(p, n)` for a thin pointer to anything else
    except a peripheral type; none for an integer or a reference to a sized

## 4. test(e2e): a driver over buffers behind references
- Status: done
- Implements: the program on QEMU above; ADR 0108, "Conformance tests".
- Changes: `tests/e2e/slice_driver.ers`.
- Tests: the program on both targets at `-O0` and `-O`, its output and exit
  code; its wrong uses in `tests/ui/slice_driver_errors.ers` (two `&mut`
  sub-slices of `line` in one call, a write of `line` while a `&[u8]` of it
  is used later, `len(s)` while a reborrow of `*s` is in use).
- Decisions:
  - The program is written as the plan describes, with three details the
    plan does not fix. `frame::encode` calls a private `number(n, out)`, which
    formats `n` in a scratch `[u8; 10]` held as `digits: &mut [u8]`, calls
    `decimal(n, digits)` (lent), copies `&(*digits)[start..]` to `out` and
    returns `len(digits) - start`; `encode` itself writes each part through
    `&mut (*out)[at..]`. So `&(*digits)[start..]` is in `number`, not in
    `encode`, to use it once for the length and once for the checksum. `uart`
    reaches the board as `crate::board::putc`, since a `use` of the root does
    not reach inside a module; `frame` imports `fmt`'s functions with `use
    super::fmt::{copy, decimal}`.
  - Payloads and values (checked by hand, the checksum `h = h * 31 + byte`
    wrapping in 32 bits): "abc" gives `3:abc;96354` ((97 * 31 + 98) * 31 + 99);
    "Erebos" gives `6:Erebos;2083799438`; "" gives `0:;0`. The three show the
    length digits, a checksum of five and of ten digits, and an empty payload
    (an empty `&[u8]` copied and a checksum of 0). The buffer is not cleared
    between encodes: after the empty one, `&line[n..n + 4]` is `ebos`, the
    bytes 4 to 7 of the second encoding, which pins that `encode` writes only
    the bytes it reports. `&line[n - 5..n + 3]` after the fill is `96354...`
    (a range whose bounds are computed, across the end of the encoding and the
    start of the dots). The loop over `small: [u8; 8]` lent as `r: &mut [u8]`
    prints `aaaaaaa7`/`7`, `bbbbb407`/`407`, `ccccc807`/`807` (digits written
    at the end by `decimal(i * 400 + 7, r)`, so the start is 7, 5, 5); `show(r)`
    reads the `&mut [u8]` converted to `&[u8]`, `show(&(*r)[start..])` a
    sub-slice of `*r`, and `fill(r, ..)` and `decimal(.., r)` lend it, all with
    `r` used after each call.
  - `main` shadows `n` and `frame` shadows `digits` (`let` with the same name
    again): the compiler accepts it and the program is shorter than with a
    name per value.
  - The program has no `targets:` header, so it runs on both targets at both
    levels, and needs no C file; no harness change was needed (`tests/e2e.rs`
    runs every `tests/e2e/*.ers`).
  - `tests/ui/slice_driver_errors.ers` is `// emit: mir`, like
    `slice_borrows_errors.ers`: the three errors are `analysis::borrow-conflict`
    on functions named after the wrong uses (`halves`, `write_while_read`,
    `length_of_a_reborrowed`), with `line: [u8; 32]` and the `copy`, `write`
    and `fill` of the driver as empty functions. The snapshot was read: three
    errors, `copy(&mut line[..16], &mut line[16..])` "cannot borrow
    `line[_.._]` as mutable while it is borrowed" with the second range
    labelled borrowed as mutable and the call "the borrow is used later here";
    `line[0] = b'x'` "cannot assign to `line[_]` while it is borrowed" with the
    borrow labelled at `&line[..8]` and the use at `write(head)`; `len(s)`
    "cannot use `s` while it is borrowed as mutable" with the borrow at `&mut
    (*s)[1..]` and the use later at `fill(rest, ..)`. A file with an error
    prints only errors, so the accepted forms are in the e2e program.
  - Left open: nothing; the program exposed no compiler problem.

## Left open

Minor findings the reviews left open, with when each was found; the same
entries are in `docs/open-findings.md`, ending with `(M5.4b)`.

- Step 1 review: `touch(&mut (*s)[0], &(*s)[1])` on a slice gives two errors
  (the index check reads `s` through `len(s)` while the `&mut` element is
  live, then the elements overlap); on an array it gives one. It follows ADR
  0108 ("`len(s)` is a read of `s`") and is only noisy. Step 3 review: in
  `two(&mut (*s)[..4], &mut (*s)[4..])` the message is "cannot use `s` while it
  is borrowed as mutable", where "cannot borrow `(*s)[_.._]`" would match the
  other cases of the file.
- Step 1: `s[i]` on a reference to a slice keeps the M5.4a `ty::cannot-index`
  help, which writes `(*r)[i]` for any reference; ADR 0108 names `(*s)[i]`.
- Step 1 review: `layout::of` works on `hir::Ty`, whose `slice_elem` and
  `is_aggregate` stay raw-only, so a HIR `&[T]` would get a thin pointer's
  layout. No input reaches it (a reference cannot be a `size_of` operand, a
  field, an element or a return type), so it is a latent trap if references
  ever become layout operands.
- Step 1 review: the `later_use` fix in `src/analysis/borrows.rs` changes
  behavior for any body without a loop, and no test pins it on an array
  (`touch(&mut a[i], &a[j])`).
- Step 2 review: `len(&buf)` leaves a dead `_7 = &_1` in MIR, so `len(&mut
  buf)` takes a `&mut` borrow of `buf` that can conflict with a live borrow;
  it matches how a written `&mut buf` is treated.
- Step 2 and 3: `name()` writes `ConstSubslice(0, N)` of an `N`-element array
  as the array, so a written `&buf[0..N]` reads "`buf` is borrowed here",
  like the converted `&buf`; MIR has no flag to tell them apart.
- Step 3 review: `&raw const (*v)[n..]` through a volatile pointer has type
  `*const [u8]`, as `&raw const (*v)[n]` does today (recorded in the
  Decisions).
- Step 4 review: the comment in `tests/e2e/slice_driver.ers` says the checksum
  wraps in 32 bits, but no payload of the program wraps (the largest value is
  2083799438); drop the word or add a payload that wraps. The Decisions of
  step 4 say `number` is used "once for the length and once for the checksum"
  (it is called twice and uses `&(*digits)[start..]` once, for the `copy`),
  and that the ui file has `copy` take a `&[u8]` (it takes a `&mut [u8]`, to
  give two `&mut` sub-slices in one call).
- Step 5 review: `docs/reference.md` says a reference to a slice casts "as the
  raw slice of its mutability does" (around line 2559), which reads as if
  `&[T] as *mut [T]` were rejected; the compiler accepts it. A few lines of
  the new prose are broken or overlong (around lines 166, 287, 1832, 2279,
  2349, 2881, 2893) and "the exception that is not one" (around line 2657) is
  cryptic.
- Final review: `slice_index` and `reference_slice_index` in
  `src/mir/build.rs` evaluate the index before reading `len(s)`, where ADR
  0109 ("What MIR building writes") writes `len(s)` first; ranges read the
  length first. It is observable only through a raw-slice variable reassigned
  inside the index (`(*p)[{ p = q; 0 }]`), which is M5.4a behavior, and the
  Decisions of step 3 do not say it differs from the ADR. The plan's test
  bullet for `slice_borrows_conversion.ers` expects the label "converted to a
  slice here" for the `held` case; the snapshot has "`buf` is borrowed here"
  at `&buf`, which is right (the conversion is a reborrow rooted at `r`), and
  `held_mut` and `held_unique` cover the other label.
- Out of scope from the start, left for later: splitting a `&mut [T]` in two
  halves in use together, `base[..]` and `base[a..=b]`, `assert` with a `&[u8]`
  message (M5.7), references to slices through volatile raw slices, `static
  mut` and peripherals (M5.4c), `core` and the tests moved to references
